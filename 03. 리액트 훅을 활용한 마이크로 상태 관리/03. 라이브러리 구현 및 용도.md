### 06. 전역 상태 관리 라이브러리 소개

- **데이터 중심 접근 방식**

  - 컴포넌트가 언마운트 돼도 데이터가 메모리에 남아있음
  - 대표적인 라이브러리: **Redux**, MobX, Zustand (일반적인 사용법)
- **컴포넌트 중심 접근 방식**
  - 리액트 **내부에** 있는 상태
  - contextAPI

⇒ 둘은 같이 사용할 수 있으며, 적재적소에 사용하는것이 중요함.

- **리렌더링 최적화 3가지 패턴**

1. **선택자 함수**

```tsx
const Component = () => {
  const value = useSelector((state) => state.b.c);
  return <>{value}</>;
};
```

- `useSelector((state) => state.b.c)`처럼
  전역 상태에서 어떤 부분을 쓸지를 함수로 명시하는 방식
- 상태가 바뀔 때마다:
  - 선택자 함수를 다시 돌려보고, 이전 값과 현재 값을 비교해서,달라졌을 때만 리렌더링.
- 어떤 부분을 사용하는지 명시적으로 적어준다 → 수동 최적화라고 봄.
- 장점:
  - 어디서 어떤 필드를 보고 있는지 코드만 봐도 딱 보임.
  - 파생 값(계산된 값)도 쉽게 만들 수 있음.
- 단점:
  - 선택자가 복잡해질수록 메모이제이션, 커스텀 비교 함수 등 고려할 게 많아짐.

1. **속성 접근 감지**

```tsx
const Component = () => {
  const trackedState = **useTrackedState();**
  return <p>{trackedState.b.c}</p>;
};
```

`useTrackedState()` 같은 훅으로 추적 가능한 상태를 가져옴 → 자동 최적화

프록시 필요 ⇒ 프록시에 기록된걸 확인해서 상태 바뀔때 그 프로퍼티 변경된 경우에 리렌더링

1. **아톰**

```tsx
const globalState = {
  a: atom(1),
  b: atom(2),
  c: atom(3),
};

const Component = () => {
  const [value] = useAtom(globalState.a);
  return <>{value}</>;
};
```

- 리렌더링을 발생시키는데 사용되는 최소 상태 단위
- 완전히 분리된 아톰은 사실상 별도의 전역 상태처럼 생각할 수 있음.
- 파생 아톰(다른 아톰들을 기반으로 계산되는 아톰)을 만들면,
  의존성은 자동 추적되지만 어떤 아톰을 쓸지는 우리가 명시적으로 정의.
- 책에서는
  - 수동 최적화(선택자)
  - 자동 최적화(프로퍼티 추적)
    사이에 있는 중간 정도의 접근으로 설명

### 08. Jotai

### Jotai 이해하기

**구문 단순성**

- Jotai의 기본은 **`atom` + `useAtom`** 딱 두 가지로 단순
- `atom(초기값)`으로 전역 상태 “설정 객체”를 만들고, 컴포넌트에서 `useAtom`으로 꺼내 쓰면 된다

**동적 아톰 생성**

- Jotai스토어는 **아톰 구성 객체**와 아톰 값으로 구성된 weakMap객체
- **아톰 구성 객체 -** atom함수로 생성
- **아톰값** - useAtom훅이 반환하는 값
- 구독은 아톰기반이므로 useAtom훅이 스토어에 있는 특정 아톰을 구독한다는것을 의미한다.
  - 불필요한 리렌더링을 피할 수 있는 기능을 제공

**렌더링 최적화**

- **atom 단위 구독**
  - 컴포넌트는 **필요한 atom만** `useAtom` / `useAtomValue` 로 구독한다.
  - 어떤 atom이 변경되면, **그 atom을 구독 중인 컴포넌트만 리렌더** 된다.
- **읽기/쓰기를 나눠서 더 줄이는 패턴**
  - `useAtomValue(atom)` → 값만 읽고 setter는 필요 없는 컴포넌트에 사용.
  - `useSetAtom(atom)` → 값은 필요 없고, setter만 필요한 버튼/액션 컴포넌트에 사용.
  - 이렇게 나누면:
    - 읽기만 하는 컴포넌트는 값 변경에 의한 리렌더를 최소화.
    - setter만 쓰는 컴포넌트는 atom 값에 의존하지 않아서 리렌더가 더 적다.
- **파생 atom을 활용한 최적화**
  - 합계/필터링 결과 같은 파생 상태는 **파생 atom** 하나로 묶어두고,
    그 atom만 구독하면 나머지 상세 상태 변경의 영향 범위를 줄일 수 있다.

**Jotai가 아톰 값을 저장하는 방식 이해하기**

- 무슨말인지 한참 보다가 뭔느낌인진 알겠는데 정리를 못하겠습니다….
- 뭔가 냉장고가 있으면 Zustand는 칸칸이 나눠진 도시락통같은곳에서 김치쪼금 가져다 쓰고 계란 조금 가져다 쓰고 이런느낌
- Jotai는 개별 반찬통을 하나씩 꺼내 쓰는 느낌..?

**배열 구조 추가하기**

- **아이템 개수가 동적으로 변하는 리스트**에서, 각 아이템마다 독립된 atom을 만들어서 관리할 수 있다.

### 10 시나리오4: React Tracked

- 리액트에서 전역 상태를 쓰면 가장 먼저 떠오르는 도구가 Context지만,
  Context는 value가 바뀌는 순간 연결된 컴포넌트가 줄줄이 리렌더되는 구조라 성능 이슈가 발생함.
- React Tracked는 새로운 상태 모델이 아니라, 이 문제를 해결하기 위해 등장한 렌더링 최적화 전용 도구
- useState, useReducer, Redux 같은 기존 상태를 그대로 사용 ⇒ 그 위에 Proxy를 얹어서

- 몇주째 말하듯.. 내가 필요한 영역중에 전역 상태 비중이 큰 편은 아니라 React Tracked가 당장 필요한 상황은 아니지만, Context 기반으로 구조가 좀 커지는 순간에는 상태 모델을 갈아엎지 않고 성능을 잡는 방법으로 **기억해둘 만한 도구, 지식 확장**의 개념으로 알아두면 괜찮은거 같음
