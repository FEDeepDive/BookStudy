# CHAPTER 7 리액트 동시성

## 📌7장의 목적

- 리액트가 동시성을 지원하기 위해 어떤 방법과 기능을 사용하는지 설명하기

## 📌동시성 렌더링

동기식 렌더링 방식의 문제점은, 렌더링 작업이 다른 작업들을 블로킹하여 렌더링 작업 중에 일어나는 사용자의 상호작용(즉 우선순위가 높은 작업)에 즉각적인 반응을 할 수 없다는 것이다. 이에 리액트는 **동시성(Concurrency) 매커니즘**을 구축해, 백그라운드에서 동시에 여러 버전의 UI를 준비할 수 있게 한다. 동시성 렌더링을 통해 렌더링 작업을 인터럽트하고 급한 작업부터 처리할 수 있다. 또 일시 중단한 렌더링 작업을 나중에 재개하거나, 아예 파기할 수도 있다.

리액트는 내부 구현을 통해 동시성 렌더링을 가능하게 한다. 예를 들어 파이버 재조정자, 더블 버퍼링, 렌더 레인, 스케줄러 등을 통해 업데이트 문제, 우선순위 결정, 순서 관리 등의 작업을 **사용자가 신경쓰지 않아도 알아서 처리되게끔** 한다.

따라서 **사용자가 이를 알 필요는 없다!** 사용자는 그저 평소처럼 개발하고, 리액트가 제공하는 새로운 기능을 필요에 따라 사용하기만 하면 된다. 이게 바로 리액트가 존재하는 이유이자 추상화 계층으로서 제공하는 진정한 가치이다. (하지만 우리는 알아보고 있다..!)

```
💡

과거에는 ‘동시성 모드’라는 용어를 사용했는데, 이름 때문에 ‘동시성을 on/off하는 기능’이라는 오해가 있었다. 그래서 동시성이 렌더링 동작의 변화임을 강조하기 위해  ‘동시성 렌더링’으로 바꾸게 되었다. (참고: [리액트-18 토론](https://github.com/reactwg/react-18/discussions/64))

```

이제 동시성 렌더링을 지원하기 위한 리액트의 내부 구현과 기능을 알아보자.

## 📌내부 구현

### 파이버 재조정자

동시성 렌더링을 가능하게 하는 리액트의 핵심 메커니즘으로, 리액트 16에서 도입되어 스택 재조정자를 대체하였다. 작업 단위를 ‘파이버’라는 작은 단위로 분할하고 단일 연결 리스트로 파이버 트리를 구성해, 렌더링 작업을 일시 중지 또는 재개하고, 우선순위를 설정해 업데이트를 지연 또는 예약할 수 있다.

### 업데이트 예약과 지연

사용자는 상호작용에 대한 반응이 즉각적으로 나타나기를 기대한다. 예를 들어 클릭을 했는데 즉각적으로 반응이 나타나지 않는다면, 사용자는 앱이 느리거나 먹통이라고 판단할 것이다. 이런 상황에서는 상호작용에 대한 업데이트가 화면 전환보다 먼저 이루어져야 한다. (뒤에서 다룰 `useTransition`을 사용해 전환 업데이트를 지연할 수 있다.)

리액트는 작업의 우선순위를 정하여, 우선순위가 높은 업데이트는 즉각 처리되도록 예약(schedule)하고 우선순위가 낮은 업데이트는 지연(defer)한다. 이를 통해 애플리케이션 응답성을 높이고, 과부하 상황에서도 UI를 매끄럽게 유지한다. 스케줄러, 렌더 레인, 여러 API 등을 활용해 업데이트 예약과 지연을 구현한다.

### 스케줄러

리액트 스케줄러는 타이밍 관련 유틸리티를 제공하는 독립형 패키지로, 파이버 재조정자 내에서 사용된다. 리액트 스케줄러는 렌더 레인을 통해 작업의 우선순위를 설정하고, 우선순위에 따라 마이크로태스크를 예약해서 메인 스레드의 제어를 관리하고 원활한 실행을 보장하는 역할을 한다.

- 리액트는 호스트 환경(ex. 브라우저)의 태스크 스케줄링(이벤트 루프 및 태스크 큐)을 사용해 스케줄링함. 마이크로태스크 큐가 가장 먼저 처리된다는 점을 활용해, 루트 스케줄 관련 작업에 대한 콜백을 마이크로태스크 큐에 집어넣음
- 리액트는 우선순위 큐(힙으로 구현된)에서 우선순위가 높은 작업을 꺼내 처리함 ⇒ 작업을 중단하고 나서 큐에 기존 작업보다 우선순위가 높은 작업이 들어왔다면, 재개 시 새 작업부터 수행하게 됨
- 리액트는 “`리액트 루트`(=커밋 단계에서 교체되는 노드)”가 업데이트되면 `ensureRootIsScheduled` 함수를 호출해 두 가지 작업을 수행함
    - 루트가 스케줄에 포함되도록 보장함
    - 루트 스케줄 처리를 위한 마이크로태스크가 이미 존재하는지 확인함

### 렌더 레인

리액트는 컴포넌트가 업데이트되거나 렌더 트리에 새로 추가되면, 해당 작업에 `레인`을 할당한다.

- 레인: 우선순위 레벨을 나타내는 단위
- 레인에는 여러 종류가 있고, 레인마다 우선순위가 다름
- 우선순위는 업데이트 종류(사용자 상호작용, 데이터 페치, 백그라운드 작업 등)와 요소의 가시성 같은 요인에 따라 정해짐

리액트는 다음과 같은 방식으로 업데이트를 예약하고 우선순위를 정한다.

- **업데이트 수집**: 마지막 렌더링 이후 예약된 모든 업데이트를 수집 & 레인에 할당
    - 우선순위 결정 및 레인 할당 과정
        - 업데이트가 발생한 콘텍스트 확인 (⇒ 업데이트가 어디서, 어쩌다 발생했는지 파악)
        - 콘텍스트에 따라 우선순위 추정 (⇒ 사용자 입력 결과같은 건 우선순위가 높음)
        - 우선순위가 재정의된 경우 해당 우선순위 사용
        - 올바른 레인에 업데이트 할당
- **레인 처리**: 우선순위가 높은 레인부터 처리, 이때 같은 레인의 업데이트는 일괄 처리함
- **커밋**: 모든 업데이트 처리 후 DOM에 변경 사항 반영

## 📌제공 기능

아래 설명하는 것 외에 서스펜스 같은 것도 동시성 렌더링을 위한 기능이라 할 수 있음.

### useTransition

**업데이트의 우선순위를 낮추는 훅**으로, 이를 통해 긴급한 업데이트부터 처리하여 애플리케이션 응답성을 높일 수 있다.

- **레퍼런스**
    - 매개변수: 없음
    - 반환값
        - `isPending`: 지연한 업데이트가 완료되었는지 여부 (→ 이를 사용해 조건부 렌더링 가능)
        - `startTransition`: 업데이트를 지연할 수 있게 해주는 함수

`startTransition` 함수 내 업데이트는 **트랜지션 레인**에 들어가는데, 이 레인은 상태 업데이트가 들어가는 **Sync 레인보다 우선순위가 낮다**. 렌더 레인 메커니즘에 따라 우선순위가 높은 Sync 레인부터 일괄 처리되고 이후에 트랜지션 레인이 처리된다.

`startTransition` 함수 내에서 호출되는 함수를 “Actions”라고 한다. Action 내에서 상태를 업데이트하거나 사이드 이펙트를 수행할 수 있다. 이 작업은 사용자 상호작용처럼 긴급한 업데이트를 블로킹하지 않고 백그라운드에서 수행되므로 Transition이 진행되는 동안에도 상호작용이 가능하다.

`startTransition` 으로 업데이트를 감싸면 상호작용이 빠르게 여러 번 일어났을 때, 먼저 일어난 상호작용 업데이트가 완료될 때까지 기다리지 않고 마지막 상호작용 업데이트를 즉시 처리한다. 즉 최종 업데이트만 수행하고 중간 작업들은 bailout(무시)한다.

[예를 들어](https://ko.react.dev/reference/react/useTransition#examples) 버튼으로 조절할 수 있는 `count`와 여기에 10을 곱한 값 `total`이 있다고 하자. `count`를 1에서 5까지 빠르게 증가시키면 `total` 또한 10에서 50으로 업데이트될 것이다. 이 계산이 오래 걸리거나 복잡하다면, 화면에는 `total`의 변화가 10에서 50까지 순차적으로 렌더링될 것이다. 사용자에게는 화면이 느리게 점차적으로 렌더링되는 것처럼 보이게 된다. 반면 이 업데이트를 `startTransition`으로 감싸면 `total`이 50이 됐을 때, 즉 **최종 요청이 완료된 후에 화면을 렌더링하여 부드러운 전환을 제공**할 수 있다.

`startTransition` 함수는 훅이 아닌 일반 함수로도 사용할 수 있다(API를 제공함).

### useDeferredValue

값 변경에 따라 **새로운 UI를 준비하는 동안, 이전에 렌더링한 UI를 보여주는 훅**이다. 예를 들어 검색 결과를 보여줄 때 입력 값이 변경될 때마다 결과를 렌더링하는 게 아니라, 입력이 완료될 때까지 이전 입력 값에 대한 결과를 보여주고, 입력이 완료되면 새 입력 값에 대한 결과를 렌더링한다. (덜 중요한)결과를 렌더링하느라 (중요한)입력 상호작용이 느려지거나 차단되는 것을 방지하고, 최종 입력 값을 기준으로 한 번만 무거운 연산을 실행한다.

단, 이전 값을 기준으로 렌더링한 결과를 보여주기 때문에 사용자가 보는 화면은 오래된(stale) 것일 수 있다. 새로운 UI를 준비하는 동안 이전 렌더링 결과에 스타일을 입혀(ex. 투명도 낮추기) UI가 변경될 예정임을 사용자에게 알리는 것이 좋다.(아니면 훅을 사용하지 않거나)

- 안 쓴 거랑 뭐가 다른가? ⇒ 안 쓰면 값 변경마다 요청이 생겨 [성능 최적화가 안 됨](https://ko.react.dev/reference/react/useDeferredValue#examples)
- `Suspense` 쓰면 되지 않나? ⇒ 폴백 UI 대신 이전 결과를 그대로 보여주어 부드러운 UI 전환 가능
- 디바운싱/스로틀링과 뭐가 다른가?
    
    
    |  | 디바운싱/스로틀링 | useDeferredValue |
    | --- | --- | --- |
    | delay 설정 | 개발자가 직접 해야 함 | 리액트가 동적으로 최적화함 |
    | 지연하는 것 | 값이 늦게 바뀌도록 제어함 | 값은 즉시 바뀌고, 이 값이 UI에 반영되는 시점을 제어함 |
    | 렌더링 중단 가능 여부 | 실행 도중에 렌더링 중단 불가</br>(⇒오히려 상호작용을 차단할 수도 있음) | 실행 도중에 렌더링 중단 가능 |

`useDeferredValue` 는 다음과 같은 상황에서 사용해볼만 하다.

- 대규모 데이터를 검색 또는 필터링할 때
- 복잡한 시각화나 애니메이션을 렌더링할 때
- 백그라운드에서 서버 데이터를 업데이트할 때 (데이터 페치 → 상태 변화 → 그에 따른 작업을 지연)
- 사용자 상호작용에 미칠 수 있는 연산 집약적 작업

### useSyncExternalStore

동기식(Synchronous) 렌더링의 경우 작업이 차례로 처리되지만, 동시성 렌더링에서는 업데이트 순서가 어긋날 수 있다. 예를 들어 컴포넌트가 렌더링되는 중간에, 컴포넌트가 의존하고 있는 외부 값(ex. DB 내 데이터)이 변경되었다고 하자. 동시성 렌더링의 경우 어떤 컴포넌트는 바뀌기 이전 값을, 어떤 컴포넌트는 바뀐 값을 보고 렌더링할 수 있다. 이러한 문제를 **티어링(tearing) 현상**이라고 한다.

`useSyncExternalStore` 훅은 외부(=비 React 코드) store를 구독할 수 있는 훅으로, 애플리케이션 외부 상태와 내부 상태를 동기화(Synchronize)해 티어링 문제를 방지한다. 즉 렌더링 중에 의존 값이 바뀌어도 일관된 UI를 유지할 수 있도록 보장한다.

## 📌복습하기

- **1. 리액트의 파이버 재조정자는 무엇이며, 복잡한 고성능 애플리케이션을 처리하는 데 어떻게 도움이 되나요?**
    
    파이버 재조정자는 작업을 파이버(Fiber)라는 작은 단위로 나누어 효율적으로 처리합니다. 파이버 구조 덕분에 렌더링을 중간에 멈추거나 재개할 수 있고, 동시성 렌더링도 가능합니다. 복잡한 고성능 애플리케이션에서도 우선순위가 높은 작업부터 처리할 수 있어 궁극적으로 애플리케이션의 응답성을 높일 수 있습니다.
    
- **2. 리액트에서 업데이트 예약 및 지연의 개념을 설명하세요. 부하가 많은 상황에서도 원활한 사용자 경험을 유지하는 데 어떻게 도움이 되나요?**
    
    리액트는 부하가 많은 상황에서도 애플리케이션의 응답성을 높이기 위해 중요한 업데이트를 먼저 스케줄링하고, 덜 중요한 업데이트는 우선순위를 낮춰 나중에 스케줄링되도록 지연하는 방식을 사용합니다.
    
- **3. 리액트의 렌더 레인이란 무엇이며, 업데이트 실행을 어떻게 관리하나요? 렌더 레인이 비트마스크를 사용해 여러 우선순위를 처리하는 방법을 설명하세요.**
    
    렌더 레인은 렌더링 우선순위를 결정하는 메커니즘입니다. 레인이란 우선순위 수준을 나타내는 단위로 여러 종류가 있습니다. 중요한 업데이트일수록 우선순위가 높은 레인에 할당되며, 각 레인은 우선순위대로 처리됩니다.
    
    비트마스크를 사용해 우선순위를 확인하는 등의 작업을 매우 빠르게 처리합니다. (아래 예시 참고)
    
    ```javascript
    const SyncLane = 0b0000000000000000000000000000001; // 즉시 업데이트
    if ((currentLanes & SyncLane) !== 0) {
      // 현재 작업 중에 SyncLane이 포함되어 있음
    }
    ```
    
- **4. 리액트에서 useTransition과 useDeferredValue 훅을 사용하는 목적은 무엇인가요? 각 훅이 유용한 상황을 설명하세요.**
    - useTransition: 덜 중요한 업데이트의 렌더링 우선순위를 낮춰 중요한 업데이트를 우선 처리하기 위해 사용합니다. 사용자의 상호작용을 차단하지 않는 동시에 백그라운드에서 업데이트 처리를 해야 할 때 유용합니다.
    - useDeferredValue: 렌더링과 관련된 업데이트를 디바운싱처럼 지연했다가 처리해야 할 때 사용합니다. 예를 들어 대규모 데이터 검색이나 사용자 상호작용이 일어날 때마다 무거운 작업을 처리해야 하는 경우처럼, 비용이 높은 작업의 실행 횟수를 최소화해야 할 때 유용합니다.
- **5. useDeferredValue를 사용하는 것이 부적절한 상황은 어떤 상황일까요? 이 훅을 사용할 때 고려할 장단점은 무엇인가요?**
    
    useDeferredValue 훅을 사용하면 새 상태에 대한 렌더링을 진행하는 동안 이전 상태 렌더링 결과를 사용하게 됩니다. 로딩 UI를 중간에 거치지 않아서 더 매끄러운 UX를 제공할 수 있지만, 오래된(stale) 렌더링 결과를 제공하게 된다는 단점이 있습니다.
    
    이러한 특징 때문에 사용자 상호작용에 의한 업데이트를 지연할 때에만 사용하는 것이 적절합니다. 그렇지 않은 경우, 예를 들어 백그라운드에서 데이터가 들어오고 있는데 이를 지연하면 최신 데이터가 있음에도 UI가 일부러 느리게 갱신됩니다.
