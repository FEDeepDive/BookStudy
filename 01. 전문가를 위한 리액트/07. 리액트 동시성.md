## 7.1 동기식 렌더링의 문제
- 동기식 렌더링은 메인 스레드를 가로막기 때문에 사용자 경험이 저하된다는 문제를 가지고 있음
  - (#) 04. 재조정 챕터에서도 이야기한 바 있지만, 비슷한 것으로 Android에 있는 [ANR 오류](https://developer.android.com/topic/performance/vitals/anr?hl=ko)를 들 수 있을 듯
  - 해당 문제를 완화하는 방법으로 널리 사용되는 것 중 하나가 바로 일괄 처리(Batching)
- 동기식 렌더링에는 우선순위라는 개념이 없음
  - 모든 갱신이 동일하게 취급되고, 사용자에게 보여야 하는지 여부를 따지지 않음
  - 보이지 않는 탭이나 모달창에 가려진 콘텐츠 등 실제로 사용자가 볼 수 없는 것도 동등한 수준으로 취급해 렌더링함
- 리액트는 동시성 렌더링을 사용하여 갱신 작업의 중요도와 긴급도에 따라 우선순위를 정함
  - 더 중요한 갱신이 덜 중요한 갱신 때문에 가로막히지 않도록!
  - 사용자 상호작용이나 애니메이션 같은 작업은 더 중요하기 때문에 CPU를 많이 소모하는 덜 중요한 작업보다 우선적으로 처리됨
- 또한 동시성 렌더링 덕분에 여러 프레임에 걸쳐 작업을 수행하거나 중지할 필요성이 있을 때 중지할 수도 있게 됨
  - 렌더링 프로세스를 더 작은 덩어리로 분할해 점진적으로 처리하는 타임 슬라이싱(Time slicing)

## 7.2 파이버 다시 보기
- 동시성 렌더링을 가능케 하는 리액트의 핵심 메커니즘은 리액트 16부터 도입된 "파이버 재조정자"
- 파이버를 활용하여 렌더링 작업을 일시적으로 중지 및 재개하거나, 우선순위를 설정해 갱신을 지연하거나 예약함

## 7.3 업데이트 예약과 지연
- 파이버 스케줄러는 리액트에서 갱신을 예약하고 지연하는 기능을 스케줄러와 기타 API에 의존하여 구현함
  - (#) 예약이라는 표현은 뭔가 잘 안 와닿는 것 같아요... 스케줄링이라는 표현이 좀 더 익숙한데
  - 스케줄러는 해야 할 작업이 있을 때 `setTimeout`, `MessageChannel` 등의 "브라우저" API를 사용해서 작업의 실행 순서를 광리하는 시스템
- 예를 들어 실시간 채팅 애플리케이션을 만든다고 할 때, 무엇보다 우선적으로 처리되어야 하는 UI 갱신은 "텍스트 입력에 대한 갱신"!
  - Why? 부드러운 사용자 경험을 보장하기 위해서
- 서버에서 도착한 메시지를 렌더링할 때, 텍스트 입력에 대한 갱신보다 해당 작업의 우선순위를 낮출 수 있어야 함
  - 동일한 수준으로 다루면 사용자 입력에 지연이 발생하기 때문

## 7.5 렌더 레인
- 렌더 레인은 작업의 렌더링과 우선순위 관리를 효율화하는 요소
  - 레인은 "우선순위 수준"을 나타내는 단위, 리액트가 렌더링 주기에서 처리할 수 있는 작업을 의미함
  - 다양한 갱신의 우선순위는 갱신이 발생하는 문맥에 따라 다르게 이해할 수 있음
    - 예를 들어 `setState`가 클릭 이벤트 핸들러 내부에서 호출되면 우선순위가 가장 높은 레인에 배정됨
    - 또 예를 들어 `setState`가 "트랜지션(Transition)" 내에서 호출되면 우선순위가 낮은 레인에 배정됨
- (#) 중요한 것은 결국 렌더 레인의 어떤... 각각의 우선순위나 이름 같은 것을 외우는 것이 아니라, "작업에는 서로 다른 수준의 우선순위가 적용되며 이러한 우선순위에 따라 스케줄링이 이루어진다"는 사실일듯
- 우선순위는 갱신의 종류와 컴포넌트의 가시성 같은 요인에 따라 정해짐
- 리액트는 다음과 같은 방식으로 렌더 레인을 사용해 갱신을 예약하고 우선순위를 정함
  1. 업데이트 수집: 마지막 렌더링 이후에 예약된 모든 갱신을 수집해서 우선순위에 따라 각 레인에 할당함
    - 갱신이 발생한 문맥과 내부 휴리스틱에 기반하여 우선순위를 추정하고, 사용자가 우선순위를 재정의했는지 확인하여 비교한 후 결정하여 올바른 레인에 할당함
  2. 레인 처리: 우선순위가 가장 높은 레인부터 시작해 각 레인에 할당된 갱신을 처리하며, 이 때 같은 레인의 갱신은 일괄 처리됨
  3. 커밋 단계: 모든 갱신이 처리된 후 커밋 단계로 진입해 변경 사항을 DOM에 적용하고 효과(Effect)를 실행하며 기타 마무리 작업을 수행함
    - 사실상 리액트가 존재하는 이유
    - 리액트가 이런 갱신 / 우선순위 결정 / 순서 관리 등의 문제를 자동으로 처리해주기 때문에 개발자는 애플리케이션 자체에 집중할 수 있음
    - (#) 처리하는 내용 자체는 파이버 시절 이전보다 많아지고 복잡해졌지만, 근본적으로 이 단계만큼은 결국 하는 일이 달라지지 않았다고 생각합니다
  4. 이상의 내용이 계속 반복됨

## 7.6 useTransition
- 컴포넌트에서 상태 갱신의 우선순위를 관리하고 우선순위가 높은 갱신으로 인해 UI가 응답하지 않는 것을 방지하는 hook
- `useTransition`에서 반환된 `startTransition` 함수로 감싸진 모든 갱신은 `TransitionLanes` / `TransitionHydrationLane`에 들어감
  - `Sync` 레인보다 우선순위가 낮다는 특성을 활용해 갱신 타이밍을 제어함
- 트랜지션이 진행 중인지 여부를 나타내는 불리언 값 `isPending`을 함께 반환함
- hook이기 때문에 함수 컴포넌트나 커스텀 hook 내에서만 사용할 수 있음
  - hook이 아닌 일반 함수 `startTransition`도 존재!
    - `isPending`을 사용할 수 없지만 함수 컴포넌트 밖에서도 사용 가능
- 전환 중 "페이지 전환"은 사용자 상호작용에 대한 응답으로 발생하기 때문에 즉각적으로 이루어져야 하는 것처럼 보일 수도 있음
  - 그러나 다음 페이지가 `Suspense`를 통해 데이터를 가져와야 하는 경우 페이지 전환도 지연될 수 있음!

## 7.7 useDeferredValue
- 특정 UI 갱신을 나중으로 미루는 데 사용되는 hook
  - 애플리케이션이 연산이 많이 이루어져야 하는 작업을 처리할 때 유용함
- 값이 바뀌어도 UI가 매번 새롭게 리렌더링되지 않고 새 값으로 업데이트될 시점을 제어해 한 번에 새 값으로 갱신되게 함
  - 새 값이 도착하기까지 이전 값을 유지해 UI의 응답성을 높임
- `useDeferredValue`의 주요 목적은 덜 중요한 갱신의 렌더링을 지연하는 것
  - 디바운싱(debouncing)과 스로틀링(throttling)같이 갱신을 지연하는 방법도 있지만 개발자가 임의로 지연 시간을 설정해야 함
  - `useDeferredValue`는 지연 시간을 사용자 기기의 성능에 맞춰 조정함
  - 두 기법을 함께 사용해 종합적인 최적화를 달성하자!
- 갱신을 지연하면 사용자에게 표시되는 데이터가 오래된(stale) 데이터일 수 있음
  - 사용자가 지연된 데이터를 보게 될 떄 발생할 영향에 대해 고려해야
  - 사용자가 즉각적인 반응을 기대할 만한 갱신은 지연하면 안 됨!!

## 7.8 동시성 렌더링 관련 문제
- 동시성 렌더링은 성능과 응답성을 높이지만 새로운 문제도 가져다줌
  - 갱신의 처리 순서를 예측하기 어렵다는 문제 <- 예기치 않은 동작과 버그 유발 가능성이 높아짐
- 애플리케이션을 렌더링하는 컴포넌트가 의존하는 상태가 갱신될 때 발생하는 버그인 "티어링(tearing)"
  - (#) 티어링이라는 현상 자체는 렌더링할 때 많이 들어본 것 같네요! 게임 많이 해봤다면 한 번은 들어봤을 거 같은데
- 동기식 렌더링에서는 컴포넌트 트리를 따라 한 컴포넌트씩 차례로 렌더링하기 때문에 애플리케이션 상태가 항상 일관성을 유지함
- 더 긴급한 갱신을 우선 처리하게 되면 일관성 없는 데이터가 사용자에게 표시되는 티어링 현상이 발생할 수 있음
- 이런 문제를 해결하기 위해 `useSyncExternalStore`이라는 hook을 제공함
  - 애플리케이션의 내부 상태와 외부 상태를 동기화하는 hook
  - 외부 저장소에 변화가 발생할 때 동기적(synchronous)으로 갱신을 강제(즉, 동기화 - synchronize)해 일관성을 유지함

## 7.10 복습하기
1. 리액트의 파이버 재조정자는 무엇이며, 복잡한 고성능 애플리케이션을 처리하는 데 어떻게 도움이 되나요?
  - 리액트의 파이버 재조정자는 동시성 렌더링을 가능케 하는 리액트의 핵심 메커니즘
  - 렌더링 프로세스를 파이버라고 하는 작업 단위로 분할해 처리
  - 렌더링 작업을 일시적으로 중지 및 재개하거나 우선순위에 따라 스케줄링하거나 지연해 응답성과 성능을 개선할 수 있음
2. 리액트의 업데이트 예약 및 지연의 개념을 설명하세요. 부하가 많은 상황에서도 원활한 사용자 경험을 유지하는 데 어떻게 도움이 되나요?
  - 예약: 해야 할 갱신 작업이 있을 때 여러 API(브라우저 API 등)를 사용해서 작업이 처리될 타이밍을 예약/관리함
  - 지연: 사용자 상호 작용을 우선시해 응답성을 유지하기 위해 중요하지 않은 갱신의 우선순위를 낮춤
3. 리액트의 렌더 레인이란 무엇이며, 업데이트 실행을 어떻게 관리하나요? 렌더 레인이 비트마스크를 사용해 여러 우선순위를 처리하는 방법을 설명하세요.
  - 작업의 우선순위 수준을 나타내는 단위, 리액트가 렌더링 주기에서 처리할 수 있는 작업
  - 예약된 갱신들을 수집해서 우선순위에 따라 레인에 할당한 후 우선순위가 가장 높은 레인부터 같은 레인의 갱신을 일괄 처리
  - (#) 비트마스크 처리 방법은 글로 정리하기는 어려울 것 같은데 말로 하면서 정리하고 싶어요
4. 리액트에서 `useTransition`과 `useDeferredValue` 훅을 사용하는 목적은 무엇인가요? 각 훅이 유용한 상황을 설명하세요.
  - `useTransition`은 `useDeferredValue`는 모두 우선순위를 관리하는 hook
  - `useTransition`은 시각적으로 혼란을 줄 수 있는 갱신을 처리할 때 유용함
  - `useDeferredValue`는 연산이 많이 이루어져야 하는 작업을 처리해야 하는 애플리케이션을 최적화할 때 유용함
5. `useDeferredValue`를 사용하는 것이 부적절한 상황은 어떤 상황일까요? 이 훅을 사용할 때 고려할 장단점은 무엇인가요?
  - 사용자가 즉각적인 반응을 원하는 갱신인 경우 `useDeferredValue`를 사용해 갱신을 지연하는 것은 부적절함
  - 애플리케이션이 사용자 입력에 대한 갱신을 우선 처리할 수 있어 응답성을 유지할 수 있다는 장점이 있음
  - 이에 반해 사용자가 오래된 데이터를 보게 될 수 있다는 단점이 있음
