## 7.1 동기식 렌더링의 문제
- 동기식 렌더링은 메인 스레드를 가로막기 때문에 사용자 경험이 저하된다는 문제를 가지고 있음
  - (#) 04. 재조정 챕터에서도 이야기한 바 있지만, 비슷한 것으로 Android에 있는 [ANR 오류](https://developer.android.com/topic/performance/vitals/anr?hl=ko)를 들 수 있을 듯
  - 해당 문제를 완화하는 방법으로 널리 사용되는 것 중 하나가 바로 일괄 처리(Batching)
- 동기식 렌더링에는 우선순위라는 개념이 없음
  - 모든 갱신이 동일하게 취급되고, 사용자에게 보여야 하는지 여부를 따지지 않음
  - 보이지 않는 탭이나 모달창에 가려진 콘텐츠 등 실제로 사용자가 볼 수 없는 것도 동등한 수준으로 취급해 렌더링함
- 리액트는 동시성 렌더링을 사용하여 갱신 작업의 중요도와 긴급도에 따라 우선순위를 정함
  - 더 중요한 갱신이 덜 중요한 갱신 때문에 가로막히지 않도록!
  - 사용자 상호작용이나 애니메이션 같은 작업은 더 중요하기 때문에 CPU를 많이 소모하는 덜 중요한 작업보다 우선적으로 처리됨
- 또한 동시성 렌더링 덕분에 여러 프레임에 걸쳐 작업을 수행하거나 중지할 필요성이 있을 때 중지할 수도 있게 됨
  - 렌더링 프로세르를 더 작은 덩어리로 분할해 점진적으로 처리하는 타임 슬라이싱(Time slicing)

## 7.2 파이버 다시 보기
- 동시성 렌더링을 가능케 하는 리액트의 핵심 메커니즘은 리액트 16부터 도입된 "파이버 재조정자"
- 파이버를 활용하여 렌더링 작업을 일시적으로 중지 및 재개하거나, 우선순위를 설정해 갱신을 지연하거나 예약함

## 7.3 업데이트 예약과 지연
- 파이버 스케줄러는 리액트에서 갱신을 예약하고 지연하는 기능을 스케줄러와 기타 API에 의존하여 구현함
  - (#) 예약이라는 표현은 뭔가 잘 안 와닿는 것 같아요... 스케줄링이라는 표현이 좀 더 익숙한데
  - 스케줄러는 해야 할 작업이 있을 때 `setTimeout`, `MessageChannel` 등의 "브라우저" API를 사용해서 작업의 실행 순서를 광리하는 시스템
- 예를 들어 실시간 채팅 애플리케이션을 만든다고 할 때, 무엇보다 우선적으로 처리되어야 하는 UI 갱신은 "텍스트 입력에 대한 갱신"!
  - Why? 부드러운 사용자 경험을 보장하기 위해서
- 서버에서 도착한 메시지를 렌더링할 때, 텍스트 입력에 대한 갱신보다 해당 작업의 우선순위를 낮출 수 있어야 함
  - 동일한 수준으로 다루면 사용자 입력에 지연이 발생하기 때문

### 7.5 렌더 레인
- 렌더 레인은 작업의 렌더링과 우선순위 관리를 효율화하는 요소
  - 레인은 "우선순위 수준"을 나타내는 단위, 리액트가 렌더링 주기에서 처리할 수 있는 작업을 의미함
  - 다양한 갱신의 우선순위는 갱신이 발생하는 문맥에 따라 다르게 이해할 수 있음
    - 예를 들어 `setState`가 클릭 이벤트 핸들러 내부에서 호출되면 우선순위가 가장 높은 레인에 배정됨
    - 또 예를 들어 `setState`가 "트랜지션(Transition)" 내에서 호출되면 우선순위가 낮은 레인에 배정됨
- (#) 중요한 것은 결국 렌더 레인의 어떤... 각각의 우선순위나 이름 같은 것을 외우는 것이 아니라, "작업에는 서로 다른 수준의 우선순위가 적용되며 이러한 우선순위에 따라 스케줄링이 이루어진다"는 사실일듯
- 우선순위는 갱신의 종류와 컴포넌트의 가시성 같은 요인에 따라 정해짐
- 리액트는 다음과 같은 방식으로 렌더 레인을 사용해 갱신을 예약하고 우선순위를 정함
  1. 업데이트 수집: 마지막 렌더링 이후에 예약된 모든 갱신을 수집해서 우선순위에 따라 각 레인에 할당함
    - 갱신이 발생한 문맥과 내부 휴리스틱에 기반하여 우선순위를 추정하고, 사용자가 우선순위를 재정의했는지 확인하여 비교한 후 결정하여 올바른 레인에 할당함
  2. 레인 처리: 우선순위가 가장 높은 레인부터 시작해 각 레인에 할당된 갱신을 처리하며, 이 때 같은 레인의 갱신은 일괄 처리됨
  3. 커밋 단계: 모든 갱신이 처리된 후 커밋 단계로 진입해 변경 사항을 DOM에 적용하고 효과(Effect)를 실행하며 기타 마무리 작업을 수행함
    - 사실상 리액트가 존재하는 이유
    - 리액트가 이런 갱신 / 우선순위 결정 / 순서 관리 등의 문제를 자동으로 처리해주기 때문에 개발자는 애플리케이션 자체에 집중할 수 있음
    - (#) 처리하는 내용 자체는 파이버 시절 이전보다 많아지고 복잡해졌지만, 근본적으로 이 단계만큼은 결국 하는 일이 달라지지 않았다고 생각합니다
  4. 이상의 내용이 계속 반복됨
