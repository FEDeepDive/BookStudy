## 📌 6. 서버 사이드 리액트

**6.1 클라이언트 사이드 렌더링의 한계**

SEO, 성능, 보안

CSR 방식은 브라우저에서 자바스크립트를 실행해서 콘텐츠를 만드는 구조

그런데 검색엔진 로봇(크롤러)이 이 자바스크립트를 실행하지 못하거나, 실행해도 우리가 예상한 대로 작동하지 않을 수 있어서, 페이지 내용을 제대로 읽지 못할 수 있음 ⇒ 그럼 검색에 잘 안 걸릴 수도 있음.

**인상깊은 문구**

> “클라이언트 사이드 자바스크립트로만 구성되는 것은 웹의 설계 의도에 부합하지 않습니다.”

→ 웹은 애초에 HTML을 기반으로 누구나 접근 가능한 정보 시스템을 만들기 위해 설계되었음.

하지만 CSR 구조에서 HTML 없이 자바스크립트만으로 화면이 구성되면,

검색엔진, 스크린리더, 저사양 기기, JS 비활성 사용자는 정보를 아예 접근할 수 없게 됨.

→ 즉, 이런 방식은 웹의 철학인 ‘열린 접근성’을 위배한다는 것.

---

> “자바스크립트의 역할은 웹페이지를 보완해 개선하는 것이지 웹페이지 그 자체가 되는 것은 아닙니다.”

→ 자바스크립트는 애초에 **보조적 역할**, 즉 ‘향상’을 위한 기술이었음.

초기 웹에서는 JS가 없어도 페이지 내용을 볼 수 있었고, JS는 인터랙션, 애니메이션, 편의성 향상을 위한 수단이었음 하지만 리액트로 개발된 사이트를 보면 자바스크립트를 아예 꺼두면 **빈 화면**이 나옴

⇒ **웹 접근성 원칙**에서 크게 벗어난 방식

**6.3 하이드레이션**

> 서버에서 미리 렌더링한 정적 HTML을 클라이언트(=브라우저)에 보내주면, 브라우저는 자바스크립트를 로드하여 React의 상태, 이벤트 리스너 등을 연결함으로써 상호작용 가능한 UI로 완성시키는 과정

💬 책이 진짜.. 어려운말을 너~무 어렵게 설명한다..

**하이드레이션의 한계**

- 서버에서 렌더링된 HTML을 먼저 보여준 뒤,
- 클라이언트(브라우저)가 자바스크립트를 로드해서
  - 이벤트 리스너 연결
  - 상태 초기화
  - 다시 렌더링
- 이 일련의 과정을 **하이드레이션**이라 하며,
  > 인터랙션이 가능해지기까지 시간이 지연될 수 있다는 단점이 있음.

**재개 가능성**

- 서버가 **앱의 상태를 미리 직렬화해서 브라우저에 같이 보냄**
- 브라우저는 이걸 받아서 **그대로 "역직렬화"해서** 이어서 실행함

      → 리렌더링 없이 바로 상호작용 가능

      이러면 상호작용시간이 빨라짐.

      근데 이제 구현 난이도가 높아서 리액트 커뮤니티 내부에도 논쟁이 활발하다고 한다.

요약해보자면

- `react-dom/server`의 `renderToString()`을 이용해서 HTML을 서버에서 만들고
- 클라이언트에서는 그 HTML을 받은 다음 `hydrateRoot()`로 하이드레이션해서 이어붙임

이게 핵심인거 같다.

**리액트의 서버렌더링 API**

| API                        | 사용 환경    | 스트리밍 방식              | 특징                     |
| -------------------------- | ------------ | -------------------------- | ------------------------ |
| `renderToString()`         | 어디서나     | 없음 (한 번에 문자열 생성) | 구현 쉬움, 느림          |
| `renderToPipeableStream()` | Node.js      | Node 스트림                | 빠름, Suspense 사용 가능 |
| `renderToReadableStream()` | 웹 표준 환경 | WHATWG ReadableStream      | Edge 환경에서 SSR 가능   |

> `renderToString()`은 간단하지만 느리고, `renderToPipeableStream()`은 Node.js에서 스트리밍을 지원하지만 플랫폼 제약이 있으며, `renderToReadableStream()`은 최신 환경에서 빠른 사용자 경험을 제공할 수 있지만 도입 난이도와 지원 환경 제한이라는 단점이 있다.

### 🎊 복습하기

1. **리액트 애플리케이션에서 서버 사이드 렌더링을 사용할 때 유리한 주요 장점은 무엇인가요?**

   서버 사이드 렌더링은 초기 HTML을 서버에서 생성해 전달하므로, 자바스크립트를 실행하지 못하는 환경에서도 콘텐츠 접근이 가능해 SEO와 초기 로딩 성능을 개선하는 데 효과적이다.

2. **리액트에서 하이드레이션은 어떻게 작동하며 왜 중요한가요?**
   하이드레이션은 서버에서 미리 렌더링된 HTML에 클라이언트에서 자바스크립트를 연결하여 상호작용을 가능하게 만드는 과정

3. **재개 가능성이란 무엇인가요? 하이드레이션보다 좋다고 주장하는 근거는 무엇인가요?**

   재개 가능성은 서버가 앱 상태를 직렬화해 보내고 클라이언트가 이를 이어받아 즉시 상호작용을 가능하게 하는 방식으로, 하이드레이션처럼 다시 렌더링하지 않아 초기 반응 속도를 크게 개선할 수 있다는 점 때문에 좋다고 한다. 하지만, 구현이 복잡함.

4. **클라이언트 사이드 렌더링의 주요 장점과 약점은 무엇인가요?**

   클라이언트 사이드 렌더링은 개발이 간편하고 사용자 중심의 동적인 인터페이스 구현에 유리하지만, 초기 HTML이 없어 SEO가 취약하고, 자바스크립트 비활성 환경에서는 콘텐츠 접근이 불가능하다는 한계가 있다.

5. **리액트에서 renderToReadableStream과 renderToPipeableStream API의 주요 차이점은 무엇인가요?**

   renderToPipeableStream은 Node.js의 스트림을 활용해 빠른 SSR을 지원하며, renderToReadableStream은 WHATWG 표준을 따르는 스트림 방식으로 Edge와 브라우저 환경에서도 SSR이 가능하다는 점에서 플랫폼 대응 방식이 다르다.
