# CHAPTER 8 프레임워크

## 📌리액트 프레임워크 개념과 필요성

- **개념**: 리액트 프레임워크란, 리액트를 기반으로 구축된 소프트웨어 라이브러리 또는 툴킷을 의미
- **배경**: 애플리케이션이 복잡해지면서 비슷한 패턴을 반복하거나 일반적인 문제에 대해 간소화된 솔루션이 필요한 경우가 생김
- 일반적인 문제에 대한 **해결책**을 제공해 애플리케이션 고유 기능에 집중할 수 있음
    - **서버 사이드 렌더링**: CSR의 한계(6장 참고) 극복 ⇒
    - **라우팅**: 직관적인 구조 + 동형(isomorphic) 라우터 + 레이아웃
    - **데이터 페치**: 데이터 페치 시점/횟수 최적화 + 캐싱 최적화

## 📌장단점

### 장점

| 구조와 일관성 | 특정 구조와 패턴 강제 ⇒ 일관성 & 개발자가 제품과 기능에만 집중 |
| --- | --- |
| 추상화 | 라우팅, 데이터 페치, 서버 렌더링 등 작업 추상화 ⇒ 가독성, 유지보수성 |
| 모범 사례 | 권장 모범 사례(가이드라인)를 기본으로 제공 ⇒ 코드 품질 향상, 안정성 |
| 성능 최적화 | 코드 분할, 서버 렌더링, 정적 사이트 생성 등 최적화 기능 제공 |
| 생태계 | 문제 발생 시 해결책 찾기 수월 |

### 단점(트레이드오프)

| 유연성과 규칙 | 특정 구조와 패턴 강제 ⇒ 불편하거나 과하게 느낄 수 있음 |
| --- | --- |
| 추상화 오버헤드 | 내부에서 일어나는 일을 이해하기 어려움 ⇒ 디버깅과 튜닝 어려움 |
| 학습 곡선 | 고유 개념, API, 규칙 등 학습 필요 |
| 의존과 서약 | 앞으로 어떻게 업데이트될지 모르기 때문에 프레임워크 사용은 일종의 서약과도 같음 |

## 📌Remix 살펴보기

### **서버 렌더링**

- `entry.server.tsx`를 통해 서버 렌더링 제공
- 봇/브라우저 요청에 따라 페이지 렌더링 자동 분기 처리
    - 봇 요청: HTML 콘텐츠 포함
    - 브라우저 요청: HTML + 하이드레이션에 필요한 JS 코드 포함

### **라우팅**

- `routes` 폴더 내 파일을 경로로 사용

### **데이터 페치**

- `loader` 함수를 내보내면 함수의 반환 값을 컴포넌트에서 `useLoaderData` 훅으로 사용 가능

### **데이터 조작**

- 데이터 생성/변경/삭제 등 서버에서 수행
- 네이티브 웹 플랫폼의 기본 기능을 최대한 활용해 브라우저가 처리하게끔 함
    - 예를 들어 폼 내에서 `input`을 사용할 때, `useState`, `onChange`같은 게 없어도 됨. 브라우저가 폼의 상태와 행동을 관리하기 때문.
    - ⇒ JS를 사용할 수 없는 환경에서도 정상적으로 동작함

## 📌Next.js 살펴보기

### 서버 렌더링

- 서버 컴포넌트: 사용자 상호작용 등이 없는 컴포넌트 (기본)
- 클라이언트 컴포넌트: `"use client"` 지시어를 추가한 컴포넌트 (⇒ 클라이언트 번들에 추가됨)
- 정적 우선 접근: 빌드 시 서버 컴포넌트는 가능한 많은 정적 콘텐츠로 렌더링되어 배포됨

<aside>
💡

Next.js는 모든 컴포넌트를 서버 측에서 먼저 렌더링한다. 다만 클라이언트 컴포넌트는 하이드레이션을 위해 클라이언트(브라우저) 측에서 다시 렌더링된다.

</aside>

### 라우팅

- 앱 라우터: `app` 폴더 내 폴더를 경로로 사용 + 해당 폴더 내에서 관심사에 따라 `layout`, `page`, `loading`, `error` 등 파일로 역할 세분화 가능
- 페이지 라우터: `pages` 폴더 내 파일을 경로로 사용
    - `blog.jsx` ⇒ `/blog` 경로
    - `/blog/index.jsx` ⇒ `/blog` 경로

### 데이터 페치

- 모든 컴포넌트는 서버 측에서 렌더링됨 ⇒ `async/await` 등 비동기 동작 가능
    
    ```jsx
    export default async function Page() {
    	const data = await fetch('/url').then((res) => res.json());
    	
    	return <>{JSON.stringify(data)}</>
    }
    ```
    
- 컴포넌트 내부에서 직접 데이터를 가져오고 렌더링할 수 있음 (Remix처럼 loader 함수 내보내기 안해도 됨)

### 데이터 조작

- 서버 액션
    - 클라이언트 번들에 포함되지 않고 서버에서 실행되는 함수
    - 폼 제출, 버튼 클릭, 페이지 이동 시 호출됨
    - 내보내기 해서 재사용 가능

## 📌프레임워크 선택하기

프레임워크를 선택하려면 프로젝트의 요구사항을 먼저 살펴보아야 한다. 가령 프로젝트의 규모, 포함시키고 싶은 주요 특징이나 기능, SSR/SSG의 필요성, 유연성, 성능, 주 타겟(사용자) 등을 고려해야 한다.

### Next.js와 Remix 비교

|  | Next.js | Remix |
| --- | --- | --- |
| 학습 곡선 | 리액트의 카나리아 릴리즈를 활용해 최신 기술을 항상 반영하므로 비교적 어려움 | 웹 기본 기능 활용으로 비교적 쉬움 |
| 복잡성 노출 | 여러 복잡성을 숨겨 앱 구축에 집중하게 함 | 서버 구성을 노출해 자유롭게 설정할 수 있게 함 |
| 설계 철학 | 정적 콘텐츠와 서버 렌더링 콘텐츠 간 유연한 전환 | 웹 기본 기능 활용으로 직관적이고 친숙하지만, ‘마법’같은 기능을 제공하진 않음 |
| 성능 | SSG, SSR, 캐싱 등 성능 최적화에 중점 | 데이터 페치가 라우트와 연결되어 특정 라우트 에 필요한 데이터만 가져옴 + 낙관적 업데이트 + 점진적 향상 전략 |

## 📌복습하기

- **1. Next.js나 Remix 같은 리액트 프레임워크를 사용하는 주된 이유와 이때 얻는 장점은 무엇인가요?**
    
    리액트 프레임워크를 사용해 리액트를 사용했을 때 겪을 수 있는 일반적이고 반복되는 패턴이나 문제들을 쉽게 해결할 수 있습니다. Next.js나 Remix 등 리액트 프레임워크를 통해 서버 사이드 렌더링, 라우팅, 데이터 페치 등의 기능을 제공받고, 제품과 기능에만 집중할 수 있습니다.
    
- **2. 리액트 프레임워크를 사용할 때 생기는 장단점이나 불리한 점에는 어떤 것이 있나요?**
    
    장점으로는 편의성이 있습니다. 리액트 프레임워크가 반복적인 문제에 대한 해결책을 추상화하여 제공하므로 개발자는 애플리케이션 개발에만 집중할 수 있습니다. 또 커뮤니티가 잘 마련되어 있는 경우 문제가 생겼을 때 도움을 받기 쉽습니다.
    
    단점으로는 학습 곡선과 제약이 있습니다. 프레임워크를 사용하려면 해당 프레임워크의 규칙, 제공하는 문법, 설계 철학 등을 학습해야 합니다. 프레임워크의 규칙에 따라 개발하는 게 제약이라고 느껴질 수도 있습니다.
    
- **3. 프레임워크로 해결되는 일반적인 문제에는 어떤 것이 있나요?**
    
    리액트는 기본적으로 CSR이기 때문에 SEO에 불리합니다.
    
    데이터 페치 시점이 너무 늦습니다. 컴포넌트가 마운트된 이후에 데이터 페치가 가능합니다.
    
- **4. 프레임워크는 이런 문제를 어떻게 해결하나요?**
    
    Next.js, Remix 같은 리액트 프레임워크는 SSR과 효율적인 데이터 페치 방식을 제공해 리액트의 CSR로 인한 문제를 해결합니다. 이외에도 라우팅 방식이나 코드베이스, 파일 구조 등을 규칙으로 정해 의사 결정 시간을 단축할 수 있으며, 캐싱이나 코드 분할 등의 성능 최적화를 지원하기도 합니다.
