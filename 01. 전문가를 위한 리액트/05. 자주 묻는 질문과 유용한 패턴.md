### 📌 5. 자주 묻는 질문과 유용한 패턴

- 메모화, 지연로딩, 성능 강화를 위해 리액트는 뭘 하는가?

### **메모화**

- 동일한 입력 값이 들어오면, 이전 결과를 저장(캐싱)하여 불필요한 연산을 방지하는 기법
- 주로 **비용이 많이 드는 연산**이나 **리스트 렌더링 최적화**에 사용됨

### **React.memo**

- 동일한 프롭을 가지고 있으면 해당 컴포넌트의 리렌더링을 방지
- 모든 컴포넌트를 메모화 하면 어플리케이션의 성능은 좋아지는가? ⇒ NO
  - `React.memo`는 프롭 비교를 수행하기 때문에, **불필요한 비교 연산이 추가되면 오히려 성능 저하를 초래할 수도 있음** → **`React.memo` 비교 자체가 오버헤드가 될 수 있기 때문**
  - **원시 타입(숫자, 문자열, 불린값) 프롭**이면 문제 없음
  - **참조 타입(객체, 배열, 함수) 프롭**이면 **렌더링마다 새로운 값으로 간주됨** → **`useMemo` 또는 `useCallback`을 사용하여 메모화**
  - `React.memo`는 어디까지나 불필요한 리렌더링 방지"를 위한 도구일 뿐, **렌더링을 완전히 차단하는 것은 아님**
- React.memo는 **부모 컴포넌트의 불필요한 리렌더링을 막을 수는 있지만, 전역 상태나 Context가 변경되면 결국 다시 렌더링됨 ⇒ 전역 상태를 많이 사용하는 컴포넌트에는 효과가 크지 않을 수 있음**

### useMemo

- 값을 메모화 하는 훅
- 배열이나, 객체같은 참조타입의 값을 캐싱하는 용도
- 리렌더링 시 **의존성 배열의 값만 비교**하여 불필요한 연산을 방지
- 정렬,필터링에 좋음
- 원시값은 굳이 감쌀필요없음

<aside>

💡 근데 이제 프롭이 **함수**라면?

- 함수도 **참조 타입**이라 렌더링마다 새로운 함수로 간주됨
- `useMemo`는 값을 메모화하기 때문에 함수 자체를 메모화 할 수 없음‼️
  ⇒ "함수 실행 결과"를 메모화할 뿐, 함수 자체를 저장하지 않음
  `useMemo(() => someFunction, [])`
  → 이건 `someFunction`을 실행한 **결과**를 메모화하는 것이지, `someFunction` 자체를 저장하는 게 아님.

</aside>

⇒ 그럼 어떡하냐 🤷🏻‍♀️

`useCallback`을 사용해서 함수 자체를 메모화해야 함

### **useCallback**

- 함수는 실행하지 않고 **그 자체를 저장해야 할 때**가 있음 → 이때는 `useCallback`을 사용해야 함.
- **함수 자체를 메모화**하는 훅
- 동일한 의존성을 가지면, 이전에 생성된 함수를 재사용하여 **불필요한 함수 재생성을 방지**

<aside>

💡 호스트 컴포넌트(예: `<div>`, `<button>`, `<input>` 등)의 `onClick` 같은 이벤트 핸들러도 함수니까 `useCallback`으로 메모화 해야할까? NO!!
이유:

- 직접전달하지 않음
  → React는 `onClick`을 **그냥 DOM 이벤트로 등록** (프롭 변경 여부를 비교하지 않음
  →**즉, 함수 참조가 변경되어도 가상 DOM 비교에서 문제가 되지 않음**
- 리액트는 가상DOM을 비교할때, **호스트 컴포넌트의 이벤트 핸들러(onClick 등)를 비교하지 않음.**

즉, 렌더링마다 새로운 함수가 생성되더라도, 가상 DOM 비교 과정에서 불필요한 연산이 추가되지 않음.

- 이벤트풀링
  리액트는 이벤트풀링이란 기법을 사용
  즉, 이벤트 객체는 **한 번만 생성되고 재사용됨** → 따라서 `onClick`이 매번 새로운 함수가 되어도 큰 성능 이슈가 없음.

</aside>

### React.memo 내부 동작 과정 (`updateMemoComponent` 함수 분석)

React는 `React.memo`로 감싼 컴포넌트를 최적화하기 위해, **렌더링 여부를 결정하는 과정**을 거친다.

이 과정은 `updateMemoComponent` 함수에서 이루어지며, 다음 7단계로 진행된다.

---

**1. 초기 점검 (Early Bailout)**

- `updateMemoComponent`가 실행되면, 가장 먼저 **이전 렌더링 결과(기존 Fiber 노드)가 존재하는지 확인**
- 첫 번째 렌더링이라면 **새로운 Fiber 노드를 생성**해야 하므로 바로 다음 단계로 이동

⇒ 첫 번째 렌더링이면 새로운 Fiber 생성, 기존 Fiber가 있다면 최적화 판단 시작

---

**2. 타입 및 빠른 경로 최적화 (Type & Fast Path Optimization)**

- 전달된 요소가 **실제 `React.memo`로 감싸진 컴포넌트인지 확인**
- `React.memo`의 **두 번째 인자(비교 함수, `areEqual`)가 존재하는지 확인**
- 비교 함수가 없으면 기본적으로 **얕은 비교(`Object.is`)를 수행**하여 프롭이 동일한지 판단

=> `React.memo`가 적용된 컴포넌트인지 확인하고, 비교 함수가 있으면 이를 사용

---

**3. 개발 모드 확인 (Dev Mode Checks)**

- React가 **개발 모드(`__DEV__`)에서 실행 중인지 확인**
- 개발 모드에서는 **Strict Mode 관련 체크 및 추가적인 디버깅 로직이 실행됨**

⇒ 개발 모드일 경우, 디버깅을 위해 추가적인 검사 수행

---

**4. 새로운 Fiber 노드 생성 (Create New Fiber)**

- 이전 Fiber가 없거나, 메모이제이션이 실패했으면 **새로운 Fiber 노드를 생성**
- 새로운 Fiber 노드를 생성한 후, 기존 트리에 추가

⇒ 기존 렌더링 결과가 없거나, `React.memo`가 리렌더링을 방지하지 못하면 새 Fiber 생성

---

**5. 기존 Fiber 업데이트 (Update Existing Fiber)**

- 이전 렌더링된 Fiber와 현재 렌더링된 Fiber를 비교
- 만약 **프롭 비교 결과가 동일하면, 기존 Fiber를 재사용하여 리렌더링을 방지**
- 다르면 **새로운 Fiber를 생성하고 업데이트 진행**

⇒ 기존 Fiber와 비교하여 변화가 없으면 기존 Fiber 재사용 (렌더링 방지)

---

**6. 업데이트 종료 (Exit if No Work Needed)**

- **변경이 없으면 업데이트 중단** (최적화 완료)
- 변경이 있다면 **새로운 Fiber를 렌더 트리에 반영**

⇒ 변경 사항이 없으면 그대로 유지하고, 있으면 새로운 Fiber 반영

---

**7. 작업용 Fiber 업데이트 (Prepare Work-in-Progress Fiber)**

- 실제로 업데이트가 필요한 경우, **현재 Fiber를 "작업 중 Fiber(Work-in-Progress Fiber)"로 설정**
- 이후 React의 **렌더링 및 커밋 단계에서 업데이트가 수행됨**

⇒ 변경 사항이 있으면 새로운 Fiber를 반영하고, 이후 커밋 단계에서 UI 업데이트 수행

---

**Immer**

복잡한 상태 관리를 할 때 유용한 라이브러리.

`produce` 함수를 사용해 **불변성을 유지하면서도 직관적인 방식으로 상태를 변경할 수 있는 것이 특징**이다.

원래는 `spread` 연산자(`...`)를 사용해 객체를 복사한 후 변경된 값을 적용해야 하지만,

Immer를 사용하면 **객체를 직접 수정하는 것처럼 작성해도 새로운 객체가 생성되기 때문에 불변성이 유지된다.**

ex. 기존 방식

```tsx
setState((prev) => ({
  ...prev,
  user: {
    ...prev.user,
    profile: {
      ...prev.user.profile,
      name: "Kim",
    },
  },
}));
```

처럼 불필요한 `spread` 연산자가 많아지지만, **Immer를 사용하면 이렇게 간단해진다.**

```tsx
setState(
  produce((draft) => {
    draft.user.profile.name = "Kim";
  })
);
```

💬 공식 문서에서도 Immer를 추천할 정도로 좋은 라이브러리처럼 보이는데, 왜 나는 안 써봤을까?

아마도 그렇게까지 복잡한 상태 관리를 해본 적이 없어서인거 같고, zustand같은데서는 불변성을 알아서 지켜줘서 그런듯하다.

**고차 컴포넌트와 훅의 비교**

| 기능           | 고차 컴포넌트                                                                         | 훅                                                                                                             |
| -------------- | ------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 코드 재사용    | 여러 컴포넌트에서 은닉된 로직을 공유하는 데 탁월하다.                                 | 컴포넌트 내 또는 유사한 컴포넌트 간에 로직을 공유하는 데 유용하다.                                             |
| 렌더링 로직    | 감싸진 컴포넌트의 렌더링을 제어한다.                                                  | 렌더링에 직접 영향을 주지는 않지만, 합성된 컴포넌트 내에서 렌더링과 관련된 부수적 작업을 관리하는 데 사용된다. |
| 프롭 조작      | 프롭을 삽입하고 조작해 추가 데이터나 기능을 제공할 수 있다.                           | 프롭을 직접 주입하거나 조작할 수 없다.                                                                         |
| 상태 관리      | 감싸진 컴포넌트 외부에서 상태를 관리하고 참조한다.                                    | 함수 컴포넌트 내에서 로컬 상태를 관리하도록 설계되었다.                                                        |
| 수명 주기 방법 | 감싸진 컴포넌트와 관련된 수명 주기 로직을 추출한다.                                   | `useEffect`를 비롯한 훅은 함수 컴포넌트 내에서 수명 주기 이벤트를 처리한다.                                    |
| 합성 용이성    | 합성할 수 있지만 깊은 중첩이 일어나면 래퍼 지옥(wrapper hell)이 될 수 있다.           | 쉽게 합성할 수 있으며 여러 훅과 컴포넌트를 추가해도 코드가 깔끔하게 유지된다.                                  |
| 테스트 용이성  | 추가 컴포넌트로 인해 테스트가 더 복잡해질 수 있다.                                    | 일반적으로 고차 컴포넌트보다 더 직관적이고 테스트하기 더 쉽다.                                                 |
| 타입 안정성    | 타입스크립트를 사용할 때, 감싸진 컴포넌트의 경우 올바른 타입으로 입력하기가 까다롭다. | 타입스크립트 타입 추론이 향상되고 일관성 있게 적용된다.                                                        |

**⇒ 서버 컴포넌트 시대**에서는 HOC보단 **Hooks + Composition + Layout**이 더 자연스러움

⇒ 대표적인 HOC의 예시로 **`React.memo`**, **`forwardRef`** 을 들었는데 이마저도 조만간 사라질 것

(리액트컴파일러, [리액트 19 forwardRef 지원 중단](https://siosio3103.medium.com/%EB%B2%88%EC%97%AD-%EB%A6%AC%EC%95%A1%ED%8A%B8-19-forwardref-%EC%A7%80%EC%9B%90-%EC%A4%91%EB%8B%A8-%EC%95%9E%EC%9C%BC%EB%A1%9C-ref%EB%A5%BC-%EC%A0%84%EB%8B%AC%ED%95%98%EA%B8%B0-%EC%9C%84%ED%95%9C-%ED%91%9C%EC%A4%80-%EA%B0%80%EC%9D%B4%EB%93%9C-13c02855efd8))

**5.5.3 렌더 프롭** 💬  여기서부터 읽기 너무 힘들었음..

<aside>

렌더 프롭은 부모 컴포넌트가 자식 컴포넌트에게 함수 형태의 prop을 전달하고, 자식 컴포넌트는 그 함수를 호출해 자신이 어떻게 렌더링될지 결정하는 방식.

즉, 부모가 기본 틀을 제공하고, 자식이 구체적인 렌더링 내용을 결정하는 거

</aside>

이 패턴을 사용하면 재사용성과 유연성이 높아짐, 예전에는 커스텀 훅이 없어서 **로직 재사용을 위해** 이 패턴이 쓰였음

그치만 요즘은 리액트 커스텀 훅으로 대체

💬 아 뭔소린가 했더니 말그대로 `render`라는 프롭을 쓴다는거였음…

**자식프롭(children 쓴다는 말)**

이전에 왜 `render`라는 prop을 썼을까? 🤔

1. **렌더링 책임을 넘겨주는 함수**니까 이름이 `render`
2. `children`으로 해도 되지만, `children`은 JSX로만 쓰인다는 오해가 생길 수 있음
3. **함수형 children**이 익숙하지 않았던 시절엔 `render`라는 명확한 이름이 더 낫다고 여겨졌음

요약

- 렌더 프롭 패턴에서 `render`라는 prop 이름은 흔히 쓰였던 **관습적인 네이밍**
- 역할: **“자식이 렌더링을 결정할 수 있게” 함수 전달**
- 지금은 **함수형 children을 더 선호함**

**5.5.4 제어프롭**

<aside>

상태 관리에 대한 **전략적 접근 방식**으로, 제어 컴포넌트의 개념을 확장한 것

</aside>

**🫸🏻 제어컴포넌트**란?

```jsx
<input value={text} onChange={(e) => setText(e.target.value)} />
```

내부 상태 없이, **외부에서 값과 이벤트를 제어하는 컴포넌트**

그럼 제어 프롭은?

컴포넌트의 내부 상태를 외부에서 제어할 수 있도록 prop으로 노출하는 패턴

⇒ 컴포넌트가 **내부 상태를 가질 수도 있고**, **원한다면 외부에서 제어할 수도 있는** 구조로 확장한 것

⇒ 그러니 **전략적 접근 방식**이라 하는 것

---

**5.5.5 프롭컬렉션**

<aside>

컴포넌트 사용자에게 **한 번에 여러 개의 관련된 props를 객체 형태로 제공**해서, 개발자가 필요한 곳에 그 props를 **적절히 분산해서 사용하도록** 하는 방식

</aside>

- 여러 개의 이벤트 핸들러나 속성을 **하나의 객체로 묶어서 제공**
- 사용자는 그 객체를 **`{...}` 스프레드 연산자로 풀어서** 원하는 엘리먼트에 적용
- 코드 간결, 일관성 ↑, 커스터마이징 가능

**프롭게터**

<aside>

사용자 정의 프롭을 프롭 컬렉션에 조합하고 병합.

**함수 형태**로 props를 받아,**merge된 props를 반환** ← 더 유연함!

</aside>

**프롭 컬렉션 vs 프롭 게터**

|                   | 프롭 컬렉션           | 프롭 게터                                |
| ----------------- | --------------------- | ---------------------------------------- |
| 형태              | `const props = {...}` | `getProps(props?) => {...}`              |
| 유연성            | props 덮어쓰기만 가능 | 병합 및 이벤트 핸들러 조합 가능          |
| 외부 커스터마이징 | 덮어쓰기만 가능       | 합성 가능 (내부 + 외부 이벤트 동시 처리) |
| 추천도            | 기본적 상황엔 충분    | 실전/라이브러리 수준에서는 더 선호됨     |

**5.5.6 복합 컴포넌트 (합성컴포넌트(compound component))**

<aside>

**여러 개의 관련된 컴포넌트를 함께 구성해서, 자연스럽게 조립할 수 있는 구조**

→ 내부에서 **공통된 상태를 공유하고**, **각 컴포넌트가 독립적으로 동작** 가능

</aside>

책에선 아코디언을 예시로 들었음

- **Context 기반 설계**에 잘 어울림

💬 여기서 부턴 재밌게 읽었고, 예전에 모달 만들때 다뤄봤던 패턴!!

**5.5.7 상태리듀서**

<aside>

컴포넌트 내부 상태 변경 로직을 외부로 넘겨서 제어할 수 있게 하는 패턴

</aside>

즉, **컴포넌트가 상태는 가지고 있지만 “상태를 어떻게 바꿀지”는 외부에서 결정**할 수 있도록 해줌
