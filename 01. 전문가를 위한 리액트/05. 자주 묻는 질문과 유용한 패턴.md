## 5.1 React.memo를 사용한 메모화
- 메모화란 전산학에서 이전에 계산된 결과를 캐싱해서 함수의 성능을 최적화하는 기법
  - 계산 비용이 많이 들거나 자주 호출되는 함수를 실행하는데 필요한 자원을 줄일 수 있음
  - 순수 함수여야 함
  - (#) 메모화는 보통 알고리즘 문제 풀 때 많이 듣던 개념!!!
- 리액트에서는 `React.memo`를 사용해 함수 컴포넌트에 메모화를 적용할 수 있음
  - `React.memo`로 감싸진 함수는 props가 변경되지 않는 한 재조정 과정에서 다시 호출되지 않음
    - 이는 곧 불필요한 렌더링을 방지해서 성능이 전반적으로 향상된다는 뜻
- 그래서 얼마나 자주, 많이 메모화해야 할까?
  - `React.memo`는 props에 "얕은 비교"를 수행해 변경 여부를 확인!
  - 그러나 스칼라(원시) 타입이 아닌 참조 타입은 정확하게 비교하기 힘듦ㅠㅠ
  - 참조 타입은 데이터 자체가 아니라 데이터가 메모리에 저장된 위치에 대한 참조를 저장함
    - 보통 객체나 배열 타입을 생각하지만 자바스크립트에서는 함수도 참조 타입!
  - 내용이 같아도 메모리 위치가 다른 두 개체는 `===`(엄격한 동등성 연산자)를 사용해 비교할 때 서로 같지 않은 것으로 간주됨
    - 예를 들어 배열을 props로 받는 컴포넌트의 경우 `React.memo`로 감쌌다고 하더라도 props로 전달되는 배열이 매번 새로 만들어지기 때문에 불필요한 렌더링이 발생함
      - 이런 경우 `useMemo` 훅으로 배열을 메모화해야 문제가 해결됨
    - 함수를 props에 넘겨주는 경우에도 비슷한 상황이 발생함
      - 함수의 경우 `useCallback` 훅으로 문제를 해결할 수 있음
  - `React.memo`는 컴포넌트를 절대 리렌더링하지 않게 만드는 장치가 아니라, 재조정자에게 전달하는 힌트!
    - 이를 통해 사용자가 원하는 UI를 렌더링하는 최선의 방법을 찾아내는 것은 여전히 리액트의 몫
    - 리액트는 메모화된 컴포넌트를 만났을 때 갱신이 필요한지 건너뛸 수 있는지 판단하는 함수가 구현되어있음
      - 상태나 컨텍스트 변경에 의해 예정된 갱신이 없고, 기존 props와 새 props를 비교한 결과 둘이 서로 같다면 재렌더링되지 않음
      - props 비교에는 사용자가 직접 비교 함수를 제공할 수도 있음

## 5.2 useMemo(# useCallback)를 사용한 메모화
- 전체 컴포넌트를 메모화하여 "재렌더링을 줄이는" `React.memo`와 달리 `useMemo`는 컴포넌트 내부의 특정 계산을 메모화하여 비싼 계산을 다시 하지 않고 결과에 대한 일관된 참조를 유지함
- **그러나 useMemo를 모든 곳에 적용한다고 해서 성능에 득이 되지는 않음**
  - 스칼라 값은 자바스크립트에서 참조가 아닌 실젯값으로 전달되고 비교되기 떄문에 `useMemo`를 사용하는 것이 더 비싼 작업이 될 수 있음
  - 또한 내장 컴포넌트 또는 호스트 컴포넌트에 전달되는 몇몇 props는 사용자 정의 컴포넌트와는 다르게 취급됨
    - 이벤트 기반 props의 경우 리액트는 내부적으로 이벤트 핸들러를 DOM에 직접 추가하지 않고 **이벤트 위임**을 사용해 최적화함!
    - 내장 컴포넌트는 리렌더링된 상위 컴포넌트의 일부가 아닌 경우 함수 props가 변경되었다고 해서 리렌더링되지 않음
    - 리액트는 내장 컴포넌트에서 변경 사항 감지를 위해 함수에 대해 깊은 비교를 수행하지 않기 때문에 성능이 절약됨
  - 내장 컴포넌트를 사용할 때는 신경을 좀 덜 써도 된다는 뜻!
- `useCallback`은 자주 리렌더링할 가능성이 있는 컴포넌트가 있고, `React.memo` 등으로 최적화된 하위 컴포넌트에 콜백을 전달할 때 매우 유용함
  - (#) `useEffect`를 사용할 때도 많이 쓰이더라구요
  - `useCallback`은 본질적으로 함수를 위한 `useMemo`!
    - (#) 별도의 단락으로 다루거나 제목에 따로 useCallback이라고 적지 않은 건 이 때문이었나보네요
- (#) 진리의 케바케... 측정하지 않으면 개선할 수 없다
- 이 모든 것을 최적화해줄 [리액트 컴파일러](https://ko.react.dev/learn/react-compiler)...는 언제 사용할 수 있을지

## 5.3 지연 로딩
- 애플리케이션 규모에 따라 실행해야 하는 코드의 양도 늘어나는데, 전체가 아닌 일부만을 사용하는 경우에도 모든 것을 다 다운로드해야하는 경우가 있음
- JS 파일은 일반적으로 HTML/CSS 코드보다 크기가 크고 처리 시간이 많이 필요하며 인터넷 속도가 느리거나 구형 기기를 사용하는 경우 로딩 시간이 많이 느려질 수 있음
- 초기 로딩 시간을 줄이기 위해 `async` 속성을 사용하여 JS 파일을 비동기적으로 받아오면 페이지 로딩 시간을 개선하는 데 도움이 될 수 있음
- 그 외에도 데이터 사용량이 늘어나는 문제가 존재하여 전송량이 제한적인 요금제를 사용하거나 인터넷 속도가 느린 경우 문제가 생김
  - 이런 경우 코드 분할이나 지연 로딩 등의 방법을 사용해 실제로 필요한 JS 파일만 받아온다면 로딩 시간과 데이터 사용량을 줄일 수 있음
  - `import(module)` 표현식(함수라고 써있지만 [ES2020부터 등장한 표현식](https://tc39.es/ecma262/2020/#sec-import-calls)임)를 이용하여 비동기적으로 가져오기가 가능함
- 리액트에서는 `React.lazy`와 `Suspense`를 통해 `import(module)` 표현식을 직접 쓰는 것보다 더 직관적으로 지연 로딩을 적용할 수 있음
  - `import(module)`로 필요한 JS 코드만 가져온 것처럼 실제 필요한 컴포넌트만 가져올 수 있음
    - 컴포넌트가 위치한 경로를 `import()` 표현식에 제공하면 해당 컴포넌트를 반환하는 Promise 객체를 얻을 수 있고, 이를 `React.lazy` 함수에 제공하여 컴포넌트에 지연 로딩을 걸 수 있음
  - (#) Next.js에서는 `dynamic` 함수를 제공하여 많이 써본 적이 있는데 뭐가 다른 것일까?
    - `dynamic` 함수는 `React.lazy`와 `Suspense`가 합쳐진 형태
    - `React.lazy`와 같이 컴포넌트를 지연 로딩하는 데 사용할 수 있으나, [여러 가지 옵션](https://github.com/vercel/next.js/blob/bb1df7d13937c8bca6a61cc88db3827a04109bca/packages/next/src/shared/lib/app-dynamic.tsx#L19)을 줄 수 있음
      - 주로 사용했던 옵션은 `loading`과 `ssr`
      - `loading` props로 `Suspense`처럼 지연 로딩 중 표시할 fallback UI를 정의할 수 있음
      - `ssr` props로 해당 컴포넌트가 서버 사이드 렌더링 과정을 거치지 않도록 할 수 있음
  - (#) 내가 지연 로딩을 사용할 때 컴포넌트를 불러오는 방식은 `import()` 표현식이 아니라 애시당초 내보낼 때 아래와 같이 적용하는 방식이었는데 차이가 있을지?
    ```tsx
    import dynamic from 'next/dynamic';
    import { Spinner } from '@/shared/components/ui/spinner';
    
    const ComponentA = () => {
      // ...
    };

    export default dynamic(() => Promise.resolve(ComponentA), {
      ssr: false,
      loading: () => <Spinner />,
    });
    ```
  - (#) 책이 언제 쓰인지는 모르겠지만, `Suspense`의 역할을 최적화를 위한 지연 로딩으로만 설명하는 것은 `Suspense`의 반절만을 설명하는 것이 아닐까? 2024~2025 현재 기준 자주 사용되는 형태인 선언적 데이터 가져오기(declarative data fetching)를 함께 설명해줬다면 좋았을 것 같음
    - `Suspense`의 등장은 지연 로딩 덕분이었을지 몰라도 요즘 리액트를 배우는 경우 이런 용법을 더 많이 접할 것으로 예상함
    - '화면을 그리기 위한 데이터가 로딩될 때까지 지연한다'고 말하면 할 말이 없긴 하지만...
## 5.4 useState와 useReducer
- (#) `useState`는 일반적으로 단일 스칼라 타입 상태를 다루는 경우 많이 사용하지만, 상태가 복잡해지면 `useState`의 호출 자체를 많이 늘리는 것보다 모든 상태를 담은 객체를 하나의 `useState`로 관리하는 형태를 사용하게 되는 듯함
- `useState`는 내부적으로 `useReducer`를 사용(!!!)
  - 따라서 `useState`는 `useReducer`의 상위 추상화라고 볼 수 있다!
  - (#) 여기서 '상위'라는 표현이 헷갈릴 수도 있을 것 같음

  - 상태와 상태를 변경하는 방식이 항상 명시적으로 useReducer와 함께 사용됨

  ```tsx
  // with Immer
  const updateName = (newName: string) => {
    setUser(produce((draft) => {
      draft.user.name = newName;
    }));
  }

  // without Immer
  const updateName = (newName: string) => {
    const next = { ...user, name: newName };
    setUser(next);
  }
  ```
## 5.5 강력한 패턴
- 디자인 패턴을 선택할 때는 사용자에게 얼마나 많은 권한을 부여할지, 프로그램이 얼마나 많이 처리할지 고려해야 함
- 흔히 볼 수 있는 리액트 디자인 패턴으로 **"프레젠테이션/컨테이너 컴포넌트"**가 있음
  - UI 상태를 처리하는 컨테이너 컴포넌트와 UI를 렌더링하는 프레젠테이션 컴포넌트의 조합
  - 컴포넌트의 외형과 작동 방식에 대한 책임을 다른 컴포넌트로 분리
  - 요즘에는 대부분 hooks로 대체하게 되었음
- 고차 함수가 다른 함수를 인수로 받아 새로운 함수를 반환하는 것처럼 다른 컴포넌트를 받아 새로운 컴포넌트를 반환하는 **"고차 컴포넌트"**가 있음
  - 여러 컴포넌트에서 공유하는 동작을 반복 작성하고 싶지 않은 경우 유용함
  - 또한 고차 컴포넌트를 합성하는 과정에서 "래퍼 지옥(wrapper hell)"이 발생할 수 있는데 여러 고차 컴포넌트를 하나로 합성하는 유틸리티 함수를 작성할 수 있음
  - 프레젠테이션/컨테이너 컴포넌트 패턴과 마찬가지로 hooks로 대체되는 경우가 많음
    - 여러 컴포넌트에서 로직을 공유하는 데 유용하며 내부 컨포넌트의 렌더링을 제어하고 props를 조작해 추가적인 데이터나 기능을 제공하기 좋음
  - 현재도 자주 사용되는 고차 컴포넌트로는 `React.memo`, `React.forwardRef` 등이 있음
    - (#) React 19에서는 `forwardRef`와 작별을 고할 수 있지요...!
    - (#) 형태가 비슷한 `React.lazy`는 HOC가 아닌데, 그 이유는 전달받은 컴포넌트를 감싸거나 기능을 수정하는 게 아닐 뿐더러, "컴포넌트"를 입력으로 받는 것이 아니기 때문이라고 합니다
      - "컴포넌트를 반환하는 Promise"를 받는 것이지 컴포넌트 그 자체가 아니라는 뜻
- UI를 표현하는 방법을 명시하지 않고 부포 컴포넌트로 받은 **"렌더 프롭"**을 호출해 렌더링 작업에 대한 제어를 부모에게로 역전시킬 수 있음
  - (#) 책에서는 더 이상 사용되지 않는다고 말하는데, 저는 아직도 `children` prop을 자주 사용하는 편이고 자주 쓰이는 라이브러리들 중에서도 이 패턴을 많이 사용하고 있는 걸로 알아요
    - [React Hook Form - Controller](https://react-hook-form.com/docs/usecontroller/controller)
    - [Tanstack Form - Field](https://tanstack.com/form/latest/docs/framework/react/guides/basic-concepts#field)
- 상태를 관리하고 값을 업데이트 하는 책임을 모두 부모 컴포넌트가 가지게 되는 제어 컴포넌트!
  - 부모 컴포넌트가 상태 및 상태 변경에 반응할 수 이는 콜백을 주지 않는 경우 내부 상태를 사용하게 되는 "제어 프롬" 패턴을 사용할 수도 있음
  - 경우에 따라 알아서 상태를 관리하거나 부모에서 제어할 수 있게 해줌
- 여러 개의 props를 하나의 객체에 담은 후 spread 연산자를 이용해 전달하는 **프롭 컬렉션** 패턴, 프롭 컬렉션 그 자체를 직접 반환하는 대신 프롭 컬렉션을 반환하는 함수를 반환하는 "프롭 게터" 패턴도 존재함
  - (#) 예시: [Zag](https://zagjs.com/components/react/select#usage)
- 서로 연결되고 상태를 공유하면서도 독립적으로 렌더링되는 컴포넌트를 한데 묶어 요소 트리를 더 세밀하게 제어할 수 있도록 하는 "복합 컴포넌트" 패턴
  - (#) 대부분의 Unstyled 컴포넌트 라이브러리들이 이런 형태를 취하고 있음!
    - [Radix Primitive](https://www.radix-ui.com/primitives/docs/components/dialog)
  - 상태와 관심사 분리가 자연스럽게 이루어지도록 돕는 패턴
- reducer 자체를 prop으로 받아 컴포넌트를 상태 로직을 사용자가 정의할 수 있도록 열어주는 "상태 리듀서" 패턴도 유용함
  - (#) 단순히 `setState`를 받아서 이리저리 조작하는 것보다 좀 더 예측 가능한 형태로 상태 로직을 재정의할 수 있을 것 같아 꽤 괜찮아보이는 패턴이네용
- (#) 추가로 [이런 웹사이트](https://patterns-dev-kr.github.io/design-patterns/introduction/)를 발견했으니 한번쯤 읽어보시는 것두

## 5.7 복습하기
1. 리액트에서 메모화란 무엇이며, 컴포넌트 렌더링을 최적화하는 데 어떻게 사용할 수 있을까요?
- 리액트에서 메모화란 컴포넌트를 DOM에 배치하거나 갱신하는 과정에서 복잡한 계산이 많은 경우, 렌더링이 오래 걸리는 문제를 방지하기 위해 비용이 큰 계산의 결과를 캐싱(저장)해두는 것
- 이렇게 캐싱된 값을 이용하여 실제로 변경된 컴포넌트만 다시 렌더링하고 변경되지 않은 컴포넌트는 캐싱된 결과를 보여주어 불필요한 리렌더링을 줄일 수 있음
2. 리액트에서 상태 관리를 위해 useReducer를 사용하면 어떤 우세한 점이 있으며, useReducer는 useState와 어떻게 다른가요?
- useReducer를 사용하면 상태 갱신 로직을 컴포넌트에서 분리해 단독으로 테스트하거나 다른 컴포넌트에서 재사용이 가능해짐
- 또한 useReducer는 이벤트 소싱 패턴을 따르기 때문에 데이터 변경의 원인을 쉽게 추적할 수 있다는 장점도 존재
- useReducer는 useState의 하위 추상화로 볼 수 있으며, 상태 기반인 useState와 달리 useReducer는 이벤트 기반 아키텍처를 따르기 때문에 복잡한 상태 변경 로직이 필요한 경우 사용하기 좋음
3. React.lazy와 Suspense 컴포넌트를 사용하는 리액트 애플리케이션에서 지연 로딩을 어떻게 구현할 수 있나요?
- 초기 렌더링에 필요하지 않은 컴포넌트의 Promise를 반환하는 함수를 `React.lazy`에 전달하여 해당 컴포넌트를 렌더링하기 위한 코드를 지연 로딩할 수 있음
- 해당 컴포넌트가 렌더링 가능하기 전까지 `Suspense`로 감싸 해당 `Suspense`에 전달된 fallback UI를 렌더링하여 사용자에게 어떤 작업이 진행되고 있는지 안내할 수 있음
4. 리액트에서 메모화를 사용할 떄 발생할 수 있는 잠재적 문제는 무엇이며 어떻게 완화할 수 있을까요?
- 전달받는 props가 참조 타입인 경우 해당 prop의 각 항목 값이 변경되지 않았다고 해도 매번 다른 것으로 간주하여 불필요한 리렌더링을 야기함
- 데이터의 경우 `useMemo`, 함수의 경우 `useCallback` hooks를 사용하여 이러한 문제를 완화할 수 있음
5. 리액트에서 컴포넌트에 프롭으로 전달된 함수를 메모화하기 위해 useCallback 훅을 어떻게 사용할 수 있나요?
- `React.memo`로 최적화되어있는 하위 컴포넌트에 콜백을 전달할 때 `useCallback`으로 감싼 함수를 전달하면 해당 함수와 관계없는 변경으로 이루어진 리렌더링 시 하위 컴포넌트가 불필요하게 리렌더링되지 않음
