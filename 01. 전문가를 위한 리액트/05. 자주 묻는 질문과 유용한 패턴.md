## 📌리액트의 메모화

### 리액트의 리렌더링 조건 (p112 Recap)

리액트는 컴포넌트의 상태/프롭이 변경되면 업데이트를 반영하기 위한 새로운 리액트 엘리먼트 트리를 생성한다. 리액트는 디핑 알고리즘을 통해 새 트리 전체가 아닌, 이전 트리에서 변경된 부분만 리렌더링한다.

그러나 **“불필요한 리렌더링”이 야기**되는 경우가 있는데, 바로 부모 노드가 변경되었을 때이다. 디핑 알고리즘에는 ‘부모 노드 변경 시 하위 트리 전체를 새 트리로 대체한다’라는 규칙이 있는데, 이 때문에 하위 트리 전체가 리렌더링되는 문제가 발생한다.

이러한 문제를 해결하기 위해 리액트는 메모화를 통한 최적화 방식을 제공해 왔다. 리액트 컴파일러가 메모화를 자동화

### `memo()`

상위 컴포넌트가 리렌더링되더라도 `memo`로 감싼 컴포넌트는 프롭이 바뀌지 않으면 재호출되지 않는다(대신 기존 파이버를 재사용함. =bailout). 즉 `memo`는 컴포넌트의 **프롭이 변경되었을 때만 리렌더링**하게 한다. (단, 사용중인 Context가 변경되면 메모 컴포넌트도 리렌더링된다)

- **레퍼런스**
    - 매개변수: 메모할 컴포넌트, (optional) 프롭 비교 함수 (기본값: `Object.is`)
    - 반환 값: 메모한 컴포넌트
        - ⇒ 기존 컴포넌트와 동일하게 동작하지만, 프롭 변경이 없으면 리렌더링되지 않음

프롭 비교는 얕은 비교로 수행된다. 만약 프롭이 스칼라 타입이면 값 자체를 비교하지만, **참조 타입이면** 참조 값을 비교하기 때문에 **실제 내용이 동일하더라도 비교 결과는 동등하지 않은 것으로 간주**된다. 즉 컴포넌트를 `memo`로 감싸도, **프롭이 참조 타입(ex. 객체, 배열, 함수 등)이면 매번 리렌더링된다.**

```jsx
const Profile = memo(function Profile({ person }) {
  // ...
});

function Page() {
	const [like, setLike] = useState(false);
  const person = { name: 'Kim', age: 18 }; // 매 렌더링마다 새로운 객체가 생성됨
  
  return (
	  <>
		  <button onClick={() => setLike(!like)}>좋아요</button>
		  <Profile person={person} /> {/* memo했지만 매번 리렌더링 됨 */}
	  </>
  );
}
```

이러한 문제를 해결하기 위해 `useMemo`, `useCallback`를 사용할 수 있다.

### `useMemo()`

인자로 받은 **함수의 반환값을 메모**한다. `useMemo`를 사용하면 컴포넌트가 리렌더링되더라도 값을 새로 생성하지 않고, **종속성이 변경될 때만 함수를 다시 실행해 새로운 값을 메모**한다. `useMemo`를 통해 1️⃣비용이 비싼 연산(ex. 정렬, 필터, 매핑 등)의 횟수를 줄이거나, 2️⃣`memo`한 컴포넌트의 프롭으로 전달되는 참조를 메모해 해당 컴포넌트의 리렌더링을 건너뛸 수 있다.

- **레퍼런스**
    - 매개변수: 계산 함수, 종속성 배열
    - 반환 값: 계산 함수의 반환 값
        - ⇒ 종속성이 변경될 때에만 값을 다시 메모함
- **예제**
    
    ```jsx
    const Profile = memo(function Profile({ person }) {
      // ...
    });
    
    function Page({ people }) {
    	const [like, setLike] = useState(false);
    	
    	// ✅ useMemo()로 이득을 보는 경우
    	// 1. 계산 함수의 연산 비용이 비싼 경우
    	const friends = useMemo(() => people.filter((p) => isFriend(p), [people]);
    	
    	// 2. 메모한 값을 프롭으로 받는 컴포넌트의 렌더링 비용이 큰 경우
      const person = useMemo(() => ({ name: 'Kim', age: 18 }), []);
      
      return (
    	  <>
    		  <button onClick={() => setLike(!like)}>좋아요</button>
    			<Profile person={person} />
    			<ul>
    				{friends.map((friend) => (
    					<li key={friend.id}>{friend.name, friend.age}</li>
    				))}
    			</ul>
    	  </>
      );
    }
    ```
    

### `useCallback()`

인자로 받은 **함수 정의를 메모**한다. `useCallback`을 사용하면 컴포넌트가 리렌더링되더라도 함수를 새로 생성하지 않고, **종속성이 변경되었을 때만 새로운 함수 정의를 메모**한다. `useCallback`을 통해 1️⃣하위 컴포넌트에 전달할 함수를 메모해 함수 생성을 매번 하는 것을 방지할 수 있고, `memo` 컴포넌트에 프롭으로 전달할 함수를 메모해 리렌더링을 건너뛸 수 있다.

내장 컴포넌트 또는 호스트 컴포넌트의 함수 프롭을 `useCallback`으로 메모이제이션하면 부하만 더하고 별로 도움이 되지 않으니 하지 말자.

## 📌지연 로딩(Lazy Loading)과 서스펜스(Suspense)

- 문제: 자바스크립트 번들 다운로드로 인해 페이지 로딩이 느려지거나 데이터 사용량이 증가
    - ⇒ 코드 분할(Code Splitting): 특정 페이지나 기능에 필요한 스크립트만 읽어 들임
    - ⇒ 지연 로딩(Lazy Loading): 초기 실행에 필수적이지 않은 스크립트의 로딩을 미룸
- 리액트에서 해결 방법: 지연 로딩과 서스펜스 사용
    - **지연 로딩(Lazy Loading)**
        - 초기 로딩에 필수적이지 않은 자바스크립트 로딩을 지연해 페이지 로드 시간과 데이터 사용량을 줄이는 최적화 기법
        - 예를 들어 버튼을 눌렀을 때 사이드바가 나타나는 UI에서, 사이드바 크기가 큰 경우 지연 로딩을 적용하여 사이드바를 펼치기 전까지 스크립트를 로드하지 않도록 할 수 있음
    - **서스펜스(Suspense)**
        - 프로미스가 해결되기 전까지 폴백(fallback) UI를 제공
    - **지연 로딩 + 서스펜스**
        - 서스펜스로 지연 로드하는(=비동기로 읽어들이는) 요소를 감싸 인터페이스 응답성을 높임

## 📌리액트의 상태 관리 훅

- `useState()`
    - 단일 상태 관리에 사용
- `useReducer()`
    - 복잡한 상태(ex. 객체) 관리에 사용
    - 장점
        - 상태 업데이트 로직(`reducer` 함수)을 컴포넌트와 분리 가능 ⇒ 테스트성, 재사용성 증가
        - 이벤트 소스 모델로, 앱 내 이벤트를 재생해 진단 로그를 추적하는 데 사용 가능(ex. 버그 재연, 시간 여행 디버깅)
    - 단점
        - 코드가 장황해짐
- Immer
    - 리액트 라이브러리로 복잡한 상태(ex. 중첩 객체) 관리 처리에 유용
    - 기존 리듀서에서는 중첩된 객체 속성을 편집할 때 전개나 `Object.assign`으로 해야 했지만, `useImmerReducer`를 사용하면 값을 객체 속성에 직접 할당하여 상태 업데이트를 할 수 있음
    - `useState`와 함께 사용해 현재 상태 기반의 불변성을 보장하면서 다음 상태를 생성할 수 있음

## 📌리액트 디자인 패턴

소프트웨어에서 디자인 패턴은 소프트웨어 개발에서 반복되는 문제에 주로 사용되는 해결책으로, 제작 템플릿이나 지침으로 표현되기도 한다. 소프트웨어 디자인 패턴은 각자 나름의 역할을 가지며, 어떤 것이 다른 것보다 근본적으로 더 좋거나 나쁘지 않다. 대부분의 패턴은 이상적인 추상화 수준을 도출하기 위해서 사용된다. 패턴을 통해 **문제에 대한 재사용 가능한 해결책을 제시**하고, **가독성**과 **유지보수성**을 챙길 수 있다.

이제부터 인기있는 리액트 디자인 패턴을 등장 시기 순으로 알아보겠다.

### 1️⃣프레젠테이션/컨테이너 컴포넌트

- UI 렌더링 컴포넌트(프레젠테이션)와 UI 상태를 처리 컴포넌트(컨테이너)를 분리
- ✅단일 책임 원칙 ⇒ 모듈화, 재사용성, 테스트가능성
- ❌대부분 훅으로 대체 가능함
- ❌소규모 앱에서 쓰면 과도한 설계로 간주될 수 있음

### 2️⃣고차 컴포넌트(HOC)

- 고차 컴포넌트란, 입력받은 컴포넌트에 특정 로직을 처리하여 반환하는 컴포넌트(ex. `React.memo`)
- ✅여러 컴포넌트의 **공통 관심사를 한 곳에서 처리** 가능
- ✅고차 컴포넌트 간 **합성**을 통해 여러 컴포넌트의 기능과 동작을 혼합할 수 있음
- ❌고차 컴포넌트 합성 시 중첩이 깊어지면, 래퍼 지옥이 될 수 있고 타입스크립트 사용이 까다로움
- 훅과 차이점
    
    
    |  | 고차 컴포넌트 | 훅 |
    | --- | --- | --- |
    | 목적 | 여러 컴포넌트 간 로직 공유 | 로직 추출 및 공유 |
    | 렌더링 제어 | 가능 | 불가능 |
    | 프롭 조작 | 가능 | 불가능 |
    | 상태 관리 | 감싸진 컴포넌트 외부에서 관리 | 함수 컴포넌트 내에서 관리 |
    | 테스트가능성 | 중첩이 깊어지면 복잡함 | 고차 컴포넌트보다는 쉬움 |
    
    ```
    💡
    고차 컴포넌트와 훅 모두 로직 재사용 메커니즘을 제공하지만, 컴포넌트에 동작을 주입할 수 있는지가 가장 큰 차이점이다.
    ```

### 3️⃣render/children 프롭

- 내부 상태는 관리하지만, 렌더링은 부모 컴포넌트의 render 함수(또는 children)에 위임함
- 예시 코드
    
    아래 코드에서 `WindowSize` 컴포넌트는 창 크기가 변경될 때마다 상태를 저장하기만 함
    
    ```jsx
    // render 프롭 사용 예시
    <WindowSize
      render={({width, height}) => (
        <div>
          창 크기: {width}x{height}px
        </div>
      )}
    />
    ```
    
    ```jsx
    // children 프롭 사용 예시
    <WinddowSize>
      {({width, height}) => (
        <div>
          창 크기: {width}x{height}px
        </div>
      )}
    </WindowSize>
    ```
    
- ❌훅으로 대체되어 사용되지 않음

### 4️⃣제어 프롭

- 컴포넌트 자체적으로 상태를 관리하면서, **필요하면 부모도 관여**할 수 있게함
    - ⇒ 상태 값, 상태 업데이트 함수를 프롭으로 받음
    - ⇒ 프롭으로 받은 게 없다면 자율적으로 상태 관리 진행
- 제어 컴포넌트(Controlled Component) 개념을 확장한 것
    - 부모 컴포넌트가 상태를 관리하고 값을 업데이트 하는 컴포넌트
    - 대표적으로 `<input>` 엘리먼트가 있음
        
        ```jsx
        function Form() {
        	const [inputValue, setInputValue] = React.useState('');
        	
        	function handleChange(event) {
        		setInputValue(event.target.value);
        	}
        	
        	return <input type='text' value={inputValue} onChange={handleChange} />;
        }
        ```
        
- ✅제어 및 비제어 시 작동 모드를 모두 제공해 컴포넌트의 유연성 향상
- ❌제어 및 비제어를 위한 코드가 혼재되어 복잡함

### 5️⃣프롭 컬렉션

- **함께 쓰이는 여러 프롭을** 한 곳에 모아두고(컬렉션), 여러 컴포넌트에서 **재사용**
- 예시: 접근성을 위한 `aria-*`, 드래그&드롭에 필요한 이벤트 핸들러들 등
- 프롭 게터: 기본 동작과 사용자 정의 동작을 조합해 프롭 컬렉션을 반환하는 함수 (프롭 주입 가능)
    
    ```jsx
    // 인수로 받은 함수들을 차례로 실행하는 함수를 반환함
    const compose = (...functions) => 
    	(...args) => 
    	functions.forEach((fn) => fn?.(...args));
    
    export const getDroppableProps = ({
      onDragOver: replacementOnDragOver,
      ...replacementProps
    }) => {
    	// 기본 동작
      const defaultOnDragOver = (event) => {
        event.preventDefault();
      };
    
      return {
        onDragOver: compose(replacementOnDragOver, defaultOnDragOver),
        onDrop: (event)> {},
        ...replacementProps,
      };
    };
    ```
    
    ```jsx
    // 프롭 게터를 사용해 프롭 컬렉션 get
    const droppableProps = getDroppableProps({
    	onDragOver: () => {
    		alert("Dragged!"); // 사용자 정의 동작
    	},
    });
    
    <Dropzone	{...droppableProps }/>
    ```
    

### 6️⃣복합(합성) 컴포넌트(Compound Component)

- 컴포넌트끼리 상태를 공유하면서도 독립적으로 렌더링할 수 있게 함
- 자식 컴포넌트가 콘텍스트 상태를 인식하고, 렌더링 제어를 부모 컴포넌트에게 넘김
- 예시 코드
    
    ```jsx
    <Accordion>
      <AccordionItem key={items[0].id} item={items[0]} index={0} />
      <AccordionItem key={items[1].id} item={items[1]} index={1} />
      <hr />
      <AccordionItem key={items[2].id} item={items[2]} index={2} />
    </Accordion>
    ```
    
- ✅상태와 관심사 분리가 자연스럽게 이루어지고, 확장성이 높아짐

### 7️⃣State Reducer

- 외부 리듀서 함수를 인자/프롭으로 받아 기본 리듀서 함수 대신 실행(또는 결합하여 실행) ⇒ 역제어
- ✅**기존 컴포넌트를 변경하지 않고도 동작을 매우 유연하게 수정**할 수 있음

## 📌복습하기

- **1. 리액트에서 메모화란 무엇이며, 컴포넌트 렌더링을 최적화하는 데 어떻게 사용할 수 있을까요?**
    
    프로그래밍에서 ‘메모화’란 함수의 결과 값을 메모하여, 동일한 함수를 다시 실행해야 할 때 메모한 값을 재사용하는 최적화 기법입니다. 리액트는 **디핑 알고리즘에 의한 불필요한 리렌더링 문제를 방지하는 방안으로 컴포넌트나 함수, 프롭 등을 메모화하는 방법을 제공**합니다.
    
    리액트는 컴포넌트 렌더링을 최적화하기 위해 `React.memo`로 컴포넌트를 메모화해 프롭 변경 시에만 리렌더링합니다. 이때 컴포넌트가 객체를 프롭으로 갖는다면, 프롭이 변경되지 않아도 변경된 것으로 간주될 수 있습니다. 이를 방지하기 위해 `useMemo`로 프롭을 메모화합니다.
    
    `useMemo`는 비용이 비싼 함수의 결과 값을 메모화하는 데에도 사용할 수 있고, `useCallback`를 사용하면 함수 정의 자체를 메모화할 수 있습니다.
    
- **2. 리액트에서 상태 관리를 위해 useReducer를 사용하면 어떤 우세한 점이 있으며, useReducer는 useState와 어떻게 다른가요?**
    
    useState와 useReducer 모두 상태 관리를 위한 훅이지만, useState는 단일 상태 관리에, useReducer는 객체처럼 복잡한 상태 관리에 강점을 보입니다. 또 useReducer를 사용하면 리듀서 함수를 작성해야 하는데, 이를 통해 다양한 케이스(action)에 대한 상태 업데이트 로직을 한 곳에서 관리할 수 있게 됩니다. 뿐만 아니라 리듀서 함수를 컴포넌트와 분리할 수 있어 따로 테스트하기 용이하거나 다른 컴포넌트에서 재사용할 수 있다는 이점이 있습니다.
    
- **3. React.lazy와 Suspense 컴포넌트를 사용하는 리액트 애플리케이션에서 지연 로딩을 어떻게 구현할 수 있나요?**
    
    React.lazy를 사용하여 당장 화면에 렌더되지 않는 컴포넌트를 지연 로딩할 수 있습니다. 이렇게 지연 로딩한 컴포넌트는 화면에 렌더링 되어야 할 때 비로소 로드되기 시작하는데, 이때 Suspense를 사용하여 렌더링이 완료될 때까지 폴백 UI를 제공하여 UX를 향상할 수 있습니다.
    
- **4. 리액트에서 메모화를 사용할 때 발생할 수 있는 잠재적 문제는 무엇이며 어떻게 완화할 수 있을까요?**
    
    💬잠재적 문제? 메모리? 남용? 잘못된 사용? 호스트 컴포넌트 메모? 뭘 말하는 거지.. 이게 잠재적인가?
    
    불필요한 메모화나 제대로 메모화하지 않은 경우에는 메모화가 오히려 성능 저하를 유발할 수 있습니다. 예를 들어 React.memo로 컴포넌트를 메모화해도 객체 프롭을 메모화하지 않거나, 비용이 비싸지 않은 컴포넌트를 메모화하는 등의 경우 불필요한 프롭 비교 연산만 추가되는 격입니다. 따라서 리액트의 메모화는 연산 혹은 렌더링 비용이 비싸서 과정을 건너뛰어야 할 때 사용을 고려해야 합니다.
    
- **5. 리액트에서 컴포넌트에 프롭으로 전달된 함수를 메모화하기 위해 useCallback 훅을 어떻게 사용할 수 있나요?**
    
    부모 컴포넌트에서 함수를 프롭으로 전달하면, 부모 컴포넌트가 리렌더링되었을 때 함수가 재생성됩니다. 자식 컴포넌트를 React.memo로 메모화했어도 프롭으로 함수를 받는다면 항상 새로운 함수를 받게 되므로 불필요한 리렌더링이 발생합니다. useCallback으로 함수를 메모화한 후 프롭으로 전달하면, 의존성이 변경되지 않는 한 메모화한 자식 컴포넌트에 항상 같은 함수를 전달할 수 있습니다.
