# CHAPTER 9 리액트 서버 컴포넌트

## 📌서버 컴포넌트와 클라이언트 컴포넌트

- 리액트 서버 컴포넌트
    - 서버에서 실행되는 컴포넌트
    - 클라이언트 자바스크립트 번들에 포함되지 않음
    - 빌드 시점에 실행될 수 있음 → 정적 콘텐츠를 가져오거나 데이터 레이어에 접근할 수 있음
    - SSR+MPA 와 CSR+SPA의 장점을 결합해, 성능은 유지하고 매끄러운 UX를 제공함
- 클라이언트 컴포넌트
    - 부작용이 있는 훅, 인터랙티브한 부분 등이 포함된 컴포넌트
    - `"use client"` 지시어를 추가해 명시할 수 있음
    - 클라이언트 자바스크립트 번들에 포함됨

## 📌장점

- **예측 가능성**: 클라이언트 환경은 예측하기 어려운 반면, 서버 환경은 우리가 제어할 수 있음
- **보안**: 안전한 서버 환경에서 실행되므로 민감한 정보가 유출될 걱정이 없음
- **비동기 동작**: 비동기로 동작할 수 있어 데이터 의존성이 해결된 엘리먼트 생성 가능
- **성능**: 서버/클라이언트 컴포넌트를 나누면서 **필요한 부분(클라이언트 컴포넌트)만 자바스크립트 번들에 포함되어 번들 크기가 작아짐**
    - 로딩 시간 빨라짐
    - CPU 측면에서 파싱 및 실행할 자바스크립트가 줄어듦
    - 네트워크 측면에서 다운로드할 데이터 양이 줄어듦

## 📌서버 컴포넌트와 서버 렌더링

### 렌더러 설명

- **RSC 렌더러**: 서버 컴포넌트 → 리액트 엘리먼트 트리
- **서버 렌더러**: 리액트 엘리먼트 → HTML 스트림
- 두 렌더러를 통해 서버 컴포넌트가 HTML로 렌더링되고, 이를 클라이언트에 전송함
- 렌더링 목적은 서버 리액트와 클라이언트 리액트 둘 다 이해할 수 있는 데이터를 반환하는 것

### 렌더링 과정

- 1️⃣서버에서 JSX 트리를 리액트 엘리먼트 트리로 변환함
    - 컴포넌트가 문자열/숫자/불리언 타입이면 JSX 그대로 반환함
    - 컴포넌트가 배열 타입이면 각 항목을 처리해 반환함
    - 호스트 컴포넌트면 JSON으로 변환하여 반환함
    - 커스텀 컴포넌트(=함수 타입)면 1️⃣을 재귀 호출한 결과를 반환함
    
    <aside>
    💡
    
    서버 컴포넌트는 서버에서만 실행될 수 있으므로 `await`을 사용할 수 있고, 이를 통해 커스텀 컴포넌트의 비동기 작업이 완료될 때까지 기다릴 수 있다. 즉 서버에서 비동기 작업이 처리되어 데이터 의존성이 모두 해결된 엘리먼트를 생성할 수 있게 된다.
    
    </aside>
    
- 2️⃣서버에서 이 엘리먼트 트리를 HTML 문자열로 변환함(=직렬화)
    
    <aside>
    💡
    
    직렬화를 통해 즉시 표시할 수 있는 완전한 HTML 페이지가 생성되고, 이를 페이지의 초기 마크업으로 사용한다. 이후 자바스크립트 번들이 클라이언트에 로드되면 그때 동적 콘텐츠를 채우면서 하이드레이션이 일어난다.
    
    </aside>
    
- 3️⃣문자열로 변환된 JSON 객체가 클라이언트로 전송됨
- 4️⃣클라이언트 측 리액트가 JSON을 파싱해 렌더링함

### 소프트 내비게이션

- 하드 내비게이션: 페이지를 완전히 새로고침하는 방식
- 소프트 내비게이션: 필요한 데이터만 불러와서 새 페이지를 표시하는 방식
- 이동하고자 하는 URL을 서버로 전송하면 서버는 해당 페이지의 JSX 트리를 문자열 등으로 변환하여 반환함 → 브라우저 측 리액트가 이 JSX 트리로 전체 페이지를 다시 렌더링함 (⇒ 새로고침 필요 X)

### 클라이언트 컴포넌트 실행 시점

- 서버에서 서버 컴포넌트와 클라이언트 컴포넌트를 렌더링하고, 결과 트리를 브라우저로 전송함
    - 이 시점부터 서버 컴포넌트는 클라이언트에서 실행되지 않음
    - 이 시점부터 클라이언트 컴포넌트는 클라이언트에서만 실행됨
- 클라이언트 번들러가 전체 트리에서 클라이언트 컴포넌트 부분을 참조해둠(=플레이스홀더)
- 리액트가 트리를 렌더링하다가 참조 지점을 만나면 번들에서 해당 클라이언트 컴포넌트를 가져와 실행함
- 플레이스홀더가 실제 모듈로 교체됨

## 📌서버 컴포넌트 규칙

- **프롭 직렬화 가능성**
    
    서버 컴포넌트에서는 모든 프롭을 직렬화해 클라이언트로 전송할 수 있어야 함 ⇒ 함수처럼 직렬화할 수 없는 값을 프롭으로 사용할 수 없음 (⇒ 렌더 프롭 디자인 패턴은 서버 컴포넌트에서 사용할 수 없음)
    
- **부작용 훅 금지**
    
    서버 환경은 인터랙티브하지도 않고, DOM이나 window 객체도 없으므로, 상태 변경, DOM 업데이트, 데이터 페칭 등 부작용이 있는 훅을 사용할 수 없음
    
    <aside>
    💡
    
    `useRef`처럼 부작용이 없는 훅은 사용할 수 있음
    
    </aside>
    
- **상태는 클라이언트 컴포넌트에서**
    
    서버와 클라이언트 관계는 1:N ⇒ 서버의 상태가 여러 클라이언트에 공유될 수 있고, 이를 통해 클라이언트 간 상태가 노출될 수 있음 ⇒ 상태를 다룰 컴포넌트는 클라이언트 컴포넌트로 작성해 클라이언트끼리 상태가 공유되지 않게 해야 함
    
- **클라이언트 컴포넌트에서 서버 컴포넌트를 `import`할 수 없음**
    
    서버 컴포넌트 `import` 시 스크립트 번들에 포함되는데, 서버 컴포넌트는 클라이언트 환경에서 사용할 수 없는 요소를 포함할 수 있음(ex. Node.js API).
    

## 📌서버 액션(서버 함수)

- 클라이언트 코드에서 호출할 수 있는 서버 함수
- `"use server"` 지시어를 추가해 명시할 수 있음
- 다양한 활용이 가능하지만 설정이 복잡하고 번거롭기 때문에, 프레임워크나 라이브러리를 통해 사용하는 것을 권장함

## 📌복습하기

- **1. 리액트 서버 컴포넌트의 주된 가치는 무엇인가요?**
    
    서버에서만 렌더링할 컴포넌트와 클라이언트에서만 렌더링할 컴포넌트를 나눔으로써 성능을 향상시킬 수 있다는 것입니다. 이 성능 향상은 사용자 경험 개선으로 이어집니다.
    
- **2. 클라이언트 컴포넌트가 서버 컴포넌트를 가져올 수 있나요? 그렇게 답변한 이유가 무엇인가요?**
    
    클라이언트 컴포넌트는 서버 컴포넌트를 `import`할 수 없습니다. 클라이언트 컴포넌트가 서버 컴포넌트를 가져오면 해당 서버 컴포넌트도 클라이언트 자바스크립트 번들에 포함되는데, 서버 컴포넌트에는 클라이언트가 이해하지 못하는 코드가 있을 수 있기 때문입니다.
    
- **3. 서버 컴포넌트와 기존 클라이언트 전용 리액트 애플리케이션 사이에는 어떤 트레이드오프가 있었나요?**
    
    기존에는 컴포넌트가 항상 클라이언트 측에서 렌더링되므로 이와 관련해서 개발할 때 유의할 점이 없습니다. 그러나 서버 컴포넌트의 경우 서버 컴포넌트와 클라이언트 컴포넌트가 나뉘어 있고, 각각의 역할이 있으므로 이를 유의하며 개발해야 합니다. 두 컴포넌트 사이 경계를 나누기 어려울 수 있습니다.
    
- **4. 모듈 참조란 무엇이며, 리액트는 재조정 과정에서 모듈 참조를 어떻게 처리하나요?**
    
    서버 컴포넌트와 클라이언트 컴포넌트가 서버 측에서 렌더링될 때, 클라이언트 컴포넌트를 번들러가 참조하는 것을 말합니다. 리액트가 재조정 과정에서 해당 클라이언트 컴포넌트를 렌더링하기 위해 번들러가 참조한 모듈(=클라이언트 컴포넌트)을 가져와 실행하고, 이를 통해 참조한 모듈이 실제 모듈로 교체됩니다.
    
- **5. 서버 액션은 어떤 방식으로 리액트 애플리케이션의 접근성을 향상시키나요?**
    
    클라이언트 코드에서 서버 함수를 사용할 수 있게 만듭니다. 서버 액션을 통해 클라이언트 컴포넌트와 서버 컴포넌트 사이에서 유연하고 확장성 있게 개발할 수 있습니다.
