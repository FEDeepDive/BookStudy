## 9.1 장점
- 서버 컴포넌트를 사용하면 토큰과 같은 민감한 정보의 유출에서 다소 안전해지며, 비동기로 동작할 수 있기 때문에 동작이 완료될 때까지 기다릴 수 있음

## 9.2 서버 렌더링
- 서버 컴포넌트와 서버 렌더링은 두 개의 독립적인 프로세스로 생각할 수 있음
  1. RSC 렌더러: 컴포넌트를 렌더링하여 리액트 요소 트리를 생성하는 과정
  2. 서버 렌더러: 생성된 리액트 요소 트리를 마크업으로 변환하는 과정 -> 즉 "서버 사이드 렌더링" 과정!
- 서버 컴포넌트와 서버 렌더링은 상호 보완적인 관계!
- 서버 컴포넌트를 리액트 요소 트리로 변환하기 위해서는 그에 맞는 리액트 렌더러를 사용할 필요가 있음
- 재귀적으로 컴포넌트를 호출하며 입력된 인자가 리액트 요소를 나타내는 속성을 가지고 있는지, 가지고 있다면 그 속성이 무엇인지에 따라 리액트 요소로 변환
- 서버, 클라이언트에 각각 있는 리액트가 모두 이해할 수 있도록 데이터를 반환해야 함
  - 스칼라 값의 경우 그냥 반환하지만, 배열/객체의 경우 별도 처리
  - 서버 컴포넌트는 서버에서 실행되기 때문에 `await`할 수 있다!
- 변환된 리액트 요소는 브라우저로 전송하기 위해 "직렬화"할 필요가 있음
  - 각 요소에 해당하는 HTML을 생성하고 이를 합쳐 하나의 큰 HTML 문자열을 생성
- 직렬화된 HTML 문자열을 클라이언트로 보내 초기 마크업으로 사용하고, 자바스크립트 번들이 클라이언트에 로드되면 하이드레이션을 실행
- 리액트 엘리먼트는 일반적인 객체가 아니기 때문에 바로 직렬화할 수 없음
  - 객체가 리액트 요소인지 판별하기 위한 속성 `$$typeof`는 `Symbol` 타입이라서 `JSON.stringify()`가 문자열로 변환하지 않기 때문
  - `JSON.stringify()`, `JSON.parse()`에 변환을 위한 별도의 함수를 지정해 직렬화/역직렬화 로직을 작성해야 함
    - (#) 책에서는 `JSON.parse()`의 매개변수도 `replacer`라고 적혀있는데 MDN을 보니 [`reviver`](https://developer.mozilla.org/ko/docs/Web/JavaScript/Reference/Global_Objects/JSON/parse#%EA%B5%AC%EB%AC%B8)라고 부르기도 하나봅니다
- 일반적으로 `<a>` 태그와 상호작용하면 하드 내비게이션이 발생하지만 RSC를 사용하여 소프트 내비게이션을 구현할 수 있음
  - 애플리케이션 내부에 있는 모든 링크의 기본 동작을 방지하기 위해 `window` 객체에 이벤트 리스너를 추가하고 타겟에 따라 이벤트를 실행하는 이벤트 위임 방식을 사용
  - 새로고침 없이 페이지 내용을 갱신하기 위해 페이지를 처음 하이드레이션할 때 리액트에서 얻어온 `root`에 새로운 요소를 렌더링
  - 요청 헤더에 `jsx-only`가 있을 경우 다음에 보여줄 JSX 트리 객체를 반환하며, 클라이언트가 역직렬화할 수 있도록 문자열 형태로 전송함
- 서버는 사용자 상호작용이 일어날 수 없는 환경이며, 서버 환경에서 '상태'라는 개념은 여러 클라이언트에 걸쳐 공유되기 때문에 애플리케이션 내부에서만 공유되는 클라이언트 상태와는 근본적으로 다름
  - 따라서 상호작용을 담당하는 부분을 별도로 분리해야 함
  - 이렇게 분리된 부분만 클라이언트 자바스크립트 번들에 포함되기 때문에 성능이 향상되고 클라이언트가 다운로드해야하는 데이터의 양도 줄어들음
- 클라이언트 컴포넌트를 서버 컴포넌트와 구분짓기 위해 `use client` 지시자를 추가해야 하며, 이를 해석하기 위해 차세대 번들러가 필요함
  - 차세대 번들러를 사용할 경우 서버와 클라이언트 각각에 대한 모듈 그래프를 생성할 수 있음
  - 서버 컴포넌트 렌더링 시 클라이언트에서 렌더링되어야 하는 모듈에 대한 참조를 렌더링함
  - 클라이언트에서 이를 전달받아 렌더링할 때 참조를 실제 모듈로 대체하는 과정을 진행
- 서버 컴포넌트는 서버에서만 실행되지만 클라이언트 컴포넌트는 클라이언트에서만 실행되지 않는다는 사실!!!

## 9.3 서버 컴포넌트 규칙
- `props`는 클라이언트로 전송될 수 있어야 하기 때문에 서버 컴포넌트에서는 모든 `props`가 직렬화 가능해야 함
- 서버 환경은 클라이언트와 완전히 다르기 때문에 렌더링 이외의 부작용이 존재하는 hooks는 서버 컴포넌트에서 사용할 수 없음
- 클라이언트 환경에는 서버 컴포넌트 관련 코드가 포함되지 않기 때문에 클라이언트 컴포넌트에서는 서버 컴포넌트를 `import`할 수 없음
  - 다만 `props` 형태로 작성할 수는 있음!

## 9.4 서버 액션
- `use server` 지시자를 사용해 클라이언트 코드에서 호출할 수 있지만 서버에서만 실행되는 "서버 함수"를 표시할 수 있음
  - 원래는 서버 액션이라는 이름이었으나 "서버 함수"로 명칭이 바뀜
  - (#) Next.js도 15 버전 기준 동일하게 서버 함수로 명칭이 변경됨
- 함수에 전달된 모든 인수는 직렬화되어 서버에 전달되고, 반환된 값도 직렬화되어 클라이언트로 반환됨
- 서버 함수를 통해 자바스크립트 번들이 모두 로드되기 전에도 폼을 전송할 수 있음
- 서버 함수는 "엔드포인트" 형태로 노출되며 클라이언트 코드 어디에서든 호출할 수 있음
  - (#) Next.js App Router 기준 서버 액션은 `POST` 형식이며, 따라서 [서버의 상태를 변경하는 형태의 로직만을 사용하도록 권장](https://github.com/vercel/next.js/commit/29fcd57ed1a5566fc00599be53732b187d17925f)하고 있습니다.
  - (#) [다른 구현체](https://tanstack.com/start/latest/docs/framework/react/server-functions#available-options)는 `GET`도 쓸 수 있는 모양입니다...

## 9.7 복습하기
1. 리액트 서버 컴포넌트의 주된 가치는 무엇인가요?
  - 파일 시스템에서 데이터를 읽거나 비동기 함수를 기다리는 등 기존 클라이언트 컴포넌트로는 불가능했던 작업을 가능케 함
  - 실제로 상호작용을 처리하는 코드만 클라이언트 번들에 포함시켜 성능을 높이고 다운로드해야 하는 데이터 양을 줄일 수 있음
2. 클라이언트 컴포넌트가 서버 컴포넌트를 가져올 수 있나요? 그렇게 답변한 이유가 무엇인가요?
  - 클라이언트 컴포넌트는 서버 컴포넌트를 `import`할 수 없음
  - 서버 컴포넌트는 클라이언트 환경에서 사용할 수 없는 요소를 포함할 수 있기에 오류가 발생하기 때문
  - 대신 `props`를 통해 조합하는 것은 가능
3. 서버 컴포넌트와 기존 클라이언트 전용 리액트 애플리케이션 사이에는 어떤 트레이드오프가 있나요?
  - 서버 컴포넌트는 UI를 빠르게 보여주며 웹사이트의 성능을 높일 수 있지만 복잡한 사용자 상호작용을 처리할 수 없고 브라우저 API를 사용할 수 없음
  - 클라이언트 컴포넌트는 자유로운 사용자 상호작용 로직을 가질 수 있지만 자바스크립트 번들이 다운로드되고 나서야 처리를 시작할 수 있음
4. 모듈 참조란 무엇이며, 리액트는 재조정 과정에서 모듈 참조를 어떻게 처리하나요?
  - 서버 컴포넌트 렌더링 시 클라이언트에서도 렌더링되어야 하는 부분을 위해 렌더링한 placeholder
  - 리액트는 클라이언트에서 이러한 placeholder를 만나면 전달받은 번들의 실제 모듈로 대체함
5. 서버 액션은 어떤 방식으로 리액트 애플리케이션의 접근성을 향상시키나요?
  - 자바스크립트 번들이 전부 로드되기 전에도 서버 액션을 사용하여 폼을 사용하고 `FormData`를 전송하는 점진적 향상(Progressive enhancement) 전략을 적용할 수 있음
