## 📌FE 기술 연대기 (React 이전)

### 1️⃣리액트는 왜 필요한가?

- 웹 초창기: 정적 페이지로 업데이트 시 새 페이지를 렌더링
- → 웹 기능이 늘자, 페이지 렌더링을 기다리지 않고 `"즉각적인 업데이트"` 제공 욕구
- → but 즉각적 업데이트를 `"대규모"`로 수행하기는 어려움
    - 업데이트 = 렌더링 = 리플로우 ⇒ 대규모 수행 시 성능 저하
    - 업데이트 = 상태 변경 ⇒ 대규모 수행 시 상태 추적/유지 어려움
    - 보안(XSS, CSRF 악용 방지)을 위해 사용자 입력 데이터 소독 필요 ⇒ 대규모 수행 비용
- 기존 HTML+JS로 대규모 앱을 구축하기엔 한계 O, `코드 추상화 필요`

### 2️⃣등장한 해결책

- **jQuery (2006~)**
    - ✅`DOM 조작 간편화` ⇒ 크로스 브라우저 이슈 완화 (ex. DOM 조작, 이벤트 핸들링 방식)
    - ❌코드 어디에서든 페이지 수정 가능 ⇒ 상태 예측 가능성 ↓ & 구조화 X
    - ❌최신 브라우저/JS와 기능 중복
- **Backbone (2010~)**
    - ✅`MVC 패턴` ⇒ 코드 재사용성 & 예측 가능성 (브라우저-JS 간 상태 불일치 문제 해결)
    - ❌보일러플레이트 코드 多
    - ❌뷰 간 조합성 부족 ⇒ 복잡한 UI 구성이 어려움
- **Knockout (2010~)**
    - ✅`MVVM 패턴` ⇒ 요소 간 결합이 강한 MVC 패턴에 비해, 데이터 소유권이 명확
    - ❌보일러플레이트 코드 多
- **AngularJS (2010~2022)** (*Angular: 2016~)
    - `양방향 데이터 바인딩`
        - ✅뷰-모델 자동 동기화
        - ❌예측 가능성 ↓ & 버그 발생 가능성 ↑
        - ❌바인딩이 많은 대규모 앱에서 변화 감지로 인한 성능 저하
    - `모듈식 아키텍처` + `의존성 주입(DI)`
        - ✅기능 별로 독립적 관리 가능 ⇒ 재사용성, 테스트 가능성, 유지보수성 ↑
        - ❌코드 복잡성 & 러닝커브

## 📌리액트의 필요성과 핵심 가치

리액트는 1️⃣**대규모 앱에서 예측 가능하고 안전하게 개발**할 수 있게 해주고, 2️⃣개발자가 개발에 몰두할 수 있도록 해준다.

- `선언적 코드`: 보여주고 싶은 것만 코딩, 이를 어떻게 가능하게 할지는 리액트가 알아서 함
- `컴포넌트 아키텍처`: 관심사 분리 & 코드 재사용성 & 로직과 로직이 필요한 UI를 가까이!
- `불변 상태`: UI가 특정 시점 특정 상태를 반영함을 보장(=예측 가능성) & 안전성
- `플럭스 아키텍처`: 대규모 앱에서 데이터 흐름을 ‘예측 가능하게’ 관리
- `가상 DOM`: DOM 조작 횟수 최소화 & 개발자가 DOM 조작할 필요 X & 업데이트 일괄 처리

## 📌복습하기

- **❓리액트를 만들게 된 동기가 무엇인가요?**
    
    웹이 발전하면서 할 수 있는 것들이 많아지자, 더 많은 상태가 더 자주 변경되기 시작했다. 개발자들은 사용자가 새 페이지 렌더링을 기다리지 않고 변경 사항을 즉시 확인할 수 있기를 바랐다. 하지만 기존의 HTML+JS는 대규모 앱을 만들고 대규모 업데이트를 즉각적으로 수행하기엔 한계가 있었다.
    
    개발자들은 대규모 업데이트를 즉각적으로 수행할 수 있으면서, 예측 가능하고 안전하게 개발할 수 있는 기술을 필요로 했다.
    
    이에 리액트가 출시되었으며, 리액트는 선언형 프로그래밍이나 컴포넌트 기반 아키텍처, 단방향 흐름, 가상 DOM 등을 통해 문제를 해결하였다.
    
- **❓리액트가 MVC와 MVVM 같은 이전 패턴보다 개선된 점은 무엇인가요?**
    
    리액트는 `컴포넌트 기반 아키텍처`와 `플럭스 아키텍처`를 도입해 MVC, MVVM 패턴을 채용한 리액트 이전 기술에 비해 더욱 “안전하고 예측 가능하게 개발”할 수 있도록 하고, “코드 재사용성과 유지보수성”을 높였다.
    
    - `MVC`
        - 각 요소 간 강한 결합 ⇒ 유지보수 ↓
        - 규모가 커질수록 컨트롤러가 많아지며 복잡성 ↑
        - 보일러플레이트 코드 多
    - `MVVM`
        - 느슨한 결합 즉, 자유로움으로 MVC 단점 커버
        - 양방향 데이터 흐름 ⇒ 버그 발생 가능성 ↑
        - 보일러플레이트 코드 多 ⇒ 리팩터링, 코드 최적화 어려움
    - `리액트`
        - 단방향 데이터 흐름 ⇒ 안전 & 예측 가능성 ↑, 버그 발생 가능성 ↓
        - 보일러플레이트 코드 필요 X
        - UI와 UI 관련 로직을 가까이 둘 수 있음 (MVC, MVVM은 관심사 분리로 서로 멀리 떨어짐)
- **❓플럭스 아키텍처의 특징은 무엇인가요?**
    - 액션, 디스패처, 스토어, 뷰로 이루어짐
    - 단방향 데이터 흐름 ⇒ 예측 가능성
    - 여러 데이터의 출처를 스토어로 통일 ⇒ 신뢰성, 안정성
    - 테스트 가능성(testability)
- **❓선언적 프로그래밍 추상화의 장점은 무엇인가요?**
    - 개발자는 보여주고 싶은 것에 초점을 맞추면 됨 (나머지는 생각할 필요가 없음)
    - 코드 가독성이 좋음
- **❓효율적인 UI 업데이트를 위한 가상 DOM의 역할은 무엇인가요?**
    
    가상 DOM은 실제 DOM을 객체로 표현하는 프로그래밍 개념으로, 컴포넌트 변경 사항 추적을 위해 사용된다. 개발자가 실제 DOM을 조작하지 않아도, 가상 DOM을 통해 UI를 업데이트할 수 있어 안전하다. 가상 DOM을 활용한 UI 업데이트 방식은 다음과 같다.
    
    - 가상 DOM 생성 → 업데이트 시 새 가상 DOM 생성 → 서로 비교 → 실제 DOM에 필요한 부분만 적용
    - 💬책에서는 가상 DOM에 대해 “변경 사항이 있을 때마다 전체 DOM 트리를 업데이트하는 것보다 빠르고 효율적이다”라고 주장하고 있는데, [실제로도 그럴까?](https://youtu.be/kgnv6ZOa81w?si=YkXOZ82Jn4UO0R9e&t=90) 이에 대한 반론은 많은데 왜 작가는 이렇게 설명했을까?

## 💬느낀 점

- 테스트 코드를 예제마다 달아준 점 => 테스트가 중요해서겠지
- 역사를 보는 게, '나 정말 많은 일이 있었어...' 를 보는 느낌 ㅋㅋ
- 기존에 알던 역사(ex. SPA의 등장 배경)는 엄청 누르고 압축한 거구나 싶었음
- 리액트 개발을 하면서 단방향 데이터 흐름 때문에 힘든 적이 많았는데, 이게 엄청난 장점이고 이 패턴만으로도 수많은 위험 요소들을 방지하고 있구나 깨달음
- 리액트가 가진 특징 "선언형", "컴포넌트 기반"이 왜 장점으로 작용하는지 더 잘 깨닫게 됨
- 다루는 내용들이 하나하나가 굵직한 건데 잘 정리해서 적어줘서 모르는 개념도 편하게 읽을 수 있었음
