# CHAPTER 1 입문자를 위한 지식

### 📌 1.1 리액트는 왜 필요한가요?

업데이트를 효율적으로 안정적으로 하기 위해서.

성능 ⇒ 업데이트시 발생하는 리플로우가 성능 병목 현상을 발생시킴

신뢰성 ⇒ 상태를 일관되게 유지 하기 어려웠음

보안 ⇒ 크로스사이트스크립팅 및 크로스 사이트 요청위조 같은 악용이 쉬웠고, 그래서 데이터 문제가 될만한 부분을 일일히 제거하는 소독 과정이 필요했다.

### 📌 **1.2 리액트 이전의 세계**

본격적으로 리액트가 없었을 시절에 웹은 어떻게 만들어졌는지를 얘기 하고 있음

생으로 구현할때 상태를 관리하는게 복잡함

시대가 발전하면서 유지보수가 용이하고 재사용이 가능하며, 예측가능한 방식으로 대규모 코드를 꾸리는것이 당시 개발자들의 숙제였다고 한다.

💬  새삼.. 이때 개발자들이 더 미친듯이 똑똑한거 같다고 느끼며, 덕분에 비교적 편하게 개발하고 있고

시간이 지나면 얼마나 더 좋은 기능들이 나올지 기대되는 느낌도 든다

### 1.2.1 jQuery

💬 한번쯤 정리해보고 싶었는데 마침 주제로 나와서 좋았다

jQuery가 처음 나왔을 당시엔 `querySelector()` 도 없었고, 바닐라로 적어주기엔 코드가 굉장히 길었다

- **코드가 간결해지고, 직관적이었음** → `document.getElementById("id")` 대신 `$("#id")` 사용 가능.
- **브라우저 호환성 문제를 해결했음** → IE6, IE7에서도 정상 동작.
- **AJAX 요청을 쉽게 처리할 수 있었음** → `$.get()`, `$.post()` 등으로 간단한 코드 작성 가능.
- **애니메이션을 쉽게 추가할 수 있었음** → `fadeOut()`, `slideUp()` 등 제공.
- **플러그인 생태계가 잘 형성되어 확장성이 뛰어났음** → 다양한 기능을 쉽게 추가 가능.

💬 나였어도 jQuery에 등장에 환호 했을것 같다.

**그러나 사람들이 점점 jQuery를 떠난 이유**

- **부작용을 이르킬수 있는 방식**
    - 전적적으로 수정가능함 (어디에서도 접근 할 수 있음)
    - 직접적인 돔조작
- **테스트 하기 어려움**
    - 브라우저 렌더링을 테스트 하려면 브라우저를 흉내내야 하는데 작업이 많이 필요하고 jQuery가 추가하는 동작은 격리하기에 어려움이 있었다고 한다.
- **크기가 큼**
- **JavaScript(ES6+)와 브라우저 API가 발전함**
    - `document.querySelector()`와 `fetch()` 같은 기능이 추가되면서 jQuery가 제공하는 기능이 기본 JS에서도 가능해짐.
        - 예를들어 `fetch()`를 사용하면 jQuery 없이도 AJAX 요청이 간편헤짐

🚀 아무튼 지금도 레거시에 코드에 많이 남아있고 jQuery는 역사적으로 중요한 역할을 했음!

**1.2.2 Backbone**

💬 처음 들어본 라이브러리다! 갑분 MVC 패턴을 설명해서 아는단어에 반가움반 반갑지 않은 느낌 반.. 필자에게 인상깊지만 보일러 플레이트, 커뮤의 저속발전으로 리액트에게 밀려난..라이브러리1.

Backbone이 해결 한것

- jQuery에서 벗어나 구조적인 MVC 패턴을 제공하여 웹 애플리케이션 개발을 더 체계적으로 만들 수 있도록 도와줌
- RESTful API와의 연동을 지원하여 서버와 데이터 동기화를 쉽게 할 수 있도록 함
- SPA의 기초를 제공하여 이후 React 등의 프레임워크가 발전할 수 있는 발판이 됨

한계

- 장황한 코드
- 양방향 데이터 바인딩 부족
    - 데이터가 변경되면 돔이 자동 업데이트가 되지 않아서 개발자는 직접 작성, 플러그인을 사용해야만 했음
- 이벤트 중심의 아키텍처
    - 모델 데이터를 업데이트하면 수많은 이벤트가 발생할 수 있고, 그 이벤트 관리가 어려웠다고함.
    - 데이터 변경시 어떤 이벤트가 어디서 어떻게 문제가 생길지 모른다는거,,
- 컴포넌트 개념이 없어서 조합성이 부족했다

🚀 지금은 거의 사용되지 않지만, 현대적인 프레임워크가 등장하기 전의 중요한 과도기적 기술이었다! 

**1.2.3 Knockout**

- **MVVM 패턴을 도입**하여 UI와 데이터를 분리함.
- **양방향 바인딩을 지원**하여 입력값과 UI의 동기화를 간편하게 함.

한계 

컴포넌트 기반 개발이 부족하고, SPA 개발을 위한 기능이 부족했음.

**1.2.4 앵귤러JS**

💬 얘는 왜 한국어로 적으셨을까 ㅋㅋ

Backbone과 Knockout은 특정 기능만 제공했지만, 전체적인 애플리케이션 구조를 강제하지는 않았던 문제를 해결하고 자 나옴

- **모듈 단위로 쪼개어 관리할 수 있는 기능을 기본적으로 제공**
- 필요한 모듈을 선언하면 **자동으로 의존성이 해결됨!**

한계

복잡하고, 버전업이 되면서 하위버전을 호환하지 않아서 개발자들이 점점 떠난듯

⇒ 이런 무수한 과정들을 지나 많은 한계점을 해결하게 된 리액트가 등장함

### 📌 1.3 리액트 등장

💬 처음 등장했을때 반발 심했다는것, 얼마 지나지 않아 이는 웹에 한계를 깨는 라이브러리라고 여론 바뀐것 재밌당 역시 사람들은 오랬동안 유지해온게 있을때 새로운것이 나오면 방어적이고 약간의 거부반응이 생기는듯. 

1.3.3 플럭스 아키텍처

기존 데이터 흐름이 양방향 바인딩을 사용했는데 이는 성능저하와, 복잡성을 야기함. 플럭스 아키텍처라는 디자인 패턴을 통해 단방향 데이터흐름을 통해 예측가능한 어플리케이션을 만들어냄

- 양방향일땐 모든 바인딩을 체크해야 했지만 단방향으로 단일정보 출처를 통해 복잡성을 제거
- 테스트 가능성을 높임
- 관심사의 분리가 명확해짐

### 📌 1.4 그래서… 리액트는 왜 필요한가요?

**컴포넌트 기반 아키텍처** → 코드 재사용성과 유지보수성이 높아짐

**선언적 프로그래밍** → UI 업데이트를 자동으로 처리해 코드가 간결해짐

**가상 DOM** → 성능 최적화, 빠른 렌더링

**광범위한 생태계** → 다양한 라이브러리와 도구를 활용 가능

**플랫폼 독립적** → 웹, 모바일, VR 등 다양한 환경에서 사용 가능

**메타(Facebook)의 지원** → 안정적이고 대규모 프로젝트에서도 신뢰할 수 있음

💬

아직까지는 엄청 어렵지 않았고 경험해본 라이브러리 같은경우에는 흥미롭고 수월하게 읽었다. 정리가 필요했던 부분인데 북스터디를 통해 정리해서 좋았음. 면접에 도움이 될거 같음. 복습하기 부분 읽는데 몇개 대답 못했음 ㅋㅋ 북스터디때 이야기 하면 좋을거 같음.
