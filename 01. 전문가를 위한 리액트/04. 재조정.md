## 4.1 재조정 이해하기
- 가상 DOM은 우리가 원하는 UI 상태의 청사진이며 이를 가지고 **재조정**이라는 프로세스를 거쳐 현실로 만듦
- 컴포넌트를 호출하면 자신의 자손 요소를 포함한 리액트 요소를 반환
  - 리액트 요소는 JSX -> `createElement`를 통해 생성됨
- 꼭 필요한 DOM API만 호출한 후 브라우저에 반영

## 4.3 기존 기술
- 예전(적어도 [2018년](https://legacy.reactjs.org/blog/2018/11/13/react-conf-recap.html)까지는...) 리액트는 렌더링에 스택 기반 알고리즘을 사용하는 "스택 재조정자"를 사용함
- 스택이란 나중에 들어온 것이 먼저 나간다는 LIFO 원칙을 따르는 선형 자료구조
- 애플리케이션 규모가 복잡해지며 문제가 발생!!!
  - 계산 비용이 비싼 컴포넌트가 렌더링을 막아버리면 사용자 경험이 나빠짐!
    - 이런 문제는 리액트 뿐만 아니라 다른 곳에서도 찾아볼 수 있음 [#](https://developer.android.com/topic/performance/anrs/keep-your-app-responsive?hl=ko)
    - 이런 부분을 측정하는 지표가 바로 [Core Web Vital의 INP](https://web.dev/articles/inp?hl=ko)
  - 계산 비용이 비싼 컴포넌트가 굳이 즉시 작업될 필요가 없다면?
  - 그러나 스택은 LIFO 원칙을 따라야 하기 때문에 무조건 나중에 들어온 게 먼저 처리되어야 함
    - **덜 중요한 갱신이 더 중요한 갱신을 차단할 수 있음**
  - 또한 스택 재조정자는 한 번 실행된 작업을 중간에 멈추거나 취소할 수 없음
    - **우선순위가 있다고 해도 한 번 실행된 작업이라면 끝날 때까지 기다려야 함**
  - 이 두 가지 문제점을 해결하기 위해 파이버(Fiber)라는 자료구조를 사용하게 되었음

## 4.4 파이버 재조정자
- 파이버는 컴포넌트 인스턴스와 그 상태를 표현함
  - 재조정 과정에서 필요에 따라 갱신 및 재배치될 수 있음
- 파이버 재조정자는 루트 파이버 노드에서 시작해 컴포넌트 트리를 따라 내려가며 컴포넌트의 업데이트 필요 여부를 표시하는 [`beginWork`](https://github.com/facebook/react/blob/2980f27779cf37a9656b25418a3c5cfca989e244/packages/react-reconciler/src/ReactFiberBeginWork.js#L3769), 다시 위로 이동하며 브라우저에서 분리된 실제 DOM 트리를 메모리에 구성하는 [`completeWork`](https://github.com/facebook/react/blob/main/packages/react-reconciler/src/ReactFiberCompleteWork.js#L944) 함수로 표현되는 [작업 루프](https://github.com/facebook/react/blob/main/packages/react-reconciler/src/ReactFiberWorkLoop.js)를 통해 사용자 인터페이스를 갱신함
- 이 과정은 사용자의 눈에 보이지 않는 곳에서 일어나기 때문에 언제든 중단하거나 버릴 수 있음
- 비디오 게임에서 사용되는 더블 버퍼링이라는 개념과 비슷함 [#](https://youtu.be/x7cQ3mrcKaY?si=O5J_skkyr1C7Csh4&t=1207)
  - 게임에서 더블 버퍼링은 흔히 깜빡임 현상(flickering)을 줄이기 위해 도입한다고 알려져있지만, 우선순위가 더 높은 작업이 필요한 경우 이를 먼저 처리할 수 있다는 점과 사용자가 현재 보고 있는 화면을 망치지 않고 작업을 진행할 수 있다는 장점이 추가로 존재한다!
- 갱신이 필요하면 현재 파이버 트리가 복사(또는 fork)되어 새로운 상태를 반영하도록 갱신되는 **렌더링**, 해당 상태가 정확히 반영된 트리를 현재 파이버 트리와 교체하는 **커밋**의 두 가지 과정을 거치며 재조정이 이루어짐
- 렌더링된 파이버 트리가 실제로 커밋되기 전, 스케줄러에 의해 이 과정이 멈추거나 결과물이 버려질 수 있다!
- (솔직히 파이버와 스케줄러 / 동시성을 이렇게 멀게 배치하는 게 맞나 싶읍니다... 둘이 같이 붙어있어야 이해하기 쉬울 것 같은데)
- (스케줄러에 관해 도식과 함께 설명하는 발표 자료 [#](https://www.youtube.com/watch?v=ZCuYPiUIONs))
---
- 재조정 과정은 렌더링과 커밋의 두 단계로 이루어짐
  - 렌더링은 `beginWork`와 `completeWork`의 두 단계로 이루어짐
  - 커밋은 가상 DOM에 적용된 변경 사항을 실제 DOM에 반영하는 **변형**과 갱신된 DOM 노드의 새 레이아웃을 계산하는 **레이아웃**의 두 단계로 이루어짐
    - 이 과정에서 배치(placement) 효과, 갱신/삭제 효과, 레이아웃 효과 등의 부작용이 특정 순서로 실행됨
- 더블 버퍼링에서 현재 화면에 보이는 버퍼를 바꾸기 위해 두 버퍼를 가리키는 포인터를 서로 맞바꾸는 플리핑(flipping) 과정처럼, 리액트는 `commitRoot` 함수를 호출하여 현재 트리를 가리키고 있는 `FiberRootNode`의 포인터를 작업용 트리로 바꿈

## 4.6 복습하기
1. 리액트의 재조정이란 무엇인가요?
  - 우리가 실제로 원하는 UI를 표현하는 가상 DOM이라는 자료구조를 이용하여 실제 DOM에 변경을 가하는 과정을 말함.
  - 렌더링 단계와 커밋 단계로 이루어지며, 렌더링 단계가 올바르게 이루어지면 커밋 단계가 실행되어 최종적으로 원하는 형태의 갱신이 실제 DOM에 반영됨.
2. 파이버 데이터 구조의 역할은 무엇인가요?
  - 기존에 리액트 재조정에 사용되던 스택 기반 재조정자는 두 가지 약점을 가지고 있음.
    - 나중에 들어온 것이 항상 먼저 처리되기 때문에 UI 관점에서 덜 중요한 갱신이 더 중요한 갱신보다 먼저 처리될 수 있음.
      - 즉, 스택 기반 재조정에서는 갱신 간 우선순위가 존재하지 않음
    - 또한, 한 번 실행된 갱신이 중간에 중단될 수 없기 때문에 설령 우선순위가 있다고 하더라도 먼저 실행된 작업이 끝날 때까지 기다려야 함.
  - 파이버는 컴포넌트 인스턴스와 그 상태를 표현하는 자료구조로, 재조정 과정에서 필요에 따라 갱신 및 재배치될 수 있음.
3. 왜 트리가 두 개 필요한가요?
  - 우선순위가 더 높은 새로운 갱신이 필요한 경우, 이를 버릴 수 있어야 하기 때문!
  - 사용자가 현재 보고있는 화면을 망치지 않고 잠시 중단했다가 다시 시작할 수 있어야 하기 때문!
4. 애플리케이션이 업데이트되면 어떻게 되나요?
  - 갱신이 발생하는 경우 렌더링 단계와 커밋 단계를 거쳐 새로운 상태의 UI를 만듦.
  - 렌더링 단계에서는 특정 파이버 노드의 갱신 필요 여부를 설정하는 `beginWork`, 그러한 노드들에 갱신을 적용하고 이를 반영하는 실제 DOM 트리를 생성하는 `completeWork`라는 과정을 거침.
  - 렌더링이 완료되면 실제 DOM에 해당 작업 사항들이 반영되고, 현재 활성화된 트리를 나타내는 `FiberRootNode`의 포인터를 작업용 트리를 가리키도록 전환함.
  - 커밋 단계에서는 가상 DOM에 적용된 변경 사항을 실제 DOM에 반영하는 **변형**, 갱신된 노드의 새로운 레이아웃을 계산하는 **레이아웃** 과정을 거침.
