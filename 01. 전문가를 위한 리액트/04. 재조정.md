4.2 일괄처리

💬 리액트 공식문서에서 읽은 스냅샷 얘기가 나올거 같은 느낌이 듦. + 일괄처리? 뭔가 동시성이 갑자기 떠올라서 셋의 차이점을 정리해봄

### **세 개념의 관계**

| 개념                    | 설명                                                                             |
| ----------------------- | -------------------------------------------------------------------------------- |
| **동시성(Concurrency)** | 여러 작업을 동시에 실행하는 것처럼 보이게 함                                     |
| **스냅샷(Snapshot)**    | 렌더링이 시작될 때의 상태를 유지하여 **렌더링이 끝날 때까지 동일한 상태를 참조** |
| **일괄 처리(Batching)** | 여러 개의 상태 업데이트를 한 번의 렌더링으로 묶어서 실행                         |

**리액트는 동시성을 활용하여 성능을 최적화하고, 스냅샷 개념을 통해 렌더링 중 일관성을 유지하며, 배칭을 통해 불필요한 렌더링을 줄인다.**

### **파이버 재조정자(Reconciler)의 핵심 역할**

1. **작업을 쪼개서 수행**
   - 이전에는 전체 UI를 한 번에 업데이트했지만, 이제는 파이버를 활용해 **작업을 작은 단위로 나누고, 우선순위를 정해서 실행**할 수 있어.
   - 이를 통해 유저 인터랙션을 블로킹하지 않고 자연스럽게 업데이트가 가능.
2. **우선순위 기반 업데이트(Scheduling)**
   - 업데이트가 들어오면 **긴급한 작업(예: 사용자 입력) → 낮은 우선순위 작업(예: 애니메이션, 데이터 패칭)** 순으로 처리.
   - `requestIdleCallback` 같은 브라우저 API와 유사한 방식으로 **여유 시간이 생길 때 나머지 작업을 수행**.
3. **인터럽트 가능한 렌더링(Interruptible Rendering)**
   - 이전에는 업데이트가 시작되면 끝날 때까지 중단할 수 없었지만, 이제는 실행 중이던 작업을 **일시 중단하고 더 중요한 작업을 먼저 수행**할 수 있음.
   - 예를 들어, 사용자가 입력하는 동안 UI 업데이트 작업이 일시 정지되었다가 다시 이어질 수 있어.
4. **비동기 렌더링(Concurrent Mode)**
   - **여러 업데이트를 동시에 처리 가능** (멀티스레드처럼 동작)
   - `startTransition`, `useDeferredValue` 같은 API를 사용하면 UI가 버벅이지 않게 부드러운 사용자 경험 제공.

### **파이버의 아키텍처: 3단계 프로세스**

파이버는 다음 3단계를 거쳐 화면을 업데이트

1. **렌더(Render) 단계 (조정/Reconciliation)**
   - 트리를 순회하며 어떤 부분이 변경되었는지 계산
   - 비동기적으로 실행될 수 있음
   - 새로운 Fiber 트리를 생성 (더블 버퍼링 활용)
2. **커밋(Commit) 단계**
   - 모든 변경 사항을 실제 DOM에 반영
   - 동기적으로 실행됨
   - `componentDidMount`, `componentDidUpdate`, `useEffect` 등이 실행되는 시점
3. **레이아웃(Layout) 단계**
   - DOM 업데이트 후 추가적인 레이아웃 작업을 수행
   - `useLayoutEffect`가 이 단계에서 실행됨

※ **더블 버퍼링(Double Buffering)**

- **현재 트리(Current Fiber Tree)**: 현재 화면에 렌더링된 상태
- **작업 중인 트리(Work In Progress Fiber Tree)**: 새로운 업데이트를 위한 트리
- `alternate` 속성을 이용해 이전과 새로운 트리를 비교하면서 업데이트를 최소화함

복습

1. **리액트의 재조정이란 무엇인가요?**

   리액트는 UI의 "청사진(설계도)"을 가지고 있고, 변경 사항이 생기면 이 청사진을 비교해서 필요한 부분만 업데이트

   ⇒ 실제 DOM을 직접 수정하는 게 아니라, 가상의 복사본을 만들어서 기존 UI와 비교(diffing)한 후 차이가 있는 부분만 바꿔주어 최소한의 DOM업데이트를 하는 것

2. **파이버 데이터 구조의 역할은 무엇인가요?**

   기존의 업데이트 방식은 한번에 일괄처리하는데 이렇게 하면 화면이 느려지거나 멈추는 등의 문제가 생길 수 있음 이 구조의 핵심은 ‘우선순위’ 기반 렌더링을 통해 성능 최적화 하는 방식

3. **왜 트리가 두 개 필요한가요?**

   사용자가 앱을 사용하는 동안, 기존 UI를 유지하면서 새로운 변경 사항을 준비

   ⇒ 즉, UI가 멈추지 않고 부드럽게 업데이트될 수 있도록 관리하는 게 핵심!

4. **애플리케이션이 업데이트되면 어떻게 되나요?**

   렌더링 단계에서 새로운 파이버트리를 만들고, 커밋 단계에서 실제 DOM을 업데이트
