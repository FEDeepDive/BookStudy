# 🎊 복습하기

## 1. 리액트의 재조정이란 무엇인가요?

### `보경`

이전의 돔 트리와 현재 돔 트리의 변경사항을 찾고, 이 변경사항을 일괄처리하여 실제 DOM에 반영하는 과정

### `미림`

재조정은 UI의 가상 표현의 변화를 감지하고 이를 호스트 환경에 반영하기 위해 조율하는 과정이다. 리액트는 파이버 재조정자를 사용해 우선순위가 높은 변경 사항부터 처리하여 사용자에게 높은 응답성을 제공한다.

### `정욱`

- 우리가 실제로 원하는 UI를 표현하는 가상 DOM이라는 자료구조를 이용하여 실제 DOM에 변경을 가하는 과정을 말함.
- 렌더링 단계와 커밋 단계로 이루어지며, 렌더링 단계가 올바르게 이루어지면 커밋 단계가 실행되어 최종적으로 원하는 형태의 갱신이 실제 DOM에 반영됨.

### `영은`

리액트는 UI의 "청사진(설계도)"을 가지고 있고, 변경 사항이 생기면 이 청사진을 비교해서 필요한 부분만 업데이트    
    ⇒ 실제 DOM을 직접 수정하는 게 아니라, 가상의 복사본을 만들어서 기존 UI와 비교(diffing)한 후 차이가 있는 부분만 바꿔주어 최소한의 DOM업데이트를 하는 것

## 2. 파이버 데이터 구조의 역할은 무엇인가요?

### `보경`

파이버 구조를 사용하면 각 작업에 우선순위를 설정할 수 있다. 또한, 업데이트 과정을 더 세분화 하여 우선순위가 높은 작업이 추가된다면 작업중인 업데이트를 중단할 수 있다.

### `미림`

파이버 데이터 구조는 리액트 엘리먼트에서 파생된 리액트 내부 데이터 구조로, 특정 시점의 컴포넌트의 상태를 나타낸다. 또한 렌더링 작업의 단위로써, 렌더링을 작은 단위로 분할하여 처리할 수 있게 한다.

### `정욱`

- 기존에 리액트 재조정에 사용되던 스택 기반 재조정자는 두 가지 약점을 가지고 있음.
    - 나중에 들어온 것이 항상 먼저 처리되기 때문에 UI 관점에서 덜 중요한 갱신이 더 중요한 갱신보다 먼저 처리될 수 있음.
        - 즉, 스택 기반 재조정에서는 갱신 간 우선순위가 존재하지 않음
    - 또한, 한 번 실행된 갱신이 중간에 중단될 수 없기 때문에 설령 우선순위가 있다고 하더라도 먼저 실행된 작업이 끝날 때까지 기다려야 함.
- 파이버는 컴포넌트 인스턴스와 그 상태를 표현하는 자료구조로, 재조정 과정에서 필요에 따라 갱신 및 재배치될 수 있음.

### `영은`

기존의 업데이트 방식은 한번에 일괄처리하는데 이렇게 하면 화면이 느려지거나 멈추는 등의 문제가 생길 수 있음 이 구조의 핵심은 ‘우선순위’ 기반 렌더링을 통해 성능 최적화 하는 방식

## 3. 왜 트리가 두 개 필요한가요?

### `보경`

하나의 트리는 화면에 보여주는 역할을 하고, 다른 트리에서 변경사항을 처리한다.

### `미림`

파이버 트리를 두 개 두는 더블 버퍼링 구조를 통해 오프 스크린 작업을 가능하게 한다. 이로써 화면 밖에서 UI를 준비하고 언제든지 UI를 폐기하거나 렌더링을 중단할 수 있게 된다.

### `정욱`

- 우선순위가 더 높은 새로운 갱신이 필요한 경우, 이를 버릴 수 있어야 하기 때문!
- 사용자가 현재 보고있는 화면을 망치지 않고 잠시 중단했다가 다시 시작할 수 있어야 하기 때문!

### `영은`

사용자가 앱을 사용하는 동안, 기존 UI를 유지하면서 새로운 변경 사항을 준비

⇒ 즉, UI가 멈추지 않고 부드럽게 업데이트될 수 있도록 관리하는 게 핵심!

## 4. 애플리케이션이 업데이트되면 어떻게 되나요?

### `보경`

변경사항이 다 적용되면, 이 트리를 화면에 보여주는 트리로 변경한 뒤 다른 트리에서 다시 변경사항을 적용함

### `미림`

애플리케이션 업데이트 시 재조정 과정이 발생한다. 업데이트가 필요한 컴포넌트를 호출해 변경 사항이 반영된 파이버 노드를 생성하고 새롭게 파이버 트리를 구성하여 이를 DOM에 삽입한다. 브라우저는 이렇게 변경 사항이 반영된 DOM을 토대로 화면을 다시 그린다.

### `정욱`

- 갱신이 발생하는 경우 렌더링 단계와 커밋 단계를 거쳐 새로운 상태의 UI를 만듦.
- 렌더링 단계에서는 특정 파이버 노드의 갱신 필요 여부를 설정하는 `beginWork`, 그러한 노드들에 갱신을 적용하고 이를 반영하는 실제 DOM 트리를 생성하는 `completeWork`라는 과정을 거침.
- 렌더링이 완료되면 실제 DOM에 해당 작업 사항들이 반영되고, 현재 활성화된 트리를 나타내는 `FiberRootNode`의 포인터를 작업용 트리를 가리키도록 전환함.
- 커밋 단계에서는 가상 DOM에 적용된 변경 사항을 실제 DOM에 반영하는 **변형**, 갱신된 노드의 새로운 레이아웃을 계산하는 **레이아웃** 과정을 거침.

### `영은`

렌더링 단계에서 새로운 파이버트리를 만들고, 커밋 단계에서 실제 DOM을 업데이트
