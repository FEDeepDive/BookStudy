# CHAPTER 4 재조정

## 📌4장의 목적

- `ReactDOM.createRoot(element).render()`의 동작 이해하기
- 재조정을 통한 실제 DOM 업데이트 프로세스 이해하기
- 현재 DOM 상태와 다음 DOM 상태를 동기화하는 과정 이해하기

## 📌재조정 이해하기

- UI의 이상적인 또는 “가상”적인 표현을 실제 호스트 환경에 반영하기 위해 조율하는 과정
    - ↳ 가상 DOM
    - 호스트 환경: 웹 브라우저나 iOS, 안드로이드, 셸 등
- 현재 가상 트리를 복제 ⇒ 새 트리에 업데이트 적용 ⇒ 새 트리를 호스트 환경에 반영

## 📌스택 재조정자

### 구조

- 스택에 렌더링이 필요한 컴포넌트를 순차적으로 push하고, 하나씩 pop하여 처리함
- 스택 기반 재조정 예시
    
    ```jsx
    function Counter() {
      const [count, setCount] = useState(0);
    
      return (
        <div>
          <ExpensiveComponent />
          <p>count: {count}</p>
          <button onClick={() => setCount(count + 1)}>increment</button>;
        </div>
      );
    }
    ```
    
    - 1️⃣ `button` 클릭 시 `Counter` 렌더링 트리거
    - 2️⃣ 스택에 `div`, `ExpensiveComponent`, `p`, `button` 순서대로 push
    - 3️⃣ 스택에서 `button`, `p`, `ExpensiveComponent`, `div` 순서대로 pop
        - 이 때 `ExpensiveComponent` 계산이 오래 걸려서 `Counter` 렌더링 자체가 지연됨
        - 변경된 부분은 `p` 뿐인데, 다른 작업이 완료될 때까지 기다리느라 업데이트가 지연됨
    - 4️⃣ 변경 사항을 모두 반영하고 작업이 완료되면, 이를 DOM에 반영함

### 문제점

- 덜 중요한 컴포넌트가 더 중요한 컴포넌트의 렌더링을 방해함
- 업데이트를 중단/취소할 수 없음 (⇒ 불필요한 업데이트가 먼저 수행될 때 이를 끊지 못함)
- ⇒ 사용자에게 상호작용 응답이 느리고, 끊기는 듯한 느낌을 줌

## 📌파이버 재조정자 개괄

### 사전 지식

DOM에 리액트 엘리먼트를 렌더링하기 위해서는…

```jsx
const root = ReactDOM.createRoot(document.getElementById('root'));
root.render(myComponent);
```

- DOM에 리액트 엘리먼트를 렌더링하기 위해서는 `root`를 생성해야 함
- 리액트 엘리먼트는 DOM에 바로 렌더링할 수 없고 `root`를 통해 렌더링해야 함

즉 리액트는 애플리케이션 최상단에 `root`를 두어, `root`로부터 시작해 하위 컴포넌트 트리를 구성한다. 후술할 더블 버퍼링 구조에서 `root`가 파이버 트리의 루트 노드(`FiberRootNode`)를 참조하고, 이를 통해 변경된 트리를 가리킬 수 있게 한다.

### 흐름

1. 각 리액트 엘리먼트를 파이버 노드로 대응해 **파이버 트리** 구성
    1. 파이버는 렌더링에 필요한 정보를 포함하는 객체이자, 조정 작업 단위임
    2. 파이버 트리는 파이버로 구성된 **단일 연결 리스트**임
2. `root`가 파이버 트리의 첫 파이버를 참조
3. 변경 사항 발생 시 현재 파이버 트리를 복제해 **작업용 파이버 트리를 생성**
4. 작업용 파이버 트리를 내려가며 업데이트가 필요한 노드 체크
5. 작업용 파이버 트리를 올라가며 변경사항 기록 (또는 DOM 요소 생성)
6. `root`가 작업용 트리의 첫 파이버를 참조 & effect 실행

이후 브라우저가 변경된 DOM을 토대로 화면을 다시 구성(리플로우-리페인팅)함

### 더블 버퍼링과 오프 스크린⭐

더블 버퍼링 구조가 오프 스크린 작업을 가능하게 함

- **더블 버퍼링**: 두 개의 버퍼를 일정한 간격으로 전환해 화면을 표시하는 기법
- **오프 스크린**: 화면 밖에서 UI의 새 상태를 계산하고 새 DOM 트리를 준비하는 것
    - ⇒ 실제 화면 밖에서 준비하므로, 준비하던 것을 폐기/중단-재개 가능
    - ⇒ 실제 DOM에 대한 불필요한 업데이트를 피할 수 있음

### 리액트의 타임 슬라이싱과 동시성 스케줄링⭐

브라우저의 자바스크립트 엔진은 **싱글 스레드**이다. 싱글 스레드에서는 모든 로직을 순차적으로 실행한다. 만약 계산이 오래 걸리는 작업을 수행한다면 UI 업데이트는 그만큼 지연되게 된다. 지연 시간이 1프레임보다 길어진다면 사용자는 마치 화면이 멈춘 것처럼 느낄 것이다.

리액트는 타임 슬라이싱 기법을 사용해 이러한 문제를 해결하고 있다. 타임 슬라이싱(Time Slicing)이란, 여러 작업을 짧은 시간 단위로 나누어 번갈아 실행하여 시스템의 응답성을 높이는 기법이다. 리액트는 **렌더링 작업을 작은 단위(chunk)로 분할**하여 수행하고, **일정 시간마다 실행을 메인 스레드에게 돌려주어**, 브라우저가 다른 중요한 작업(ex. 사용자 입력, 애니메이션, 네트워크 응답 등)을 처리할 수 있게 한다. 즉 렌더링을 중단하고 다시 재개한다.

타임 슬라이싱이 가능한 이유는 파이버 재조정자의 매커니즘 덕분이다. 기존 스택 재조정자는 재귀 호출 기반으로 재조정을 처리했기 때문에, 한 번 시작하면 중단이 불가능했다. 반면 파이버 재조정자는 렌더링 작업을 파이버 노드 단위로 구분하고, 이를 비동기로 실행(스택 재조정과 달리)하여 최대 실행 시간이 16ms가 넘지 않도록 제어한다. 또 **우선순위 큐**를 사용해 경우에 따라 작업을 중단하고 우선순위가 높은 작업을 먼저 수행한다.

정리하자면 리액트는 렌더링을 작게 나누고 점진적으로 수행하여 UI가 멈추지 않고 부드럽게 업데이트되도록 한다.

## 📌파이버 노드

### 개념

- **데이터 구조로서의 파이버**
    - 특정 시점에 존재하는 컴포넌트 트리를 나타내는 리액트의 내부 데이터 구조
    - 컴포넌트에 대한 정보(props, 상태, 하위 컴포넌트 등)를 담고 있는 구조체
    - 특정 컴포넌트가 렌더링되는 동안의 상태를 추적하는 객체
- **작업 단위로서의 파이버**
    - 컴포넌트의 렌더링을 수행하는 작업 단위 → 조정 과정에서 업데이트/재배치 됨
    - 파이버 트리의 구성 요소

### 구조

참고: [FiberNode()](https://github.com/facebook/react/blob/v16.12.0/packages/react-reconciler/src/ReactFiber.js#L255), [type Fiber](https://github.com/facebook/react/blob/9e3b772b8cabbd8cadc7522ebe3dde3279e79d9e/packages/react-reconciler/src/ReactInternalTypes.js#L67)

```tsx
type Fiber = {
  tag: WorkTag, // 파이버의 종류를 나타냄 (ex. HostComponent = 5)
  key: null | string,
  type: any, // 파이버가 나타내는 함수/클래스 컴포넌트 (즉 연결된 구현체)
  stateNode: any, // 호스트 컴포넌트: 연결된 DOM 요소 / 커스텀 컴포넌트: null
  
  // 단일 연결 리스트로 된 "트리" 구조를 이루기 위한 포인터
  return: Fiber | null, // 부모 파이버 (스택에서처럼 현재 작업 이후 돌아갈 파이버)
  child: Fiber | null, // 첫 번째 자식 파이버
  sibling: Fiber | null, // 형제 파이버

	memoizedState: any, // 현재 또는 마지막 렌더링에서 사용된 상태 값 / hook 리스트
	alternate: Fiber | null, // 더블 버퍼링 구조에서 pair가 되는 파이버
  //  ...
};
```

```
💡

모든 파이버는 결국 출력(렌더링 결과)을 가지지만, 실제로 출력되는 것은 호스트 컴포넌트이다. 커스텀 컴포넌트의 가장 끝단에는 호스트 컴포넌트가 있으며, 커스텀 컴포넌트는 이를 반환한다(`Fiber.stateNode`).

```

### 리액트 엘리먼트와 비교

[`createFiberFromElement()`](https://github.com/facebook/react/blob/v16.12.0/packages/react-reconciler/src/ReactFiber.js#L731)를 호출해 리액트 엘리먼트를 토대로 파이버를 생성함

- 파이버: 상태를 저장 / 수명이 긺 / 파이버 트리 구성 요소 & 렌더링 작업 단위
- 리액트 엘리먼트: 상태가 없음 / 임시적임 / 가상 DOM 구성 요소

## 📌파이버 재조정 과정

### 파이버 트리 구분

파이버 재조정 매커니즘은 두 개의 파이버 트리를 가진다. (참고로 [우선순위 큐도 두 개](https://github.com/facebook/react/blob/v18.2.0/packages/react-reconciler/src/ReactFiberClassUpdateQueue.new.js#L12-L15))

- `현재 트리(current tree)`: 현재 DOM 상태와 동일한 파이버 트리
- `작업용 트리(work-in-progress tree)`
    - 업데이트가 적용되고 실제 DOM에 반영되는 트리로, 업데이트가 필요할 때 현재 트리를 복제하여 만듦
    - 렌더링 단계에서 언제든지 폐기될 수 있으며, 커밋 단계 이후에 현재 트리가 됨

### 렌더링 단계

렌더링 단계는 화면 밖에서 **다음 UI를 준비하는 단계**로 **변경된 상태 값을 반영한 작업용 트리를 구축하는 과정**이다. 렌더링 단계는 `beginWork()`와 `completeWork()` 실행에 따라 진행된다.

- `beginWork()`
    - 루트부터 리프까지 트리를 따라 내려가면서(DFS로), 업데이트가 필요한 파이버 노드를 체크하는 작업
- `completeWork()`
    - 리프부터 루트까지 트리를 따라 올라가면서, 작업용 파이버 트리에 업데이트를 적용하고 실제 DOM 요소를 생성하는 작업
    - 리프 노드(항상 호스트 컴포넌트)에 대응되는 DOM 요소를 생성해 파이버 노드의 `stateNode` 프로퍼티에 담음 ⇒ 새 DOM 트리를 메모리에 구성함
- **💡 `beginWork()`와 `completeWork()`의 함수 시그니처**
    
    ```tsx
    // beginWork()와 completeWork()의 함수 시그니처는 동일함
    function beginWork(
      current: Fiber | null, // 현재 트리에서 순회중인 파이버(=workInProgress와 pair)
      workInProgress: Fiber, // 작업용 트리에서 순회중인 파이버(=current와 pair)
      renderLanes: Lanes, // 우선순위
    ): Fiber | null;
    ```
    
    - 루트부터 업데이트 컴포넌트까지는 리액트 엘리먼트 상으로 변경 사항이 없기 때문에, `current`를 재사용해 `workInProgress`로 설정한다(단, `workInProgress.return`은 수정해줘야 함).
    - 리액트 엘리먼트가 변경된 경우 해당 컴포넌트를 호출하여 변경된 상태를 반영한 파이버 노드를 생성하고 이를 `workInProgress`로 설정한다.

### 커밋 단계

커밋 단계는 변형 단계와 레이아웃 단계로 나뉘며, 이후 여러 효과(side effect)가 실행된다. 커밋 단계는 동기적으로, 즉 콜스택을 한 번도 비우지 않고 멈춤 없이 진행된다. 커밋 단계가 끝나고 콜스택이 비면 브라우저가 삽입된 DOM을 토대로 화면을 그릴 수 있게 된다.

- `변형 단계`: 작업용 트리에 적용된 변경 사항을 실제 DOM에 반영
- `레이아웃 단계`: DOM에서 업데이트된 노드의 새 레이아웃을 계산
- 💡**효과(side effect)**
    
    커밋 단계 이후 다양한 부수효과가 실행된다.
    
    - `useLayoutEffect()`: 브라우저 레이아웃 업데이트 시점에 개발자 개입이 가능
    - `useEffect()`: 브라우저 페인트 이후 개발자 개입이 가능

## 📌복습하기

- **1. 리액트의 재조정이란 무엇인가요?**
    
    재조정은 UI의 가상 표현의 변화를 감지하고 이를 호스트 환경에 반영하기 위해 조율하는 과정이다. 리액트는 파이버 재조정자를 사용해 우선순위가 높은 변경 사항부터 처리하여 사용자에게 높은 응답성을 제공한다.
    
- **2. 파이버 데이터 구조의 역할은 무엇인가요?**
    
    파이버 데이터 구조는 리액트 엘리먼트에서 파생된 리액트 내부 데이터 구조로, 특정 시점의 컴포넌트의 상태를 나타낸다. 또한 렌더링 작업의 단위로써, 렌더링을 작은 단위로 분할하여 처리할 수 있게 한다.
    
- **3. 왜 트리가 두 개 필요한가요?**
    
    파이버 트리를 두 개 두는 더블 버퍼링 구조를 통해 오프 스크린 작업을 가능하게 한다. 이로써 화면 밖에서 UI를 준비하고 언제든지 UI를 폐기하거나 렌더링을 중단할 수 있게 된다.
    
- **4. 애플리케이션이 업데이트되면 어떻게 되나요?**
    
    애플리케이션 업데이트 시 재조정 과정이 발생한다. 업데이트가 필요한 컴포넌트를 호출해 변경 사항이 반영된 파이버 노드를 생성하고 새롭게 파이버 트리를 구성하여 이를 DOM에 삽입한다. 브라우저는 이렇게 변경 사항이 반영된 DOM을 토대로 화면을 다시 그린다.

- 기존 스택 재조정자 설명할 때 스택을 그림으로 안 그리고 문자로 한 땀 한 땀 만든 게 웃기다 ㅋㅋ 왜 그림으로 안했지 ㅋㅋㅋ
- 책이 구체적으로 설명하고 있어서인지 용어를 딱 정리하지 않고 두루뭉실하게 설명해서인지 책만 보고는 이해하기 다소 난해했다. 내부 구현체라 언제든지 바뀔 수 있고, 개념을 정확히 아는 것보다 리액트 사용할 때 도움을 받으려고 설명해주는 거라 그런지 일부러 자세히 말 안 한 듯? 인터넷에서 자세히 찾아보고 느낀 점은 '내부 구현이라 역시 깊게 알 필요 없다'는 것이었지만... 이렇게 찾아보지 않으면 계속 의문이 남았을 것 같음. 어쩔 수 없는 듯
- ‘인스턴스’라는 말을 자꾸 써서 헷갈렸다(ex. “파이버는 컴포넌트 인스턴스와 그 상태를 표현한다”, “[파이버의 각 인스턴스](https://github.com/facebook/react/blob/v16.12.0/packages/react-reconciler/src/ReactFiber.js#L255)”). 파이버를 ‘컴포넌트의 인스턴스’라고 표현하는 건, 파이버가 컴포넌트로부터 파생된 구조체라서인가?
    - 책에서는 파이버를 설명하면서 ‘인스턴스’라는 표현을 사용하고 있다. 이는 클래스 컴포넌트가 생성하는 인스턴스를 의미하는 게 아니라(함수 컴포넌트는 인스턴스도 없다), 컴포넌트의 존재를 의미하는 표현일 가능성이 크다. 즉 파이버는 “해당 컴포넌트가 렌더링되는 동안의 상태를 추적하는 객체”라고 해석하는 게 맞다. (by ChatGPT)
- `beginWork()`와 `completeWork()`를 통해 트리를 깊이 우선으로 순차적으로 탐색하는 것과,  lane(우선순위) 순서대로 렌더링 하는 게 서로 상충되는 거 같은데 어떻게 이 시스템이 가능한 거지?
    - 트리 **순회는 DFS로** 하지만 렌더링 작업의 **실행 순서는 lane을 기반으로 결정**한다. `beginWork()` 단계에서 lane이 낮은 작업이면 건너뛰거나 나중으로 미룰 수 있다. 즉 **높은 우선순위 작업만 모아서 일괄적으로 처리**할 수 있다. 나중으로 미룬 작업들은 렌더링 단계가 끝난 후에 다시 확인하며, 만약 남아 있는 작업이 있으면 work loop를 시작해 처리한다.
- 스택 데이터 구조처럼 파이버라는 데이터 구조가 있다는 게 신기. 근데 스택처럼 원래 있는 구조인지, 아니면 리액트가 내부적으로 구현한 구조체인지 명확하게 말해주면 더 좋았을 것 같음. 또 리액트 엘리먼트가 파이버를 낳는 것처럼 말하고 있는데, 리액트 엘리먼트를 토대로 파이버를 생성하는 거니까 파생 또는 대응되는 관계라고 표현하는 게 좋아 보임. 이런 류의 애매하고 아리까리한 설명이 넘 많았다 ㅋㅋ
