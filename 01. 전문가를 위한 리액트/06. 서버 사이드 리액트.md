## 1. 리액트 애플리케이션에서 서버 사이드 렌더링을 사용할 때 유리한 주요 장점은 무엇인가요?

### `미림`

- 리액트 애플리케이션에서 서버 사이드 렌더링을 사용하면 검색 엔진 최적화(SEO) 개선과 정적 콘텐츠 로드 시간 단축, 보안 강화 등의 이점을 얻을 수 있습니다.

### `정욱`

- First Meaningful Paint 지표가 줄어들어 콘텐츠를 볼 수 있는 시간이 빨라짐
    - (#) [이 글](https://developer.chrome.com/docs/lighthouse/performance/first-meaningful-paint?hl=ko)에 따르면 FCP와 FMP는 동일한 경우가 많다고 하네요! 보통 FCP라는 지표를 더 많이 봐서 뭐가 다른가 했습니당
- 웹 페이지의 접근성, SEO, 보안을 향상시킬 수 있음

### `영은`

서버 사이드 렌더링은 초기 HTML을 서버에서 생성해 전달하므로, 자바스크립트를 실행하지 못하는 환경에서도 콘텐츠 접근이 가능해 SEO와 초기 로딩 성능을 개선하는 데 효과적이다.


## 2. 리액트에서 하이드레이션은 어떻게 작동하며 왜 중요한가요?

### `미림`

클라이언트는 HTML의 body 끝에 있는 script 태그를 만나면 하이드레이션을 시작합니다. 자바스크립트를 다운로드, 파싱, 실행하여 이벤트리스너를 비롯한 동적 기능을 DOM 요소에 추가해 상호작용할 수 있게 만듭니다. 이 과정은 클라이언트가 정적 콘텐츠를 렌더링하는 동안 일어납니다.

하이드레이션을 통해 기존 SSR보다 빠르게 페이지를 로드할 수 있습니다.

### `정욱`

- 하이드레이션은 서버에서 렌더링된 초기 정적 HTML이 다운로드되면 발생함
- 정적 HTML을 렌더링하는 동안 애플리케이션 코드가 포함된 번들을 로드함
- 번들이 로드되면 이벤트 리스너 등 상호작용 동작을 위한 기능을 DOM 요소에 추가한 후 페이지를 다시 렌더링함
- 상호작용 지원이 부족한 정적 HTML에 동적 기능을 활성화해주기 위해서는 하이드레이션이 필수적임

### `영은`

하이드레이션은 서버에서 미리 렌더링된 HTML에 클라이언트에서 자바스크립트를 연결하여 상호작용을 가능하게 만드는 과정
빨

## 3. 재개 가능성이란 무엇인가요? 하이드레이션보다 좋다고 주장하는 근거는 무엇인가요?

### `미림`

하이드레이션을 사용하면 스크립트를 실행한 후 DOM에 적용하고 리렌더링하는 과정이 필요합니다. 재개 가능성은 하이드레이션의 불필요한 과정을 생략하기 위한 대안으로, 초기 HTML을 전송할 때 자바스크립도 함께 직렬화하여 전송하는 방식입니다. 이렇게 하면 클라이언트는 이를 역직렬화하여 TTI를 줄일 수 있습니다. 하지만 구현이 복잡하고 비용이 커 실질적으로 구현할 만한 가치가 있는지는 논란이 되고 있습니다.

### `정욱`

- 재개 가능성이란 초기 정적 마크업과 함께 모든 상호작용 동작이 직렬화되어 한 번에 전송되는 것
- 이벤트 리스너를 연결하고 리렌더링하는 과정이 필요없어 건너뛸 수 있으므로 TTI가 짧아져 사용자 경험이 향상될 수 있다고 함

### `영은`

재개 가능성은 서버가 앱 상태를 직렬화해 보내고 클라이언트가 이를 이어받아 즉시 상호작용을 가능하게 하는 방식으로, 하이드레이션처럼 다시 렌더링하지 않아 초기 반응 속도를 크게 개선할 수 있다는 점 때문에 좋다고 한다. 하지만, 구현이 복잡함.

## 4. 클라이언트 사이드 렌더링의 주요 장점과 약점은 무엇인가요?

### `미림`

클라이언트 사이드 렌더링은 자바스크립트를 통해 동적으로 콘텐츠를 렌더링해 부드러운 상호작용 경험을 제공합니다. 그러나 빈 HTML과 과도한 자바스크립트 의존성으로 인해 검색 엔진 최적화(SEO)에 불리합니다. 또 자바스크립트 다운로드, 파싱, 실행 시간만큼 렌더링이 지연되며 이로 인해 느린 환경에서 접근성이 낮습니다. 마지막으로 CSRF 공격에 취약합니다.

### `정욱`

- CSR 사용 시 서버에서 처음에 전달받는 HTML은 거의 비어있어 검색 엔진 결과를 위해 필요한 데이터가 없으므로 SEO에 불리함
- 또한 페이지를 읽은 후 전체 사이트의 동작을 위한 자바스크립트를 다시 요청해야 하기 때문에 네트워크 폭포가 일어나는 등 성능 문제가 존재함
- 그러나 CSR은 사용자에게 더 빠른 상호작용을 제공할 수 있으며, 새로고침 없이 네이티브 애플리케이션과 비슷한 경험을 줄 수 있음

### `영은`

클라이언트 사이드 렌더링은 개발이 간편하고 사용자 중심의 동적인 인터페이스 구현에 유리하지만, 초기 HTML이 없어 SEO가 취약하고, 자바스크립트 비활성 환경에서는 콘텐츠 접근이 불가능하다는 한계가 있다.

## 5. 리액트에서 renderToReadableStream과 renderToPipeableStream API의 주요 차이점은 무엇인가요?

### `미림`

두 API 모두 리액트에서 서버 렌더링을 위해 제공하는 API로 스트리밍 및 Suspense를 지원합니다. renderToReadableStream는 브라우저 네이티브로 웹 스트림을 이용하는 프로미스 기반인 반면, renderToPipeableStream는 서버 네이티브로 Node.js 스트림을 이용하는 이벤트 기반 API입니다.

### `정욱`

- `renderToPipeableStream`은 Node.js 스트림을 사용하지만 `renderToPipeableStream`은 브라우저 스트림을 사용한다는 차이점이 있음

### `영은`

renderToPipeableStream은 Node.js의 스트림을 활용해 빠른 SSR을 지원하며, renderToReadableStream은 WHATWG 표준을 따르는 스트림 방식으로 Edge와 브라우저 환경에서도 SSR이 가능하다는 점에서 플랫폼 대응 방식이 다르다.
