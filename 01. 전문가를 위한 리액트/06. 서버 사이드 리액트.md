## 6.1 클라이언트 사이드 렌더링 한계
클라이언트 사이드 렌더링에는 몇 가지 한계가 있어 점점 더 많은 관심사를 서버 사이드로 이전하게 되었음

### 6.1.1 검색 엔진 최적화(SEO)
- 일부 검색 엔진의 크롤러는 자바스크립트를 실행하지 않음
- 자바스크립트를 실행하는 크롤러도 그 동작이 올바르다고 믿을 수 없음
- 때문에 콘텐츠를 올바르게 색인할 수 없음
  - 리액트와 같은 라이브러리로 구축된 CSR 애플리케이션은 거의 비어있는 HTML을 전송하고 이 HTML 파일이 자바스크립트를 읽어들여 콘텐츠가 동적으로 렌더링됨
  - 때문에 사용자에게 필요한 파일을 전부 다운로드하지 않고 페이지를 읽어들인 후 다시 요청하는 "네트워크 폭포" 현상이 발생함

### 6.1.2 성능
- 콘텐츠 렌더링 전 자바스크립트를 다운로드하고 구문 분석 및 실행이 이루어져야 하는 CSR
- 사용자 참여율과 이탈률에 직접적인 영향을 미치는 인터랙티브 가능 시간(Time To Interactive, TTI)이 오래 걸리면 검색 엔진의 페이지 순위에 부정적 영향을 미칠 수 있음
- CPU 가용성이 낮은 저전력 기기에서 CSR을 사용하면 처리 능력이 부족해 사용자 경험이 나빠질 수 있음
- 많은 콘텐츠를 성능이 뛰어나고 접근성이 좋은 방식으로 제공하고 싶을 때는 서버 사이드 렌더링(Server Side Rendering) 또는 정적 사이트 생성(Static Site Generation)을 더 신뢰할 수 있음
- 서버에서 자바스크립트를 먼저 실행하여 최소한의 데이터나 마크업을 보낼 수 있다면 저전력 기기가 많은 작업을 수행하지 않아도 되므로 사용자 환경이 개선됨
  - 기본 콘텐츠와 기능을 모든 브라우저에 보이도록 제공하되 고급 기능을 선택 가능한 개선 사항으로 여기는 점진적 개선(Progressive Enhancement)
  - 전체 사용자 경험이 오직 클라이언트 사이드 자바스크립트로만 구성되는 것은 웹의 설계 의도가 아님

### 보안
- CSR은 애플리케이션의 모든 코드가 클라이언트의 브라우저로 다운로드되기 때문에 크로스 사이트 요청 위조(Cross-Site Request Forgery, CSRF) 같은 공격에 취약함
- 웹사이트를 사용자에게 제공하는 신뢰할 수 있는 서버를 제어할 수 있다면 클라이언트와 적절한 CSRF 방지 토큰을 가지고 통신하여 CSRF를 방어할 수 있음
- 어차피 서버를 쓸 것이라면 SSR을 하지 않을 이유가 없음

## 6.2 서버 렌더링의 부상
- 서버 렌더링은 다음과 같은 장점이 있음
  - 최초 의미 있는 페인트(First Meaningful Paint)가 완성되는 시간이 빨라짐
  - 웹 애플리케이션의 접근성, SEO 및 보안을 개선할 수 있음
- 그러나 서버에서 렌더링된 HTML은 정적이기 때문에 상호 작용 지원이 부족하며, 필요한 자바스크립트를 정적 HTML에게 공급하는 하이드레이션(Hydration) 과정이 필요함

## 6.3 하이드레이션
- 서버에서 렌더링된 리액트 애플리케이션을 다운로드한 후, 정적 HTML을 렌더링하는 동안 애플리케이션 코드가 포함된 자바스크립트 번들을 다운로드하고 파싱함
- 번들이 모두 준비 완료되면 이벤트 리스너와 같은 동적 기능을 DOM 요소에 추가함
- 하이드레이션 과정이 완료되면 애플리케이션이 완전히 상호작용 가능하게 변함
- 일부에서는 하이드레이션이 필요 이상으로 느리며 재개 가능성(Resumability)를 더 나은 대안으로 꼽기도
  - (#) 이를 강하게 말하는 프레임워크로는 [Qwik](https://qwik.dev/docs/concepts/resumable/)이 있습니다!

## 6.4 서버 렌더링 작성
- 클라이언트 전용 애플리케이션이 있을 때 서버 렌더링을 추가하기 위해서는 서버 렌더링 프레임워크를 사용하는 것이 비교적 간단하나, 수동으로 추가할 수도 있음
- 서버에서 컴포넌트를 렌더링하여 HTML 문자열을 생성한 후 클라이언트로 전송되는 응답에 삽입하면 해당 페이지 소스에 실제 마크업이 포함되어 있음을 알 수 있음
- 해당 페이지 소스 파일 끝에는 클라이언트 번들을 로드하는 `<script>` 태그가 포함되며, 이 때 하이드레이션이 발생함

## 6.5 리액트의 서버 렌더링 API
- `renderToString`은 서버에서 리액트 컴포넌트를 HTML 문자열로 렌더링할 때 사용함
  - 동기적으로 동작하며 완전히 렌더링된 HTML 문자열을 반환
  - 성능, SEO, 접근성 개선을 위해 서버에서 렌더링이 필요할 때 주로 사용함
  - 리액트 요소 트리를 탐색하고 실제 DOM 요소에 해당하는 문자열 표현으로 변환
  - 동기적으로 동작하기 때문에 실행이 중단되거나 일시적으로 중지할 수 없음
- `renderToPipeableStream`은 대규모 리액트 애플리케이션을 Node.js 스트림에 렌더링할 때 사용함
  - **파이프**할 수 있는 **스트림**을 반환함
    - (#) 파이프와 스트림에 대해서는 따로 좀 더 자세하게 다룰 필요가 있을 듯! CS 공부할 때 이야기했었던가요?
  - 비동기 데이터 fetching을 더 잘 처리해주는 Suspense를 완벽히 지원함
  - HTML 덩어리를 비동기적으로 전송할 수 있어 네트워크 지연 없이 점진적인 데이터 전달이 가능하며 이 덕분에 첫 번째 바이트 시간(Time To First Byte)이 줄어듦
  - Node.js(# 뿐만 아니라 사실 모든) **스트림**은 출발지에서 목적지로 흐르는 데이터의 흐름을 나타냄
    - 메모리를 효율적으로 처리할 수 있는 확장 가능하고 강력한 추상화 기능을 제공!
  - 페이지가 렌더링되기 전에 HTML을 클라이언트에 전송하는 "스트리밍" 능력을 통해 성능 향상 및 사용자 경험 개선이 가능함
  - HTML이 렌더링되는 방식을 더 세밀하고 "유연하게" 제어할 수 있음
- `renderToReadableStream`은 Node.js 대신 브라우저 스트림에 렌더링할 때 사용함

## 6.6 직접 구현하지 마세요
- 서버 렌더링을 처음부터 직접 구현하려면 비효율적일 뿐만 아니라 다양한 문제를 겪을 수 있음
  - 서버 렌더링을 구현하려면 비동기 데이터 fetching, 코드 분할, 다량한 리액트 수명 주기 이벤트 관리 등 여러 동작과 다양한 엣지 케이스를 해결해야 함
  - 한 클라이언트의 민감한 데이터가 실수로 다른 클라이언트로 유출되지 않도록 하는 등의 보안 문제도 있음
  - 프레임워크가 지원하는 수많은 성능 최적화를 직접 하려면 까다로움
  - 기본 서버 렌더링 환경 걱정보다 애플리케이션 기능 구현에 집중할 수 있는 환경이어야 생산성 향상과 개발자 경험이 개선됨
  - 이미 검증된 모범 사례가 많이 적용되어있는 프레임워크를 사용하면 탄탄한 기반에서 애플리케이션을 작성할 수 있음

## 6.8 복습하기
1. 리액트 애플리케이션에서 서버 사이드 렌더링을 사용할 때 유리한 주요 장점은 무엇인가요?
- First Meaningful Paint 지표가 줄어들어 콘텐츠를 볼 수 있는 시간이 빨라짐
  - (#) [이 글](https://developer.chrome.com/docs/lighthouse/performance/first-meaningful-paint?hl=ko)에 따르면 FCP와 FMP는 동일한 경우가 많다고 하네요! 보통 FCP라는 지표를 더 많이 봐서 뭐가 다른가 했습니당
- 웹 페이지의 접근성, SEO, 보안을 향상시킬 수 있음

2. 리액트에서 하이드레이션은 어떻게 작동하며 왜 중요한가요?
- 하이드레이션은 서버에서 렌더링된 초기 정적 HTML이 다운로드되면 발생함
- 정적 HTML을 렌더링하는 동안 애플리케이션 코드가 포함된 번들을 로드함
- 번들이 로드되면 이벤트 리스너 등 상호작용 동작을 위한 기능을 DOM 요소에 추가한 후 페이지를 다시 렌더링함
- 상호작용 지원이 부족한 정적 HTML에 동적 기능을 활성화해주기 위해서는 하이드레이션이 필수적임

3. 재개 가능성이란 무엇인가요? 하이드레이션보다 좋다고 주장하는 근거는 무엇인가요?
- 재개 가능성이란 초기 정적 마크업과 함께 모든 상호작용 동작이 직렬화되어 한 번에 전송되는 것
- 이벤트 리스너를 연결하고 리렌더링하는 과정이 필요없어 건너뛸 수 있으므로 TTI가 짧아져 사용자 경험이 향상될 수 있다고 함

4. 클라이언트 사이드 렌더링의 주요 장점과 약점은 무엇인가요?
- CSR 사용 시 서버에서 처음에 전달받는 HTML은 거의 비어있어 검색 엔진 결과를 위해 필요한 데이터가 없으므로 SEO에 불리함
- 또한 페이지를 읽은 후 전체 사이트의 동작을 위한 자바스크립트를 다시 요청해야 하기 때문에 네트워크 폭포가 일어나는 등 성능 문제가 존재함
- 그러나 CSR은 사용자에게 더 빠른 상호작용을 제공할 수 있으며, 새로고침 없이 네이티브 애플리케이션과 비슷한 경험을 줄 수 있음

5. 리액트에서 `renderToReadableStream`과 `renderToPipeableStream` API의 주요 차이점은 무엇인가요?
- `renderToPipeableStream`은 Node.js 스트림을 사용하지만 `renderToPipeableStream`은 브라우저 스트림을 사용한다는 차이점이 있음
