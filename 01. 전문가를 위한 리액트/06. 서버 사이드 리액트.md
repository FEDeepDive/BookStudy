## 📌CSR의 한계

### **검색 엔진 최적화(SEO) 지원 부족**

- 빈 HTML 문서
- 검색 엔진 크롤러는 기본적으로 자바스크립트를 실행하지 않음
- 설령 실행한다 하더라도 예상대로 실행되지 않을 수 있고, 무엇이 어디까지 수집되는지 알 수 없음

### **렌더링 지연**

- 자바스크립트 다운로드 및 파싱까지 완료해야 렌더링을 시작함 (⇒ TTI 증가 ⇒ SEO에 부정적)
    
    ```
    💡
    
    브라우저가 다운로드, 파싱, 실행해야 하는 자바스크립트 때문에 초기 페이지 로드가 차단되는 현상을 **네트워크 폭포(Network Waterfall) 현상**이라고 함
    
    ```
    
- 이 문제는 느린 네트워크나 낮은 성능 기기에서 더욱 심화됨 (=접근성↓)
- 리액트는 기본적으로 DOM 전체를 제어하므로 애플리케이션은 리액트 없이 UI를 그릴 수 없음 ⇒ 리액트와 리액트DOM을 전부 읽을 때까지 기다려야 함

### **보안**

- 애플리케이션의 코드가 클라이언트의 브라우저로 다운로드되므로 **CSRF**(Cross-Site Request Forgery, 크로스 사이트 요청 위조) 공격에 취약함
- 서버-클라이언트 간 토큰 전송 및 검증을 통해 CSRF 방어가 가능하지만, 서버를 제어할 수 있는 상황에서 SSR 안 쓸 이유가 없음

## 📌SSR의 장점

- 검색 엔진 크롤러가 애플리케이션 수집할 때 HTML이 완전히 렌더링되어 있음 ⇒ **검색 엔진 최적화(SEO)에 유리**
- 자바스크립트 다운로드 전에 정적인 페이지를 먼저 제공 ⇒ **최초 의미 있는 페인트 시간 단축**
- 느린 환경에서 자바스크립트 다운로드를 기다리는 동안 페이지 로드 가능 ⇒ **접근성 개선**
- **보안 향상**

## 📌하이드레이션

서버에서 렌더링한 HTML은 정적이므로 자바스크립트를 적용시키는 과정이 필요하다. 이를 하이드레이션이라고 한다.

리액트 애플리케이션에서 하이드레이션은 초기 HTML이 다운로드된 후 발생한다. 브라우저는 HTML을 렌더링하는 동안 자바스크립트 번들을 다운로드, 파싱, 실행해 이벤트 리스너를 비롯한 동적 기능을 DOM 요소에 추가한다. 이 동작은 `react-dom` 패키지의 `hydrateRoot` 함수를 통해 수행된다.

```
💡

하이드레이션 과정은 자바스크립트 번들 다운로드 및 DOM에 추가, 리렌더링 등 많은 작업을 필요로 한다. 이러한 방식은 콘텐츠가 사용자에게 표시되는 시점과 실제로 인터랙션이 가능한 시점의 차이를 만들 수 있다. 

재개 가능성(Resumability)은 하이드레이션 대안으로 등장한 개념이다. 재개 가능성을 활용하면 전체 애플리케이션이 서버에서 렌더링되어 브라우저로 스트리밍된다. 초기 마크업과 함께 모든 동적인 동작을 직렬화해 클라이언트로 전송하면, 클라이언트는 동적인 동작을 DOM에 연결하고 리렌더링할 필요 없이 서버가 제공한 내용을 역직렬화해 TTI를 줄일 수 있다.

그러나 구현이 복잡하고 장점보다 비용이 더 커서 실질적인 구현 가치는 작다.

```

## 📌리액트의 서버 API

### `renderToString()`

- 개념
    - 서버에서 **React 트리 전체를 HTML 문자열로 변환**하여 반환하는 함수
    - 서버는 반환한 HTML을 클라이언트에 응답으로 보냄
- 예시 코드
    
    ```jsx
    import { renderToString } from 'react-dom/server';
    
    // 라우트 핸들러 구문은 백엔드 프레임워크에 따라 다릅니다
    app.use('/', (request, response) => {
      const html = renderToString(<App />);
      response.send(html);
    });
    ```
    
- 단점
    - 동기식 동작 ⇒ 실행되는 동안 이벤트 루프 차단 & 서버 응답 시간 ↓
    - 동기식 동작 ⇒ 서버-클라이언트 1:N 관계에서 여러 클라이언트가 대기해야 함
    - HTML 문자열 전체를 생성해야 함 ⇒ 대규모 애플리케이션의 경우 메모리 사용량 ↑
    - 스트리밍 지원 부족
    - Suspense 등 데이터 대기 지원 부족

### `renderToPipeableStream()`

- 개념
    - React 트리를 HTML로 **파이프 가능한 `Node.js` 스트림에 렌더링**하는 함수
    - `renderToString()`과 유사하지만 HTML 문자열 대신 **Node.js 스트림을 반환**하고 **파이프**로 연결해 청크 단위로 **점진적으로 처리**하는 것이 가능함
        
        ```
        💡
        
        Node.js는 스트림과 스트림 간 파이프 기능을 지원하여 데이터 처리 프로세스를 간소화하고 메모리 사용량을 줄인다. 또 쓰기 스트림이 읽기 스트림보다 느려서 버퍼 뒤에 써야 할 데이터가 쌓이는 문제, 즉 백프레셔 처리도 지원한다.
        
        이러한 Node.js 스트림을 통해 메모리를 효율적으로 처리하고 추상화할 수 있다.
        
        ```
        
- 예시 코드
    
    ```jsx
    import { renderToPipeableStream } from 'react-dom/server';
    
    // 라우트 핸들러 구문은 백엔드 프레임워크에 따라 다릅니다
    app.use('/', (request, response) => {
      const { pipe, abort } = renderToPipeableStream(<App />, {
        bootstrapScripts: ['/main.js'],
        // 초기 셸이 렌더링된 직후 실행되는 콜백
        onShellReady() {
          response.setHeader('content-type', 'text/html');
          pipe(response); // 파이프를 통해 스트리밍
        }
      });
    });
    ```
    
- 특징
    - 스트리밍 및 파이프 지원 ⇒ 메모리 효율성
    - HTML 렌더링 파이프라인을 세밀하게 조정 가능
    - 이벤트 기반
    - 서버 네이티브
    - Suspense 지원

### `renderToReadableStream()`

- 개념
    - React 트리를 HTML로 **웹 스트림에 렌더링**하는 함수
- 예시 코드
    
    ```jsx
    import { renderToReadableStream } from 'react-dom/server';
    
    async function handler(request) {
      const stream = await renderToReadableStream(<App />, {
        bootstrapScripts: ['/main.js']
      });
      return new Response(stream, {
        headers: { 'content-type': 'text/html' },
      });
    }
    ```
    
- 특징
    - 스트리밍 지원
    - 프로미스 기반
    - 브라우저 네이티브
    - Suspense 지원

## 📌SSR을 지원하는 프레임워크의 이점

- 서드 파티 라이브러리와 호환성 (리액트 서버 API는 호환성이 낮음)
- 에지 케이스, 추상화, 보안 처리, 성능 최적화 등 기본 제공 및 자동 적용
- 개발자 경험, 생산성 증가
- 모범 사례와 코딩 규칙 적용으로 탄탄한 애플리케이션 작성 가능

## 📌서버에서 Suspense 지원 동작 원리

리액트는 “피즈(Fizz)”라는 서버 렌더러 아키텍처를 통해, 브라우저가 리액트 번들을 다운로드하지 않아도 서버에서 Suspense 구조를 반영한 HTML 스트리밍을 지원한다. 서버에서 애플리케이션을 HTML로 변환할 때 HTML 내부에 Suspense를 위한 스크립트를 인라인으로 집어 넣어 이를 가능하게 한다.

서버는 폴백과 자식 컴포넌트를 분리하여 Suspense 컴포넌트를 처리한다. HTML 상에서 폴백을 특수한 형식의 주석으로 감싸 Suspense 경계임을 나타내고, 나중에 자식 컴포넌트가 준비되었을 때 DOM을 조작하여 주석을 통해 해당 경계를 찾아낸다. 서버는 자식 컴포넌트에 해당하는 HTML 청크를 생성해 스트리밍하고, 폴백 위치에 자식 컴포넌트를 삽입한다.

자세한 내부 구현은 [ReactDOMFizzInstructionSetShared](https://github.com/facebook/react/blob/main/packages/react-dom-bindings/src/server/fizz-instruction-set/ReactDOMFizzInstructionSetShared.js#L48)에서 확인할 수 있다.

## 📌복습하기

- **1. 리액트 애플리케이션에서 서버 사이드 렌더링을 사용할 때 유리한 주요 장점은 무엇인가요?**
    
    리액트 애플리케이션에서 서버 사이드 렌더링을 사용하면 검색 엔진 최적화(SEO) 개선과 정적 콘텐츠 로드 시간 단축, 보안 강화 등의 이점을 얻을 수 있습니다.
    
- **2. 리액트에서 하이드레이션은 어떻게 작동하며 왜 중요한가요?**
    
    클라이언트는 HTML의 body 끝에 있는 script 태그를 만나면 하이드레이션을 시작합니다. 자바스크립트를 다운로드, 파싱, 실행하여 이벤트리스너를 비롯한 동적 기능을 DOM 요소에 추가해 상호작용할 수 있게 만듭니다. 이 과정은 클라이언트가 정적 콘텐츠를 렌더링하는 동안 일어납니다.
    
    하이드레이션을 통해 기존 SSR보다 빠르게 페이지를 로드할 수 있습니다.
    
- **3. 재개 가능성이란 무엇인가요? 하이드레이션보다 좋다고 주장하는 근거는 무엇인가요?**
    
    하이드레이션을 사용하면 스크립트를 실행한 후 DOM에 적용하고 리렌더링하는 과정이 필요합니다. 재개 가능성은 하이드레이션의 불필요한 과정을 생략하기 위한 대안으로, 초기 HTML을 전송할 때 자바스크립도 함께 직렬화하여 전송하는 방식입니다. 이렇게 하면 클라이언트는 이를 역직렬화하여 TTI를 줄일 수 있습니다. 하지만 구현이 복잡하고 비용이 커 실질적으로 구현할 만한 가치가 있는지는 논란이 되고 있습니다.
    
- **4. 클라이언트 사이드 렌더링의 주요 장점과 약점은 무엇인가요?**
    
    클라이언트 사이드 렌더링은 자바스크립트를 통해 동적으로 콘텐츠를 렌더링해 부드러운 상호작용 경험을 제공합니다. 그러나 빈 HTML과 과도한 자바스크립트 의존성으로 인해 검색 엔진 최적화(SEO)에 불리합니다. 또 자바스크립트 다운로드, 파싱, 실행 시간만큼 렌더링이 지연되며 이로 인해 느린 환경에서 접근성이 낮습니다. 마지막으로 CSRF 공격에 취약합니다.
    
- **5. 리액트에서 `renderToReadableStream`과 `renderToPipeableStream` API의 주요 차이점은 무엇인가요?**
    
    두 API 모두 리액트에서 서버 렌더링을 위해 제공하는 API로 스트리밍 및 Suspense를 지원합니다. `renderToReadableStream`는 브라우저 네이티브로 웹 스트림을 이용하는 프로미스 기반인 반면, `renderToPipeableStream`는 서버 네이티브로 Node.js 스트림을 이용하는 이벤트 기반 API입니다.
