## 2.1 자바스크립트 XML?
- JSX란 자바스크립트 코드 내에서 HTML과 유사한 코드를 작성할 수 있게 하는 구문 확장자(syntax extension)
  - 확장자? 뭔가 이 문맥에 쓰이기에는 번역이 익숙하지 않은 것 같다는 생각이 듦
  - 원래 많이 보던 용법은 "파일 확장자", "확장 프로그램" 등이 있는 것 같은데, 예전부터 봐온 전자의 경우가 요즘엔 더 왜 그런 이름이 붙었는지 의문이 가시지 않는 듯
  - 확장자는 표현보다는 "확장 문법"이라고 하는 게 개인적으로 좀 더 와닿음
- 컴파일 과정을 거쳐 일반 자바스크립트 코드로 변환됨
- 중괄호(`{}`)를 사용해 HTML과 유사한 코드 내에 자바스크립트 표현식을 삽입
  - JSX 시절 이전에 사용하던 템플릿 엔진([Handlebars](https://handlebarsjs.com/), [Mustache](https://mustache.github.io/))들과 JSX가 다른 점이 무엇일지 책에서 다룰지 궁금함
- 속성을 `camelCase`로 작성해야 하며 JSX 요소나 컴포넌트는 첫 문자가 대문자여야 함
  - ??? 컴포넌트는 이해가 가는데 요소는 소문자여도 되지 않나? [공식 문서](https://ko.react.dev/reference/react/createElement)에서 볼 수 있듯, 기본 HTML 요소로 변환되는 것들은 소문자여도 되지 않나? 기본 HTML 요소로 변환되는 것들은 JSX 요소로 안 쳐주나?
- (책에서는 다루지 않지만) PHP를 이용해 HTML과 유사한 코드를 작성할 수 있게 해주는 [XHP](https://github.com/phplang/xhp)에서 아이디어가 [발전되었다고 함](https://taegon.kim/archives/5097)(번역가님 블로그 ㅎ,ㅎ)

## 2.2 JSX의 장점
1. 더 쉬운 읽기 및 쓰기
2. 향상된 보안
  - 템플릿 엔진과의 차이점을 여기서 잠깐이나 짚는 것 같음!
  - 입력값을 그대로 사용하는 것이 아니라, 소독(sanitization)하여 사용하기 때문에 더 안전함
  - 템플릿 엔진들도 HTML 태그 정도는 제거/변환해주지만 자칫하다 [XSS 공격에 노출될 수도 있음](https://security.snyk.io/vuln/npm:handlebars:20151207)
3. 강력한 타이핑
4. 컴포넌트 기반 아키텍처
  - 음... JSX를 안 써도 React 자체가 컴포넌트 기반 아키텍처를 권장하는데 장점이라고 할 수 있을지는?
  - 컴포넌트 기반 아키텍처를 권장하는 부분보다는 개인적으로 "선언형" 방식을 장려한다는 점을 들고 싶음
    - 본인이 원하는 UI 구조가 무엇(What)인지 그대로 작성할 수 있다!
5. 광범위한 사용
  - 이것도 그 자체가 장점이라기보다는... 다른 곳에 많이 쓰이고 있으니 JSX를 이미 쓰던 사람들이 해당하는 타 기술들로 쉽게 넘어갈 수 있다는 당연한 말을 하는 느낌

## 2.3 JSX의 단점
1. 학습 곡선 가중
  - 장점 1번이랑 뭔가 상충하는 내용같음... 더 읽고 쓰기 쉬운데 학습 곡선이 가중된다구요?
2. 전용 도구 필요
  - 현대에 와서는 그리 문제가 되지는 않는 내용일듯? 2025년 대 번들러 시대에 부싯돌로 불 피우고 나뭇가지 꺾어서 젓가락 만드는 사람은 없을 거 같아용
3. 관심사 혼합
  - 1장에서 이야기했던 "관심사 분리에 대한 시선의 차이"가 드러나는 부분!
4. 자바스크립트 호환성 부족
  - 이건 JSX 요소가 자바스크립트 함수로 변환된다는 사실을 알고, 문과 식의 차이를 명확하게 알고 있다면 너무 당연한 이야기일 것 같음! 문은 함수 인자로 전달될 수 없기 때문~

## 2.4 내부 동작
### 2.4.1 코드는 어떻게 작동하나요?
- 소스 코드가 프로그램으로 변환되는 과정(토큰화 -> 구문 분석 -> 코드 생성)을 간단히 설명하는 단락!
- 자바스크립트 동작원리 스터디했을때 다루었던 자바스크립트 엔진의 동작 방법이 생각나는 부분이네요~
### 2.4.2 JSX로 자바스크립트 구문 확장하기
- 기존에 "컴파일러"라고 하면 보통 도착 언어가 기계어인 것을 생각하지만, JSX는 도착 언어가 자바스크립트를 생성함
- 이 과정을 "트랜스파일", "소스 대 소스 컴파일"이라고 부름
  - 타입스크립트도 TS 코드를 JS로 만들기 때문에 위 경우의 일종
  - 개인적으로는 꼭 그렇게 일일이 구분해야 하나 싶음... 삐딱하게 보자면 컴파일 언어를 사랑하는 사람들이 JS 배척하고 싶어서 만든 말인가 싶고
## 2.5 JSX 프라그마
- 일반적인 JS에서는 `<`는 비교 연산에서만 사용 가능한 문자지만 JSX에서는 함수 호출로 변환될 수 있음
  - 지시어? 프라그마? C 계열 언어를 해본 사람이라면 전처리기 매크로가 생각날 수도 있을 듯
  - 제 책에 오탈자가 있어요... `use strict`라고 두 번 적혀있음ㅠㅠ 아마 `use client`나 `use server`겠지요
## 2.6 표현식
- 위에서 잠시 이야기했던 문과 식의 차이점에 대한 내용 등장
- `{arr.map((v, i) => { console.log(1); return <span key={i} /> })}` 뭐 이렇게 하면 출력을 못할 건 없겠지만 결국 중요한 건 표현식의 형태가 되어야 한다는 것이겠지요

## 2.8 복습하기
1. JSX란 무엇이며, 장단점은 무엇인가요?
  - "자바스크립트 코드 안"에서, "HTML과 유사한 코드"를, 작성할 수 있게 해주는 "구문 확장 문법"
  - 자바스크립트로 코드를 쓰면서 선언적으로 UI를 선언할 수 있다는 장점이 있음
  - 개인적으로는 저 위의 모든 단점에 동의하지 않음... 진짜 HTML을 작성하는 것이 아님에도 HTML을 작성하는 것처럼 느껴져서 혼동이 올? 수도? 있겠다 정도?
2. JSX와 HTML의 차이점은 무엇인가요?
  - 중괄호를 사용해 자바스크립트 표현식을 삽입할 수 있어 동적인 UI를 작성하기 쉬우며, 속성 작성 시 네이밍 컨벤션이 `camelCase`라는 차이점이 있음
  - 추가로, 어쨌든 자바스크립트 코드이기 때문에 특정 자바스크립트 예약어를 사용할 수 없다! `class`를 사용할 수 없어서 `className`을 쓴다던가 `for`를 못 써서 `htmlFor`을 쓴다던가
3. 텍스트 문자열은 어떻게 기계어가 되나요?
  - 문자열을 의미있는 단위로 나누는 토큰화(tokenization) 과정, 토큰을 가져와 추상 구문 트리(abstract syntax tree, AST)로 변환하는 파싱(parsing) 과정, AST를 기계어로 변환하는 코드 생성(code generation, codegen) 과정을 거쳐 텍스트 문자열 형식의 소스 코드가 실행될 수 있는 기계어로 변환됨
4. JSX 표현식이란 무엇이며 어떤 좋은 점이 있나요?
  - JSX 코드 작성 시 요소 트리 내에서 중괄호 안에 작성할 수 있는 자바스크립트 표현식
  - 목록 반복을 통해 복수 개의 요소 생성, 삼항 연산자를 이용해 조건부 렌더링, 데이터 조작 후 렌더링 등이 가능함
