# CHAPTER 10 리액트 대체제

## 📌UI 라이브러리/프레임워크의 공동 목표

- **컴포넌트 기반 아키텍처**
    - 컴포넌트에 자체 상태와 로직을 캡슐화
    - 컴포넌트 조합으로 복잡한 UI 구성 가능
    - 관심사 분리, 재사용성, 유지보수성 향상
- **선언적 구문**: 복잡한 DOM 조작 추상화
- **업데이트**: 상태 변경에 대응해 UI를 효율적으로 업데이트
- **수명 주기 메서드**: 수명 주기 별 메서드 호출을 가능하게 해 개발자에게 편의 제공
- **생태계와 도구**: 생태계의 도움 & 다른 도구와 호환성, 활용성, 확장성

## 📌반응성(Reactivity)

- **반응형 시스템**
    - 데이터 변화에 따라 자동으로 업데이트되는 시스템
    - 코드 실행 시, 계산에 필요한 의존성을 자동으로 추적
    - 의존성 변경 시, 자동으로 의존성에 연관된 모든 계산이 다시 실행
- **리액트의 거친 반응성(coarse-grained reactivity)**
    - `v = f(s)`: 새 상태와 함께 함수가 다시 실행되어야 비로소 뷰가 업데이트됨
    - ⇒ 전통적인 반응성 부족 but…
    - ⇒ 상태 업데이트 일괄 처리 가능
    - ⇒ 어떤 시점에서든 상태 추론이 쉬움 (예측가능성)
- **시그널(Signal)이란?**
    - 반응형 시스템 구현을 위한 한 가지 방법
    - 반응형으로 동작하는 값 컨테이너
    - 값에 접근할 때 **의존성 추적(track)** & 값을 변경하면 **부작용 실행(trigger)**
    - 구독을 통해 의존성 변경에 따라 업데이트하는 렌더링 모델과 함께 사용되기도 함
    - 라이브러리/프레임워크에 따라 `observable`, `ref`, `atom` 등으로 불리기도 함

<aside>
💡

리액트가 반응성이 부족하다고 해서 나쁜 게 아니다. 모든 상황에 맞는 방법은 없다! 모두 장단점이 있고 각기 다른 사례에 적합하다. 이러한 차이를 이해하는 것이 적합한 도구를 선택하는 데 매우 중요하다.

## 📌리액트의 대체제

### 1️⃣뷰(Vue)

- 반응형 모델: `reactive`, `ref` (시그널과 유사)
    - 값의 게터/세터를 재정의해 반응성을 주입함
    - 복잡한 상태 관리를 위한 `reactive`와 단일 상태 관리를 위한 `ref`가 있음
        
        ```jsx
        // 게터/세터를 재정의하는 JS Proxy 객체를 반환
        function reactive(obj) {
          return new Proxy(obj, {
            get(target, key) {
              track(target, key)
              return target[key]
            },
            set(target, key, value) {
              target[key] = value
              trigger(target, key)
            }
          })
        }
        
        // 사용 예시
        const state = reactive({ count: 0 });
        state.count++;
        ```
        
        ```jsx
        // 게터 및 세터를 재정의한 객체 반환
        function ref(value) {
          const refObject = {
            get value() {
              track(refObject, 'value')
              return value
            },
            set value(newValue) {
              value = newValue
              trigger(refObject, 'value')
            }
          }
          return refObject
        }
        
        // 사용 예시
        const count = ref(0);
        count.value++;
        ```
        
- 단순성
    - 러닝커브가 낮음(html, css, js 기반)
    - 스캐폴딩 지원

### 2️⃣앵귤러(Angular)

- 반응형 모델: 시그널
    
    ```jsx
    const count = signal(0);
    count(); // get
    count.set(1); // set
    count.update((v) => v * 2); // 기존 값 기반 업데이트
    ```
    
- 강제성
    - 일반적인 문제에 대한 자체 방식을 제공하고 이를 강력히 권장하는 프레임워크
    - 러닝커브가 높음
- 변경 감지 매커니즘
    - 컴포넌트를 top-down으로 살펴 보며 변경 사항을 찾음
    - 이를 주기적으로 실행해 변경 사항이 뷰에 반영되게 함
    - 이는 수동 혹은 자동(이벤트를 통해)으로 트리거 됨

### 3️⃣스벨트(Svelte)

- 반응형 모델: 컴파일러 활용 (+시그널)
    - 컴파일러를 통해 선언적 컴포넌트를 최적화된 명령형 자바스크립트 코드로 변환
        - 컴파일은 코드를 해석하고 다른 코드로 변환하는 과정
        - ⇒ **특별한 문법 없이도 반응성 구현** (스벨트가 컴파일 시점에 알아서 주입해줌)
        - 내부적으로 시그널을 활용해 이를 구현함
        
        ```html
        <script>
        	let count = 0; // 일반 변수처럼 써도 자동으로 반응성 적용
        	// let count = $state(0); // 룬을 사용해 상태임을 나타낼 수도 있음
        	const increment = () => count++; // 일반 변수처럼 조작 가능
        </script>
        
        <button onclick={increment}>
        	clicks: {count}
        </button>
        ```
        
    - 가상 DOM 비교 및 patch 단계가 없어 런타임 성능이 빠름
- 룬(rune)
    - 유지보수, 리팩토링 등을 위해, 반응형 값과 아닌 값을 구분하고자 사용하는 키워드 (`$`)

### 4️⃣솔리드(Solid)

- 반응형 모델: 시그널
    
    ```jsx
    import { createSignal } from "solid-js";
    
    function Counter() {
      const [count, setCount] = createSignal(1);
      const increment = () => setCount(count => count + 1);
    
      return (
        <button type="button" onClick={increment}>
          {count()}
        </button>
      );
    }
    ```
    
    - 리액트의 `useState` 🆚 솔리드의 `createSignal`
        
        
        |  | 리액트 | 솔리드 |
        | --- | --- | --- |
        | 반응형 값 명칭 | state | signal |
        | 반응형 값 정체성 | 값 자체 | 게터 함수 |
        | 트리거 함수 이펙트 | 컴포넌트 재실행 | signal에 의존하는 모든 UI의 업데이트 트리거 |
        | 반응성 구분 | coarse-grained reactivity | **세밀한 반응성(fine-grained reactivity)** |

### 5️⃣퀵(Qwik)

- 설계
    - 웹 페이지를 컴포넌트의 집합으로 봄
    - 각 컴포넌트를 필요에 따라 독립적으로 읽어 들이고 상호작용하게 함 (코드 분할)
    - 반응형 모델 사용 but 그보다 성능에 초점을 맞춤
- 재개 가능성(resumability) (6장 참고)
    - 페이지 초기 상태에서도 즉각적인 상호 작용이 가능 (하이드레이션과 대비되는 부분)
    - 상호 작용이 필요할 때마다 온디맨드 방식으로 필요한 동작을 읽어들임
- 리액트와 호환성
    - JSX 사용
    - `qwikify` 유틸리티를 통해 퀵 애플리케이션에서 리액트 컴포넌트 사용 가능

## 📌리액트 컴파일러와 시그널

- 리액트는 전체 컴포넌트 트리를 탐색하고 각각을 비교해 리렌더링할 컴포넌트를 결정함
- 시그널 사용 시, 트리 순회 없이 UI의 반응형 부분만 업데이트하면 됨
- 리액트 컴파일러로 메모화를 최적화해도 시그널의 세밀한 반응성보단 기본적으로 느릴 듯

## 📌복습하기

- **1. 리액트, 뷰, 스벨트, 솔리드, 앵귤러의 반응형 모델은 각각 어떻게 다른가요? 이러한 차이가 라이브러리/프레임워크의 성능과 개발 경험에 어떤 영향을 미치나요?**
    
    뷰, 스벨트, 솔리드, 앵귤러 모두 시그널 기반으로 반응형 모델을 구현합니다. 뷰는 `reactive`, `ref`,  앵귤러는 `signal`, 솔리드는 `createSignal` API를 제공해 개발자가 의존성을 직접 설정할 수 있게 합니다. 스벨트는 컴파일 시점에서 컴파일러가 자동으로 의존성을 트래킹하므로 별도의 문법을 사용하지 않아도 되지만, 룬(`$`)을 통해 의존성을 명시할 수 있습니다 .
    
    리액트는 전통적인 반응형 모델과는 달리, 값을 변경해도 연관된 다른 값(혹은 뷰)들의 업데이트가 자동으로 수행되지 않습니다. 대신 리액트는 적절한 타이밍에 새 상태를 반영한 컴포넌트를 리렌더링, 즉 함수를 다시 실행하도록 스케줄링합니다. 이 실행 결과가 비로소 업데이트로 이루어집니다.
    
    반응형 모델의 차이로 도구의 성능이 달라질 수 있습니다. 가령 리액트는 업데이트 시 전체 컴포넌트를 가상 DOM으로 다시 그리고 이전 가상 DOM과 비교하는 과정을 필수로 거칩니다. 반면 시그널 기반의 반응형 모델을 채용한 다른 도구들은 가상 DOM 비교 및 패치 단계 없이 변경된 부분만 업데이트하는 게 가능하므로 그만큼 리소스가 단축될 수 있습니다.
    
    또 개발 경험 측면에서 의존성을 시스템이 자동으로 추적하고 업데이트하는 것과 개발자가 수동으로 하는 것의 차이가 있습니다. 하지만 리액트의 경우 어떤 시점에서든 상태를 쉽게 예측할 수 있다는 장점이 있습니다.
    
- **2. 성능을 극대화하는 퀵의 고유한 접근 방식을 설명해 주세요. 지금까지 살펴본 UI 라이브러리/프레임워크의 접근 방식과 어떻게 다른가요?**
    
    지금까지 살펴본 다른 라이브러리/프레임워크에서는 하나의 문서를 생성하기 위해 여러 컴포넌트를 결합했습니다. 반면 퀵은 웹 페이지를 컴포넌트의 집합으로 보고, 각각의 컴포넌트를 필요에 따라 독립적으로 읽고 상호작용할 수 있는 대상으로 취급합니다.
    
- **3. 이 장에서 설명한 각 UI 라이브러리/프레임워크의 주요 강점과 약점은 무엇인가요? 이러한 강점과 약점이 특정 프로젝트의 라이브러리/프레임워크 선택에 어떤 영향을 미칠까요?**
    
    
    |  | 주요 강점 | 주요 약점 |
    | --- | --- | --- |
    | 리액트 | 예측 가능성 | 반응성 부족 |
    | 뷰 | 반응성, 단순성, 낮은 러닝커브 |  |
    | 앵귤러 | 반응성, 변경 감지기, 자체 솔루션 제공 | 규칙 강제 ⇒ 높은 러닝커브 |
    | 스벨트 | 반응성, 성능(컴파일러) | 생태계 규모 작음 |
    | 솔리드 | 반응성, 성능 | 생태계 규모 작음 |
    | 퀵 | 반응성, 성능(코드분할) | 생태계 규모 작음 |
- **4. 리액트는 전통적인 의미의 반응형이 아닙니다. 이를 뷰 또는 스벨트 같은 라이브러리에서 볼 수 있는 ‘푸시 기반(push-based)’ 반응형 모델과 비교해 자세히 설명하세요.**
    
    뷰와 스벨트는 의존성이 변경됨에 따라 자동으로 의존성과 연관된 모든 계산들이 다시 실행되고 업데이트가 일어나는 푸시 기반(push-based) 반응형 모델을 사용합니다. 푸시 기반 아키텍처에서는 상태를 생성한 쪽이 해당 상태를 필요로 하는(의존하는) 쪽에게 넘겨줄(push) 책임이 있습니다.
    
    반면 리액트는 상태를 변경해도 업데이트를 즉각적으로 수행하지 않고 렌더링을 지연할 수 있습니다. 컴포넌트 함수가 새 상태를 반영하여 다시 실행된 후에 비로소 업데이트가 일어납니다. 이처럼 상태를 필요로 하는 소비자(=리액트)가 새로운 값을 요청하는 방식을 풀 기반(pull-based) 아키텍처라고 합니다. ([참고: 리액트의 Pull Approach](https://legacy.reactjs.org/docs/design-principles.html#scheduling))
    
- **5. 리액트 컴파일러란 무엇인가요? 어떻게 작동하나요? 시그널과 비교하면 어떤가요?**
    
    리액트 컴파일러는 리액트에서 불필요한 리렌더링을 방지하기 위해 컴포넌트 등을 메모화하는 것을 자동으로 해주는 최적화 도구입니다. 아직 정식 출시되지 않았습니다.
    
    리액트 컴파일러가 메모화를 최적화해도 리액트의 렌더링 프로세스는 이전과 동일하게 가상 DOM 비교를 중심으로 이루어집니다. 시그널 기반 도구는 가상 DOM 비교 프로세스 없이도 필요한 부분만 업데이트하는 게 가능하기 때문에 리액트보다 빠를 것입니다.
    

## 💬느낀 점

- 방법은 다르지만 다 비슷비슷한 것 같았다. 마치 다들 각자의 자리에서 최선의 다하는 느낌이라 재미있었음 ㅋㅋ
- 뷰의 `reactive`와 `ref`가 똑같아 보여서 뭐가 다른지 직접 찾아보았음. 근데 그냥 복잡한 상태냐 아니냐가 기준이라고 해서 이걸 이렇게 설명한 저자에게 화가 쪼금 났다
- 시그널이 뭔지 책에서 설명해주긴 했는데 그거론 부족해서 더 찾아봤다.
- 녹아웃(knockout)… 기억이 잘 안나…ㅠㅠ
- 솔리드는 정욱님께서 자주 언급했었는데 이렇게 만나네요
- 365쪽부터 나오는 카운터 코드 예시에서 추가/삭제한 코드 색상이 달라서 읽기 힘들었다 ㅎㅎ
- 뷰가 리액트처럼 가상 DOM을 사용하면서도 반응성을 가진다는 게 신기했음. 세밀한 반응성을 통해 가상 DOM 비교와 같은 과정 없이 효율적으로 업데이트할 수 있다고 책에서 계속 말하는데 뷰는 왜 가상 DOM을 사용하는지 잘 모르겠음. 이런 구체적인 부분들이 헷갈림.
    - ✅ React, Vue, 기타 반응형 프레임워크의 업데이트 방식 비교 (by ChatGPT)
        
        **React**
        
        - 업데이트가 발생하면 해당 컴포넌트를 **함수로 다시 실행**해 새로운 **가상 DOM 트리 전체**를 생성
        - 새 가상 DOM과 이전 가상 DOM을 **diff 알고리즘으로 비교**하여, 실제 DOM에 **차이점만 반영**
        - → **렌더링 단위는 전체**, **업데이트 단위는 부분**
        
        **Vue**
        
        - 반응형 시스템(Proxy 기반)으로 상태의 변경을 **정밀하게 추적**
        - 변경된 상태를 **참조하고 있는 컴포넌트만 다시 렌더링**
        - 그 컴포넌트의 템플릿에서 만들어진 **작은 가상 DOM 조각만 비교(diff)**하여 실제 DOM을 업데이트
        - → **렌더링 단위도 부분**, **업데이트 단위도 부분**
        
        **Svelte / Solid 등 컴파일 기반 프레임워크**
        
        - 상태 변경을 추적하는 **시그널/컴파일 분석 기반 반응형 시스템**
        - 변경이 일어난 상태에 **직접 연결된 DOM만 명령형으로 즉시 업데이트**
        - **가상 DOM을 사용하지 않음**, diff 과정도 없음
        - → **렌더링 단위 없음**, **업데이트 단위는 정확히 해당 DOM**
- 스벨트는 예전에 아무것도 모르던 시절에 신기하게 쳐다보곤 했었는데 반응성이라는 개념을 알고 난 다음에 다시 보니까 컴파일러로 반응성을 주입한다는 게 재미있고 신기하다고 느꼈다. 역시 아만보야~
