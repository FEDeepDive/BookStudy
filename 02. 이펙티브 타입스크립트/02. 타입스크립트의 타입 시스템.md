`아이템 13`

> 명명된 타입을 정의할 때 인터페이스 대신 클래스를 사용할 수 있지만 클래스는 값으로도 쓰일 수 있는 자바스크립트 런타임의 개념입니다.  (69p)
> 
- TypeScript에서는 타입을 만들 때 `interface`, `type`, `class` 셋 다 사용 가능함
- `class`를 선언하면, **자동으로 타입도 생성됨**
- 즉, 클래스는 **값 + 타입** 둘 다 역할을 할 수 있음

👀 헉시.. 몰랐다.(알앗는데 지금은 모르는 걸수도,,?)

`type`과 `interface`는 대부분의 경우 서로 대체 가능하지만, 명확한 차이점이 존재하며 언제 무엇을 사용해야 할지 아는 것이 중요

- `interface` : API의 형태(객체)를 정의하거나, 클래스가 구현해야 하는 구조를 만들 때. 특히 선언 병합이 필요한 라이브러리 등에서 유용
- `type` : 유니온, 튜플 등 복잡한 타입을 정의하거나, 기존 타입에 별칭을 붙이거나, 매핑된 타입을 활용할 때 사용
- 일관성이 중요: 프로젝트 내에서 일관된 스타일을 유지하는 것이 가장 중요

`type`과 인터페이스는 보통 협업의 관점에서 컨벤션을 정할때 논의를 많이 하는것 같다

개인적으론 `interface`가 더 쉽게 느껴졌는지 주로 `interface`를 쓴다. 

근데 타입만 가능한 경우들이 몇 가지 있어서 그럴거면 `type`을 쓰는게 낫지 않나 하는 생각도 요즘 하고 있다 실제로 주변에선 `type`만 쓰시는 분들도 있다.

**✋용어 정리**

**인덱스 시그니처** : 객체의 키가 무엇이든 상관없이 특정 타입으로 값을 받을 수 있도록 정의하는 문법

```tsx
interface UserMap {

```

동적으로 키가 추가되는 객체를 표현할때 사용함

⇒ 가능하다면 정확한 타입 사용

**맵드 타입**: 기존 타입의 키들을 순회하면서 새로운 타입을 만드는 방식

```tsx
type NewType = {
  [K in keyof ExistingType]: Type;
```

`아이템 17`
> 함수가 매개변수를 변경하지 않는다면 readonly로 선언해야 한다.
> 
> 
> 더 넓은 타입으로 호환될 수 있고, 의도치 않은 변경을 방지할 수 있다.
> 

> 라이브러리의 함수를 호출하는 경우라면, 타입 선언을 바꿀 수 없으므로 number[] → readonly number[]를 사용해야 한다.
> 

⇒ 외부에서 들어오는 값을 변경하지 말자

객체나 배열은 타입을 고정하더라도, 그 내부 값을 바꾸는 건 막을 수 없다.그래서 타입 수준에서 해당 프로퍼티의 재할당을 금지하려면 `readonly`를 적어야 하고,이때 얕은 수준의 변경만 막힌다. (참조 타입 내부는 여전히 변경 가능)
