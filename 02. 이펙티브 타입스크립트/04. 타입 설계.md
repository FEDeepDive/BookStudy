## 📌타입을 유효한 상태로 표현하기

- 유효한 상태란?
    - 상태 간 서로 겹치거나 충돌(모순)하지 않아야 함
    - ex) 상태가 `isLoading`이면서 `error`인 상황이 없도록 타입을 설계해야 함
- 상태가 유효하지 않으면 분기 로직이 복잡해지고, 상태 예측이 어렵고, 버그가 발생함
- 태그드 유니온을 활용해 상태를 완전히 분리할 수 있음
    
    ```tsx
    interface RequestPending { state: 'pending' }
    interface RequestError { state: 'error'; error: string }
    interface RequestSuccess { state: 'ok'; pageText: string }
    
    // 각 상태 중 한 개만 가질 수 있도록 분리
    type RequestState = RequestPending | RequestError | RequestSuccess;
    
    interface State {
      currentPage: string;
      requests: {[page: string]: RequestState};
    };
    
    // 사용 예시
    const state: State = {
      currentPage: 'dashboard',
      requests: {
        dashboard: { state: 'ok', pageText: 'Welcome!' },
        profile: { state: 'pending' },
        settings: { state: 'error', error: 'Server timeout' }
      }
    };
    ```
    

## 📌느슨한 매개변수, 엄격한 반환 타입

- 함수의 매개변수 타입은 느슨하게, 반환 타입은 엄격하게 설계하자
    - 매개변수 타입이 느슨하면, 함수 매개변수로 넣기 위해 타입을 재단할 수고를 덜 수 있음
    - 반환 타입이 엄격하면(좁으면), 반환 결과를 바로 사용할 수 있음
- ⇒ 선택적 속성, 유니온 타입은 반환 타입보다 매개변수 타입으로 더 일반적임
- 매개변수와 반환 타입의 재사용을 위해, 하나의 타입을 `기본형`과 `느슨한 형태`로 나눠놓으면 편함
    - 반환할 때는 더 좁은 기본형, 매개변수로 받을 때는 더 넓은 느슨한 형태를 사용
    - ex) `Array`와 `ArrayLike`, 이터러블 …

## 📌null 값이 내부에 들어가지 않도록 하기

- 한 값의 `null` 여부가 다른 값의 `null` 여부에 암묵적으로 관련되게 설계하지 않기
    - ⇒ 관련되어야 하는 **두 값을 하나의 객체로 묶고, 이 객체 자체가 `null`이거나 아니도록 만들자**
        
        ```tsx
        // bad
        interface BlogData {
          title: string | null;
          content: string | null;
        }
        
        // good
        type BlogData = 
          | { status: 'loaded'; title: string; content: string }
          | { status: 'error'; message: string };
        ```
        
- 클래스 선언 시, 필요한 모든 값이 준비되었을 때 생성해서 `null`이 없도록 하자
    - 안 좋은 예
        
        ```tsx
        class UserPosts {
          user: UserInfo | null;
          posts: Post[] | null;
          
          constructor() {
            this.user = null;
            this.posts = null;
          }
          
          async init(userId: string) {
            return Promise.all([
              async () => this.user = await fetchUser(userId),
              async () => this.posts = await fetchPostsForUser(userId)
            ]);
          }
        }
        ```
        
        - 필드에 접근하는 모든 곳에서 null 체크 해야 함
        - 가질 수 있는 타입의 경우의 수가 4가지임
        - `user`는 `null`이면서 `posts`는 `not null`인 모순이 생길 수 있음
    - 좋은 예
        
        ```tsx
        class UserPosts {
          user: UserInfo;
          posts: Post[];
        
        	constructor(user, posts) {
        		this.user = user;
        		this.posts = posts;
        	}
        	
          static async init(userId: string): Promise<UserPosts> {
        	  const [user, posts] = await Promise.all([
        		  fetchUser(userId),
        		  fetchPosts(userId)
        	  ]);
        	  return new UserPosts(user, posts); // 처음부터 null이 아니게 해서 인스턴스 반환
          }
        }
        ```
        
- `null` 또는 잠재적인 불완전한 값이 코드 안쪽에 있으면, 타입 체커가 미처 체크하지 못할 수 있음
- `strictNullChecks` 설정이 없으면 이런 잠재적 오류를 캐치하지 못함

```
💡

아이템31의 소제목이 "타입 주변에 null 값 배치하기"인데 내용이랑 매치가 잘 안 돼서 원문을 찾아봤다. "Push Null Values to the Perimeter of Your Types"으로 직역하자면 "null 값을 타입의 둘레로 밀어 넣어라"가 된다. 즉 null 값을 안쪽이 아닌 바깥쪽(경계)에서 처리하라는 말이다.
```

## 📌태그된 유니온 활용하기

- 유니온으로 된 인터페이스보다, 인터페이스 각각을 유니온(=태그된 유니온)하자
    
    ```tsx
    // bad
    // 각 필드가 서로 다른 스타일을 가지는 것을 방지하지 못함
    interface Layer {
      type: 'fill' | 'line' | 'point';
      layout: FillLayout | LineLayout | PointLayout;
      paint: FillPaint | LinePaint | PointPaint;
    }
    
    // good
    interface FillLayer {
      type: 'fill';
      layout: FillLayout;
      paint: FillPaint;
    }
    interface LineLayer {
      type: 'line';
      layout: LineLayout;
      paint: LinePaint;
    }
    interface PointLayer {
      type: 'paint';
      layout: PointLayout;
      paint: PointPaint;
    }
    type Layer = FillLayer | LineLayer | PointLayer;
    ```
    
- ⇒ 합리적이며, 사용하기 편함

## 💬느낀 점

- 한 타입을 기본형과 느슨한 형태로 나눠본 적이 없는데, 지금 와서 생각해보면 라이브러리 내장 타입들은 이렇게 설계된 게 많은 것 같다.
- 타입을 만들다보면 '모든 상황을 커버할 수 있는 완벽한 타입을 하나 만들어서, 다른 타입들은 안 써도 되게끔 해주겠어'같은 이상한 욕심을 종종 가지게 된다(나만 그런가?). 그런 타입을 뚝딱 만드는 것이야말로 잘하는 것이라고 생각해서 그랬던 것 같은데(물론 잘하는 건 맞겠지만) 그럴 필요가 전혀 없고, 상황에 따라 유동적으로 사용할 수 있도록 나눠놓으면 되는데 말이다~ 띠용
- "타입 시스템 개발자들은 수십 년의 경험을 가진 언어 전문가입니다(p167)" << 멋있당
- 변수명에 타입을 적으면 안되는 것은 알고 있지만서도… `string`타입을 `number` 타입으로 변환할 때 `numeric...`처럼 이름을 짓는 습관이 있는데, 이런 경우는 어떻게 해야 할까?
- `null` 값이 내부로 들어가지 않도록 경계에서 처리하는 것은 어찌보면 당연한데 별 생각 없이 코드를 짜거나, 이미 있는 코드에 하나씩 추가하다보면 `null`이 난무하는 경우가 있는 거 같다.
- 클래스 만들 때 static으로 init 메서드를 만들고 거기서 인스턴스를 반환하는 건 넘 꿀팁이다. TS로 클래스 만들 때 고통스러웠는데 저렇게 하면 되는구나… 흑흑
- - 4장의 아이템32까지 읽었을 때 내용을 두 가지 정도로 정리할 수 있을 것 같다. 하나는 타입이 더 가치를 가질 수 있게 유효하게 만드는 것, 다른 하나는 타입을 명확하게 설계하는 것이다(달리 말하면 타입을 **좁게** 만드는 것이라고 볼 수 있을 것 같다). 3장에서도 느꼈지만 이런 디테일이 타입스크립트를 얼마나 이해하고 잘 활용하는지를 나타내는 것 같음.
