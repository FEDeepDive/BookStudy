- 한 타입을 기본형과 느슨한 형태로 나눠본 적이 없는데, 지금 와서 생각해보면 라이브러리 내장 타입들은 이렇게 설계된 게 많은 것 같다.
- 타입을 만들다보면 '모든 상황을 커버할 수 있는 완벽한 타입을 하나 만들어서, 다른 타입들은 안 써도 되게끔 해주겠어'같은 이상한 욕심을 종종 가지게 된다(나만 그런가?). 그런 타입을 뚝딱 만드는 것이야말로 잘하는 것이라고 생각해서 그랬던 것 같은데(물론 잘하는 건 맞겠지만) 그럴 필요가 전혀 없고, 상황에 따라 유동적으로 사용할 수 있도록 나눠놓으면 되는데 말이다~ 띠용
- "타입 시스템 개발자들은 수십 년의 경험을 가진 언어 전문가입니다(p167)" << 멋있당
- 변수명에 타입을 적으면 안되는 것은 알고 있지만서도… `string`타입을 `number` 타입으로 변환할 때 `numeric...`처럼 이름을 짓는 습관이 있는데, 이런 경우는 어떻게 해야 할까?
- `null` 값이 내부로 들어가지 않도록 경계에서 처리하는 것은 어찌보면 당연한데 별 생각 없이 코드를 짜거나, 이미 있는 코드에 하나씩 추가하다보면 `null`이 난무하는 경우가 있는 거 같다.
- 클래스 만들 때 static으로 init 메서드를 만들고 거기서 인스턴스를 반환하는 건 넘 꿀팁이다. TS로 클래스 만들 때 고통스러웠는데 저렇게 하면 되는구나… 흑흑
- 4장의 아이템32까지 읽었을 때 내용을 두 가지 정도로 정리할 수 있을 것 같다. 하나는 타입이 더 가치를 가질 수 있게 유효하게 만드는 것, 다른 하나는 타입을 명확하게 설계하는 것이다(달리 말하면 타입을 **좁게** 만드는 것이라고 볼 수 있을 것 같다). 3장에서도 느꼈지만 이런 디테일이 타입스크립트를 얼마나 이해하고 잘 활용하는지를 나타내는 것 같음.
- 타입을 구체적으로 만들어.. 하지만 유연하게 해.. 그러면서 명확하게 해… 하지만 너무 과도하게 명확해선 안될 때도 있어… 무한 연속의 굴레… ㅋㅋㅋ 물론 말하고자 하는 바는 이게 아니지만 ㅋㅋ 아수라백작같아서 웃김. 이런 유연함을 얼마나, 어떻게 활용하고 조절할 건지가 타입스크립트 일짱이 되는 관건이라는 것이다. 타입을 줄까말까 좁힐까말까 밀당하는 스킬이 필요하기 때문에 더 어려운 것 같고, 고인물 고수 언어 학자 샘들이 조아하는 이유가 있구나 싶다. 정복하고 싶게 만들어..서?
- 아이템 33~36에서 말하려는 바는 타입스크립트 뿐만 아니라 일반적인 글쓰기나 말하기같은 언어학(?)에도 똑같이 적용된다고 생각한다. 프로그래밍에서 네이밍 잘 하려고 하는 것은 현실 세계에서 정확한 어휘를 써서 전달하는 것과 같은 맥락이라고 항상 느낌.
- 브랜디드 타입 부분을 읽을 때에는 "Symbol을 쓰면 안되나?" 하고 생각했음. 찾아보니 실제로 이를 활용해 더 안정적으로 만드는 듯(`unique symbol`). 또 라이브러리에서 제공하는 Brand 유틸리티 타입도 많이 사용되는 것 같음.
