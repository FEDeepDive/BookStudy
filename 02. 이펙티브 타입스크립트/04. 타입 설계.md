## 아이템 28. 유효한 상태만 표현하는 타입을 지향하기
- 이해를 돕기 위해 든 예시가 그리 효과적이지는 않은 것 같네요
- 저는 작업할 때 특정 작업의 성공과 실패를 명시적으로 다루기 위해 아래와 같은 유니온으로 이루어진 결과 타입을 많이 사용합니다
```ts
type Success<T> {
  success: true; // boolean이 아님에 주의
  value: T;
}

type Failure<E> {
  success: false; // boolean이 아님에 주의
  error: E;
}

type Result<T, E> = Success<T> | Failure<T>;

// example
const someProcess: Result<number, Error> = {
    // ...
}

const useSomeProcess = (result: Result<number, Error>) => {
  if (result.success) {
    // do something with result.value
    // cannot access to result.error
    console.log(result.value)

    return;
  }

  // do something with result.error
  // cannot access to result.value;
  console.error(result.error);
}

useSomeProcess(someProcess());
```
- 이게 좀 번거로울 때도 있는데 익숙해지면 예외 상황을 다루지 않아도 되어서 결과를 예측하기 쉬워지더라구요

## 아이템 29. 사용할 때는 너그럽게, 생성할 때는 엄격하게

  - `Bounds`, `Coord` 등을 보시면 위경도 정보 `LatLng`와 함께 x/y 좌표를 의미하는 `Point`를 보실 수 있지용
- 느슨한 타입은 "기본값"을 지정할 수 있는 대부분의 라이브러리에서 사용하는 일종의 패턴으로도 볼 수 있겠습니다
  - ex. [react-hook-form](https://github.com/react-hook-form/react-hook-form/blob/3f4d24ce0734a5f573a77b701822b68d4c242203/src/types/form.ts#L35)
