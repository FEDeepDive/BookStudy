## 📌타입을 유효한 상태로 표현하기

- 유효한 상태란?
    - 상태 간 서로 겹치거나 충돌(모순)하지 않아야 함
    - ex) 상태가 `isLoading`이면서 `error`인 상황이 없도록 타입을 설계해야 함
- 상태가 유효하지 않으면 분기 로직이 복잡해지고, 상태 예측이 어렵고, 버그가 발생함
- 태그드 유니온을 활용해 상태를 완전히 분리할 수 있음
    
    ```tsx
    interface RequestPending { state: 'pending' }
    interface RequestError { state: 'error'; error: string }
    interface RequestSuccess { state: 'ok'; pageText: string }
    
    // 각 상태 중 한 개만 가질 수 있도록 분리
    type RequestState = RequestPending | RequestError | RequestSuccess;
    
    interface State {
      currentPage: string;
      requests: {[page: string]: RequestState};
    };
    
    // 사용 예시
    const state: State = {
      currentPage: 'dashboard',
      requests: {
        dashboard: { state: 'ok', pageText: 'Welcome!' },
        profile: { state: 'pending' },
        settings: { state: 'error', error: 'Server timeout' }
      }
    };
    ```
    

## 📌느슨한 매개변수, 엄격한 반환 타입

- 함수의 매개변수 타입은 느슨하게, 반환 타입은 엄격하게 설계하자
    - 매개변수 타입이 느슨하면, 함수 매개변수로 넣기 위해 타입을 재단할 수고를 덜 수 있음
    - 반환 타입이 엄격하면(좁으면), 반환 결과를 바로 사용할 수 있음
- ⇒ 선택적 속성, 유니온 타입은 반환 타입보다 매개변수 타입으로 더 일반적임
- 매개변수와 반환 타입의 재사용을 위해, 하나의 타입을 `기본형`과 `느슨한 형태`로 나눠놓으면 편함
    - 반환할 때는 더 좁은 기본형, 매개변수로 받을 때는 더 넓은 느슨한 형태를 사용
    - ex) `Array`와 `ArrayLike`, 이터러블 …

## 📌null 값이 내부에 들어가지 않도록 하기

- 한 값의 `null` 여부가 다른 값의 `null` 여부에 암묵적으로 관련되게 설계하지 않기
    - ⇒ 관련되어야 하는 **두 값을 하나의 객체로 묶고, 이 객체 자체가 `null`이거나 아니도록 만들자**
        
        ```tsx
        // bad
        interface BlogData {
          title: string | null;
          content: string | null;
        }
        
        // good
        type BlogData = 
          | { status: 'loaded'; title: string; content: string }
          | { status: 'error'; message: string };
        ```
        
- 클래스 선언 시, 필요한 모든 값이 준비되었을 때 생성해서 `null`이 없도록 하자
    - 안 좋은 예
        
        ```tsx
        class UserPosts {
          user: UserInfo | null;
          posts: Post[] | null;
          
          constructor() {
            this.user = null;
            this.posts = null;
          }
          
          async init(userId: string) {
            return Promise.all([
              async () => this.user = await fetchUser(userId),
              async () => this.posts = await fetchPostsForUser(userId)
            ]);
          }
        }
        ```
        
        - 필드에 접근하는 모든 곳에서 null 체크 해야 함
        - 가질 수 있는 타입의 경우의 수가 4가지임
        - `user`는 `null`이면서 `posts`는 `not null`인 모순이 생길 수 있음
    - 좋은 예
        
        ```tsx
        class UserPosts {
          user: UserInfo;
          posts: Post[];
        
        	constructor(user, posts) {
        		this.user = user;
        		this.posts = posts;
        	}
        	
          static async init(userId: string): Promise<UserPosts> {
        	  const [user, posts] = await Promise.all([
        		  fetchUser(userId),
        		  fetchPosts(userId)
        	  ]);
        	  return new UserPosts(user, posts); // 처음부터 null이 아니게 해서 인스턴스 반환
          }
        }
        ```
        
- `null` 또는 잠재적인 불완전한 값이 코드 안쪽에 있으면, 타입 체커가 미처 체크하지 못할 수 있음
- `strictNullChecks` 설정이 없으면 이런 잠재적 오류를 캐치하지 못함

## 📌string 타입보다 더 구체적인 타입 사용하기

- `string` 타입보다 정확한 타입을 사용 ⇒ 오류 방지, 가독성 향상, 자동완성 기능 …
- 객체 속성 이름을 매개변수로 받을 때는 `string` 대신 `keyof T`를 사용
    - 이때, `keyof T`의 부분 집합인 `K extends keyof T`를 사용하면 더 정확하게 표현 가능
    
    ```tsx
    type RecordingType = 'studio' | 'live';
    
    interface Album {
      artist: string;
      title: string;
      releaseDate: Date;
      recordingType: RecordingType;
    }
    
    // keyof T
    function pluck1<T>(records: T[], key: keyof T) {
      return records.map(r => r[key]);
    }
    // K extends keyof T
    function pluck2<T, K extends keyof T>(records: T[], key: K): T[K][] {
      return records.map(r => r[key]);
    }
    
    declare let albums: Album[];
    const releaseDates1 = pluck1(albums, 'releaseDate'); // (string | Date)[]
    const releaseDates2 = pluck2(albums, 'releaseDate'); // Date[]
    ```

## 📌브랜딩 기법(Branding/Nominal Typing, Branded Type)

- 같은 구조의 타입(주로 원시 타입)을 별도의 타입으로 구분하여 사용하기 위한 기법
- 목적: 구조적 타이핑으로 인해 의도치 않은 타입 호환이 일어날 때, 명목적 타이핑을 더해 문제를 해결
- **사용 방법**
    - 구분하려는 타입에 `_brand` 속성을 갖는 객체 타입을 인터섹션해서 브랜디드 타입을 만듦
    - 구분하려는 값을 브랜디드 타입으로 단언한 후에 사용함
- **효과**
    - 타입 안정성 향상 & 런타임 오류 줄임
    - 런타임 오버헤드 없이 런타임에서 타입 검사하는 것과 같은 효과를 보임 (예제2 참고)
    - 정적 분석 도구(자동완성 도구, 오류 탐지 등)와 잘 연동됨
- **사용 상황**
    - 혼동해선 안되는 값들을 구분하고 싶을 때
    - 숫자나 문자열 등 원시 타입에 의미적 차이를 부여하고 싶을 때
    - 런타임 비용 없이 타입을 강화하고 싶을 때
- **주의할 점**
    - 이미 `_brand` 속성을 갖는 객체가 있을 수 있음
    - `_brand` 속성에 접근 및 쓰기 가능할 수 있음
    - 실수로 `_brand` 속성의 값을 다른 타입과 동일하게 지정하면 같은 구조로 취급됨
    - 남용하면 코드가 복잡해짐 & 타입스크립트의 구조적 타이핑의 의미가 없어짐
    - 개발자가 값이 무엇인지 알고 있다면 브랜드 타입보다 단언하는 게 더 쉬울 수 있음
- **예시**
    - 예시1 (값 구분 측면)
        
        **사용 전: 실수로 두 값을 혼동하지만 타입 체커가 모르는 문제**
        
        ```tsx
        type Meters = number;
        type Seconds = number;
        
        // 속력(m/s) 구하기
        function run(distance: Meters, time: Seconds) {
          return distance / time;
        }
        
        run(10, 5); // OK
        run(5, 10); // 또 OK 😱
        
        // Meters, Seconds 모두 number여서 OK이지만
        // 의미론적으로는 거리와 시간을 헷갈리면 안 되는 상황
        // => 값을 구분할 필요성
        ```
        
        **사용 후: 값을 혼동할 수 없게 만듦**
        
        ```tsx
        type Meters = number & { _brand: 'meters' };
        type Seconds = number & { _brand: 'seconds' };
        
        const meters = (n: number) => n as Meters;
        const seconds = (n: number) => n as Seconds;
        
        run(meters(100), seconds(10)); // OK
        run(seconds(10), meters(100)); // ❌ 타입 오류!
        ```
        
    - 예시2 (런타임 타입 검사 측면)
        
        **사용 전: 런타임 시점에서야 검사하여 오류를 확인하게 되는 문제**
        
        ```tsx
        function listAbsolutePath(path) {
          if (!path.startsWith('/')) {
            throw new Error('Not an absolute path');
          }
          // ...
        }
        ```
        
        **사용 후: 타입을 통해 컴파일 시점에 오류를 확인할 수 있음**
        
        ```tsx
        type AbsolutePath = string & { _brand: 'abs' };
        
        function listAbsolutePath(path: AbsolutePath) {
          // ...
        }
        
        function isAbsolutePath(path: string): path is AbsolutePath {
          return path.startsWith('/');
        }
        
        if (isAbsolutePath(path)) {
          listAbsolutePath(path); // 타입이 이미 검사됨 → 안전
        }
        ```

### ✨번외

- **브랜디드 타입이 `never`가 아닌 이유**
    
    ```tsx
    type A = number & object; // never
    type B = number & {}; // number & {}
    type C = number & { _brand: "C" }; // number & { _brand: 'C' }
    ```
    
    `object`의 타입은 정확히 `object`이다. 따라서 원시형 타입과 인터섹션하면 `never`가 된다. 원시형 타입이면서 `object`일 수는 없으니까.
    
    그러나 객체 리터럴의 타입은 해당 객체 리터럴이다. 그리고 타입은 할당 가능한 값의 집합을 의미한다. 즉 객체 리터럴의 타입은 해당 프로퍼티을 갖는 값들의 집합을 의미한다.
    
    그러므로 원시형 타입과 객체 리터럴 타입을 인터섹션한 것은, 원시형 타입에도 포함되면서 특정 프로퍼티를 갖기도 하는 값이라는 것으로 판단할 수 있다.
    
    그러나 **이런 값은 실제로 존재하지 않는다**(런타임에서는). **그런데 왜 `never`로 평가되지 않는 걸까?**
    
    명쾌한 해답을 찾기 위해 찾아본 정보들을 적는다.
    
    - **자바스크립트의 원시형 타입이 프로퍼티에 접근하는 동작을 계승하기 위함이다.**
        
        자바스크립트에서 원시형 타입에서 메서드를 사용할 수 있는 이유는, 원시형 타입에서 프로퍼티에 접근 시 객체 랩퍼 타입으로 auto-boxing 되기 때문이다. 이는 마치 원시형 타입에서 직접적으로 메서드가 호출되는 것 같은 환각을 보여준다.
        
        이처럼 원시형 값이 프로퍼티에 접근할 수 있는 자바스크립트 동작을 계승하기 위해, 타입스크립트에서는 원시형 타입과 객체 리터럴의 인터섹션을 `never`로 평가하지 않는 것 같다.
        
        ```jsx
        const a = 1;
        console.log(a + 1); // 2
        console.log(a._brand); // undefined
        
        a.__proto__._brand = 'a';
        console.log(a._brand); // a
        ```
        
        출처
        
        - https://hrtyy.dev/anything/intersection-number-object/
        - https://bufferings.hatenablog.com/entry/2025/01/12/171721
    - **타입스크립트 컴파일러는 성능 저하 방지를 위해 불필요한 계산을 수행하지 않기 때문이다.**
        
        타입스크립트 컴파일러는 다음 이유로 불가능한 타입이라고 항상 `never`로 축소하진 않는다.
        
        > 프로퍼티 확인은 지연된다. 특정 타입의 프로퍼티가 계산될 필요가 없다면 그 프로퍼티는 계산되지 않는다. 무한한 프로퍼티 체인으로 된 경로가 존재할 가능성이 매우 높고, `never`가 해당 경로의 임의의 지점에 있을 수 있기 때문이다. ([#](https://github.com/microsoft/TypeScript/issues/42324#issuecomment-759771519))
        > 
        
        출처: https://stackoverflow.com/questions/65908355/why-is-it-allowed-to-intersect-primitives-and-objects-in-typescript
        
    
    근거는 서로 다르지만, 두 주장 모두 타당하다고 생각한다.
    
    두 주장에서 공통되는 의견은 **컴파일러에게 환각을 일으킨다**는 것이었다. 실제로는 불가능한 타입이지만 **타입 단언을 통해 컴파일러를 속이고**, 이를 이용해 구조적 타입 시스템에서 명목적 타이핑을 구현할 수 있다.
    
    또 런타임에서 불가능한 값이지만, 런타임 시점에 유효한지 아닌지는 중요하지 않다. 브랜디드 타입의 역할은 런타임 시점의 값이 아니라 컴파일 시점의 타입이기 때문이다.
    
- **더 안정적인 브랜딩 기법**
    
    ([출처](https://egghead.io/blog/using-branded-types-in-typescript), [번역본](https://siosio3103.medium.com/typescript-branded-types%EB%A1%9C-%EB%9F%B0%ED%83%80%EC%9E%84-%ED%83%80%EC%9E%85-%EC%95%88%EC%A0%95%EC%84%B1-%EA%B0%9C%EC%84%A0%ED%95%98%EA%B8%B0-768222c8df0d))
    
    - 1️⃣ 하드코딩된 `_brand` 프로퍼티 대신 `computed property name` 사용
        
        computed property name란, 변수를 사용해 프로퍼티명을 결정하는 것을 말함
        
        ```tsx
        let dynamicKey = 'productName';
        let item = {
          [dynamicKey]: 'Laptop',
        };
        item.productName; // Laptop
        ```
        
        참고로 인덱스 시그니처는 여러 프로퍼티의 타입을 한꺼번에 지정할 때 쓰는 거고 이거랑 다름
        
        ```tsx
        interface Scores {
          [subject: string]: number;
        }
        
        const s: Scores = {
          math: 90,
          english: 85,
          science: 88,
        };
        ```
        
    - 2️⃣ `key`를 중복 언급하는 걸 방지하기 위해 `unique symbol` 사용
    - 3️⃣ `Brand` 유틸리티 타입으로 편하게 사용
    
    ```tsx
    declare const __brand: unique symbol
    type Brand<B> = { [__brand]: B }
    export type Branded<T, B> = T & Brand<B>
    ```
    
    - 예시
        
        ```tsx
        type UserID = Branded<string, "UserId">
        type PostID = Branded<string, "PostId">
        type CommentID = Branded<string, "CommentId">
        type User = {
          id: UserID;
          name: string
        }
        
        type Post = {
          id: PostID;
          ownerId: string;
          comments: Comments[]
        }
        
        type Comments = {
          id: CommentID
          timestamp: string
          body: string
          authorId: UserID
        }
        
        async function getCommentsForPost(postId: PostID, authorId: UserID) {
          // fetch some data
        }
        const user = {} as User 
        const post = {} as Post
        const comments = getCommentsForPost(user.id, post.id) // ❌ This fails since `user.id` is of type UserID and no PostID as expected
        ```
        
- **태그 기법과 차이점**
    
    | 구분 | 태그 기법 | 브랜드 기법 |
    | --- | --- | --- |
    | 사용 목적 | **조건 분기 (타입 좁히기)** | **의미 부여 / 혼동 방지** |
    | 대상 | 객체 타입 | 원시형 타입 or 객체 타입 모두 가능 |
    | 런타임 값 | 있음 | 없음 (브랜드는 타입에만 존재) |

## 💬느낀 점

- 한 타입을 기본형과 느슨한 형태로 나눠본 적이 없는데, 지금 와서 생각해보면 라이브러리 내장 타입들은 이렇게 설계된 게 많은 것 같다.

- "타입 시스템 개발자들은 수십 년의 경험을 가진 언어 전문가입니다(p167)" << 멋있당
- 변수명에 타입을 적으면 안되는 것은 알고 있지만서도… `string`타입을 `number` 타입으로 변환할 때 `numeric...`처럼 이름을 짓는 습관이 있는데, 이런 경우는 어떻게 해야 할까?
- `null` 값이 내부로 들어가지 않도록 경계에서 처리하는 것은 어찌보면 당연한데 별 생각 없이 코드를 짜거나, 이미 있는 코드에 하나씩 추가하다보면 `null`이 난무하는 경우가 있는 거 같다.
- 클래스 만들 때 static으로 init 메서드를 만들고 거기서 인스턴스를 반환하는 건 넘 꿀팁이다. TS로 클래스 만들 때 고통스러웠는데 저렇게 하면 되는구나… 흑흑
