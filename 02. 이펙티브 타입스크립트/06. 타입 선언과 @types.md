## 📌typescript와 @types 의존성 관리

- 타입스크립트, `@types`는 런타임에 필요하지 않으므로 `devDependencies`로 추가함
- 타입스크립트 버전을 동료와 통일하기 위해 시스템 레벨이 아닌 `devDependencies`에 포함해야 함
- `@types`는 [DefinitelyTyped](https://github.com/DefinitelyTyped/DefinitelyTyped)에서 특정 라이브러리의 타입 정의를 제공하는 패키지
- `@types`는 라이브러리 버전, `@types` 버전, 타입스크립트 버전에 의존함 ⇒ 호환에 신경써야 함
- `@types` 🆚 `index.d.ts`(타입 선언을 번들링해 라이브러리 자체에 포함하는 방법)
    - `@types`는 여러 버전으로 관리하기 쉽지만, 번들된 타입은 어려움
    - `@types`는 라이브러리 버전에 맞춰 버전을 선택할 수 있지만, 번들된 타입에선 불가능
    - 번들된 타입이 다른 라이브러리의 타입 선언에 의존하면, 프로젝트를 새로 설치했을 때 타입 오류 발생 (의존한 라이브러리의 타입 선언이 패키지 의존성에 없기 때문)
    - `@types`는 커뮤니티에서 관리되지만, 번들된 타입은 자체 관리해야 함
    - 타입스크립트로 작성된 라이브러리이면 컴파일러로 `index.d.ts`를 만들어 라이브러리 자체에 선언을 포함하는 것을 추천, 자바스크립트로 작성된 라이브러리는 `@types` 추천

## 📌라이브러리 제작 시 타입 주의사항

### ✅공개 API에 등장하는 모든 타입을 export하기

- 라이브러리 사용자가 타입을 쉽게 사용할 수 있도록, 타입을 숨기지 말고 `export`하자
    - 어차피 공개 API이면 `ReturnType`, `Parameters`으로 함수 시그니처의 타입을 추출할 수 있음
    - 사용자가 이런 일을 직접 할 필요가 없도록 `export`하자

### ✅API 주석에 TSDoc 사용하기

- 공개 API 주석에 TSDoc(`/** … */`)을 사용하자
- 단 타입 정보가 코드에 있으므로 타입 정보는 명시하지 말자

### ✅콜백 함수에서 this 타입 제공하기

- `this`는 렉시컬 스코프가 아니라 다이나믹 스코프 ⇒ 호출 방식에 따라 값이 달라짐
- 콜백 함수에서 `this`를 사용할 경우 타입을 명시하자

### ✅의존성 분리를 위해 미러 타입 사용하기

- 작성중인 라이브러리가 의존하는 라이브러리의 구현과 무관하게 타입에만 의존한다면, 미러 타입 사용
- 미러 타입: 의존하는 타입과 구조적으로 호환되는 타입
- 라이브러리 타입 대신 미러 타입을 만들어 사용 ⇒ 의존성 분리

## 📌오버로딩 타입보다 조건부 타입 사용하기

- 조건부 타입으로 오버로딩 타입보다 정교하게 타입을 지원할 수 있음
    
    ```tsx
    function double<T extends number|string>(
    	x: T
    ): T extends string ? string : number;
    
    function double(x: any) {
    	return x + x;
    } 
    ```
    
- 오버로딩 타입이란? (아이템 3 참고)
    
    ```tsx
    function dobule(x) {
    	return x + x;
    }
    ```
    
    ```tsx
    // 1. 유니온 타입을 사용할 경우
    function double(x: number|string): number|string; // number 넣고 string 반환도 허용
    ```
    
    ```tsx
    // 2. 제네릭을 사용할 경우
    function double<T extends number|string>(x: T): T;
    function double(x: any) {
    	return x + x;
    }
    const num = double(1) // 넣은 대로 반환 타입이 정해지지만, 타입이 1로 너무 과함
    ```
    
    ```tsx
    // 3. 하나의 함수 구현체에 여러 타입 선언을 오버로딩할 경우
    function double(x: number): number;
    function double(x: string): string;
    
    function f(x: number|string) {
    	return double(x);
    						//  ~ 'string|number' 형식의 인수는
    						//    'string' 형식의 매개변수에 할당될 수 없습니다.
    }
    ```
    

## 📌타입 선언 테스트

- 타입 테스트 시, 타입 간 동일성과 할당 가능성의 차이를 주의해야 함
    - ex) 함수 반환 타입이 `number`여야 할 때, 테스트를 잘못 설계하면 숫자 리터럴도 통과될 수 있음
- 함수에 콜백이 있는 경우 콜백 매개변수의 추론된 타입을 체크해야 함
- 함수에 `this`가 포함된 경우 `this`의 타입을 테스트해야 함
- `dtslint`로 간편하게 타입 테스트 가능
    - 특수한 주석으로 타입 테스트를 할 수 있게 해주는 도구
    - 명시한 타입과 실제 타입이 동일한지 문자열 비교를 통해 테스트함
    - ⇒ 할당 가능성이 아닌 타입이 같은지를 비교함
    - ⇒ 문자열 비교이므로 `string|number`와 `number|string`이 서로 다르다고 판단함
    
    ```tsx
    const beatles = ['john', 'paul', 'george', 'ringo'];
    map(beatles, function(
    	name, // $ExpectType string
    	i,    // $ExpectType number
    	array // $ExpectType string[]
    ) {
    	this; // $ExpectType string[]
    	return name.length;
    });     // $ExpectType number[]
    ```
    

## 💬느낀 점

- TSDoc 주석이 마크다운 형식으로 꾸며진다는 것, 객체 필드에 TSDoc으로 주석을 달면 필드별로 설명을 볼 수 있다는 것을 처음 알았다.
- `dtslint` 되게 편해보인다 주석으로만 적어주면 되니까
  - '제대로 된 타입 언어라면 애초에 타입을 테스트할 필요가 없을 것'이라는 정욱님 말씀에 '그렇네?' 싶었다. C 언어의 타입을 누가 테스트 하겠는가? 좋게 말하면 유연성, 나쁘게 말하면 허점이라고 표현할 수도 있겠다.
- 일반적인 타입스크립트 사용보다는 특수한 상황(ex. 라이브러리 제작 등)에서 겪는 일들을 이야기하기 시작하는 걸 보니, 이 책도 거의 다 읽었구나 가 실감됨.. 앞으로 두 장 남았다..!
