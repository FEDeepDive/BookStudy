## 아이템 1. 타입스크립트와 자바스크립트의 관계 이해하기

- 타입스크립트는 자바스크립트의 상위집합(superset)
  - 자바스크립트는 타입스크립트의 부분집합(subset)
  - 모든 자바스크립트 프로그램은 타입스크립트이지만, 그 역은 성립하지 않는다
- 그러나 타입스크립트로 작성된 프로그램이 "타입스크립트 문법을 잘 지키는지"와 "해당 프로그램이 잘 동작하는지"는 별개의 문제
- 타입 시스템의 목표 중 하나는 런타임에 발생할 오류를 미리(정적으로) 찾는 것
- 타입 구문을 작성하여 타입스크립트에게 코드의 "의도"를 전달할 수 있다
- 타입스크립트 타입 시스템은 자바스크립트의 런타임 동작을 "모델링"함
  - 타입스크립트가 이해하는 값의 타입과 실제 값에는 차이가 있음
  - 타입스크립트의 타입 시스템은 정적 타입의 정확성을 보장하기 위해 만들어지지 않았기 때문

## 아이템 2. 타입스크립트 설정 이해하기

- 타입스크립트 컴파일러는 매우 많은 설정을 가지고 있고, 개중에는 언어 자체의 핵심 요소를 제어하는 것도 있음
  - `noImplicitAny`, `strictNullCheck` 등
- 매번 커맨드라인 상에서 설정을 주입하기보다는 `tsconfig.json` 설정 파일을 작성하는 것이 좋음

## 아이템 3. 코드 생성과 타입이 관계없음을 이해하기

- 타입스크립트 컴파일러(`tsc`)는 크게 아래의 두 가지 기능을 수행함
  - 최신 타입스크립트/자바스크립트 코드를 브라우저에서 동작 가능한 자바스크립트 코드로 트랜스파일
    - (#) `tsc`는 자바스크립트 코드도 트랜스파일이 가능하군요...
  - 코드의 타입 오류 체크
- 두 기능은 서로 완벽히 독립적이며 서로의 동작에 영향을 주지 않음
- 타입 오류가 있는 코드도 컴파일이 가능함(!!!)
  - 타입 오류가 있을 때 컴파일하지 않게 하는 `noEmitOnError` 설정이 존재
- 타입스크립트가 자바스크립트로 컴파일되는 과정에서 모든 인터페이스/타입 구문은 제거되기 때문에 런타임 타입 체크는 불가능함
  - 런타임에 타입 정보를 유지하는 방법을 몇 가지 생각해볼 수 있음
  - 속성 체크 / 태그 기법 / 클래스 타입 등
  - (#) 저는 태그 기법이 마음에 들어서 자주 사용합니다
- 타입스크립트 타입은 런타임에는 타입 체크뿐만 아니라 타입을 바꾸는 연산도 영향을 주지 않으며, 런타임 자바스크립트 타입 검사 및 변환을 별도로 수행해야 함
- 또한 런타임 중 실제 값은 선언된 값과 다를 수 있음
- 타입스크립트 타입만으로 함수 오버로딩 또한 불가능함
- 타입스크립트 타입 처리는 온전히 빌드타임 오버헤드일 뿐 런타임에는 영향을 미치지 않음

## 아이템 4. 구조적 타이핑에 익숙해지기

- 자바스크립트는 본질적으로 덕 타이핑 기반이며, 타입스크립트는 이를 모델링함
- 특정 타입의 속성을 동일하게 가지고 있는 다른 타입을 가져다 사용할 수 있음
- A, B 두 타입이 "구조적으로 호환"되는 경우 A 타입을 매개변수로 받는 함수에 B 타입의 인자를 넣는 등의 동작이 가능
- 여기서 "구조적 타이핑"이라는 용어가 사용됨
  - (#) 같이 주로 나오는 용어로 "명목적 타이핑"이라는 것도 있죠? 같은 구조라도 타입명 자체가 다르면 호환되지 않는...
- 타입스크립트에서 타입은 열려있으며, 이는 곧 타입에 선언된 속성 외에 임의의 속성을 추가하더라도 오류가 발생하지 않는다는 뜻

## 아이템 5. `any` 타입 지양하기

- 타입스크립트 타입 시스템은 코드에 타입을 조금씩 추가할 수 있기 때문에 점진적이며 언제든 타입 체커를 해제할 수 있기 때문에 선택적
- `any`를 사용하여 타입 체커를 무효화할 수 있음
- `any`를 사용하게 되면 타입 체커뿐만 아니라 자동완성 기능 등의 언어 서비스도 적용되지 않음
- 타입 체커를 통과했다고 디버깅이 끝나는 것이 아니며, 런타임에 오류가 발생할 수 있음
- `any`를 사용하면 타입 설계를 감춰버리게 되며 타입 시스템의 신뢰도를 떨어뜨리기 때문에 최대한 사용을 피하자
