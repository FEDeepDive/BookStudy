## 📌any 타입 다루기

### any 사용 시 주의할 점

- `any` 는 생각하는 것보다 더 넓으니, 구체적인 타입을 사용하자
- 암시적 `any` 및 `any[]`타입은 할당되는 값에 따라 다른 타입으로 진화할 수 ****있다 ⇒ 예측하기 어려움
- 함수 반환 타입을 `any`로 두지 말자
- `noImplicitAny`가 설정되어 있어도 `any`가 존재할 수 있다 (명시적으로 선언 or 라이브러리로부터 전파된 경우)
    - ⇒ **타입 커버리지**로 남아 있는 `any` 추적 가능
- 오류를 없애는 게 목적이면 `@ts-ignore`도 있다 (단, 부작용 O)

### 써야 하는 경우 좁은 범위에서 다루기

- `any`로 타입 단언을 해야 하는 경우, 함수 안에서 하자
    - 함수 내부에 숨겨서 함수를 사용하는 측에서는 `any`가 사용되었는지 모르게 함
    - 매개변수로 넘길 때 `any`로 넘겨야 한다면, 변수 자체가 아닌 매개변수 값을 단언하자
        
        ```tsx
        const x = 1 as any;
        f(x); // 이렇게 하지 말고
        
        const y = 1;
        f(y as any); // 이렇게 해라
        ```
        

## 📌unknown이 필요한 경우

- 모르는 타입이면 `any`가 아닌 `unknown`을 사용하자
- `unknown` 대신 제네릭을 사용하지 말자
    
    ```tsx
    // unknown + 타입 단언(또는 좁히기) 쓰는 게 낫다
    function safeParseYAML(yaml: string): unknown {
      return parseYAML(yaml);
    }
    const book = safeParseYAML(data) as Book;
    ```
    
    ```tsx
    // 제네릭을 unknown 대신 쓰지 말자
    function safeParseYAML<T>(yaml: string): T {
      return parseYAML(yaml);
    }
    const book = safeParseYAML<Book>(data); // ❌
    ```
    
- (참고) `any`, `unknown`, `never` 비교
    
    타입 시스템에서 어떤 집합은 다른 집합의 상위 집합이면서 부분 집합일 수 없음
    
    |  | any | unknown | never |
    | --- | --- | --- | --- |
    | 어떤 타입이든 상위 집합인가? | O | O | X |
    | 어떤 타입이든 부분 집합인가? | O | X | O |
    | 타입 시스템에 부합한가? | X | O | O |
- (참고) `unknown`, `{}`, `object` 비교
    - `unknown` 타입은 모든 타입을 포함함
    - `{}` 타입은 `null`과 `undefined`를 제외한 모든 값을 포함함
    - `object` 타입은 모든 non-primitive 타입을 포함함 (객체, 배열 등)

## 📌안전하게 동적 프로퍼티 생성하기

- 런타임 시 동적 프로퍼티를 생성하면
    - 타입 체커가 알아채지 못함
    - `window`, `DOM 노드`에 추가할 경우 전역 변수로 선언되어 의존성이 생김 → 부작용
- ⇒ 런타임에 동적으로 코드를 바꾸지 말자
- 안전한 방법
    - `interface`로 보강(augmentation)
        
        ```tsx
        interface Document {
        	someProp: string;
        }
        ```
        
        ```
        🚨
        
        보강 시 전역으로 적용되고, 모듈 관점에서 제대로 동작하려면 `global`로 선언해야 하며, 실행 시점에 어떤 엘리먼트는 속성이 있고 어떤 엘리먼트는 없을 수도 있다.
        
        ```
        
    - 타입 단언
        
        ```tsx
        interface MonkeyDocument extends Document {
        	monkey: string;
        }
        (document as MonkeyDocument).monkey = 'Tamarin';
        ```
        

## 💬느낀 점

- 가능하면 `any` 사용을 피하고 구체적으로 명시하자는 내용들은 기본적인 내용 같았음. 그럼에도 불구하고 한 장을 들여 설명한 이유는 **그만큼 중요해서** (+TS 책인데 안 짚고 넘어가긴 찝찝하니까)일 것 같다.
- 4장의 브랜디드 타입 부분에서 객체와 원시 타입의 인터섹션 타입에 의문을 가지면서, `{}`도 참 이상하다는 생각을 했었다. 뭔데 이것저것 다 되지? 그냥 빈 객체라고 생각했는데 생각보다 매우매우 넓었구나. `object`도 마찬가지(JS에서 `object`는 지뢰같다..ㅠ)로 사용에 주의해야할 것 같다.
- `unknown` 대신 제네릭을 사용하는 방식이 대표적인 안티 패턴이라고..? 마치 내 모습.. `unknown`에 타입 단언을 쓰는 거랑 제네릭으로 쓰는 거랑 안정성 면에서 별 차이 없다고 생각이 드는데 (어차피 함수를 호출하는 인간이 `as T` 또는 `<T>`로 쓰는 거니까..).
    - ⇒ `unknown`은 타입을 한 번 보호해주고 그걸 사용하는 입장에서 검증 또는 단언을 해야만 하지만, 제네릭은 바로 사용할 수 있게 함. 잘못된 타입으로 단언하더라도 한 번 검증해야 하는 것과 아닌 것에는 차이가 있음. 즉 **신뢰성과 책임** 면에서 제네릭보다 `unknown`을 쓰는 게 나음.
    - ⇒ 제네릭과 `unknown` 모두 잘못된 타입을 써도 타입 검사에 통과하고 런타임에서야 에러가 발생함. 그러나 에러 발생 요인(지점)을 추적할 때, `unknown`을 쓴 경우는 `as` 또는 타입 가드로 좁힌 지점이 코드에 남지만, 제네릭은 함수 시그니처가 해당 타입임을 보증하는 것처럼 보이므로 추적하기 더 어려움.
