## 감상평

### `보경`

- 아이템 38

  - 함수의 매개변수로 들어가는 타입이 `any`라면 인자로 전달할때 단언
  - 객체 전체를 `any`로 정의한다기보단 `any`값을 `value`만 단언
  - any를 반환할 경우 상위 스코프에서도 any 타입이 영향을 미치게 된다는 의미
  - 엥? 난 책 읽고 @ts-ignore이 더 좋다고 이해하지 않았는데… 이런의도였군

- 아이템 39

  - 모든값이 올 수 있는 배열인 경우 any 타입대신 any[]
  - 모든값이 올 수 있는 객체인 경우 any 타입대신 {[id: string]: any}
  - 모든 타입의 값을 리턴하는 함수일 경우 any 타입대신 () ⇒ any

- 아이템 40

  - 복잡한 로직의 함수라 안전한 타입으로 구현하기 어려운 경우, 매개변수와 리턴타입을 명확하게 명시한 뒤 함수의 내부에서 단언해도 된다.

- 아이템 41

  - any는 진화한다! 단 noImplicitAny가 설정된 상황에서만!
  - 암시적 `any` 타입은 함수 호출을 거쳐도 진화하지 않음. 반드시 값 자체를 업데이트 해야 진화됨
  - 근데 사실 이해가 잘안됨 ㅋㅋ….; 특히 마지막 예제

- 아이템 42

  - instanceof, is, in 등의 타입 좁히기 기능을 사용하여 안전하게 사용하자

- 아이템 43

  - 보강보다는 사용자 정의 인터페이스 단언. 즉 인터페이스를 확장해서 새로 정의한 뒤 사용하자.
  - 타입이 더 안전하고, 속성에 주석을 붙일 수 있고, 속성을 자동완성 할 수 있고, 몽키패치 시점의 기록이 남음
  - 보강은 전역적으로 적용되기 때문에 코드의 라이브러리나 일부와 분리할 수 없음.
  - 만약 보강이 런타임환경에서 발생한다면 제대로 적용되지 않는다.
    - ex) 버튼 클릭시 엘리먼트에 어떤 기능을 담은 속성을 보강할 때, 이전에 생성된 엘리먼트는 해당 속성이 없고, 버튼이 클릭되고 난 후 생성된 엘리먼트는 속성이 있는 문제가 생김

- 아이템 44

  - npx type-coverage 패키지를 활용해 any가 얼마나 쓰였는지 확인하고 주기적으로 점검

- 전체
  - 타입스크립트에서 any를 논하는 것은 흔한 일인데 이 파트에서는 새롭게 알게된, 혹은 잊고있던것을 상기시켜주는 주제를 다뤄줘서 좋았다.
  - 타입에 대해 잘 알고있다고 생각했는데 `{}`, `object`, `unknown`이 세가지 타입에 대해 질문받았다면 제대로 대답 못했을 것 같다.
  - 타입커버리지는 처음보는데 신기하군
  - 타입을 완벽하게 안전하게 설계해주겠어!!라고 생각했었는데 40장을 보니 확실히 논리적으로 복잡한 내부 코드는 그냥 단언을 해도 괜찮겠다… 라고 생각했다. 결국 개발이란 코스트에 비해 최대의 결과물을 출력해야 하는데 타입 설계에 시간을 쏟고, 머리를 엄청 쓰는것보다 단언하고 다른 기능을 개선하는것이 나을 듯함
